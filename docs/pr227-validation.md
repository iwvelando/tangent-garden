# PR #227: final local validation

This change batches storage for refined spatial points and cached canal contact circles. The intended result is the same drawing, controls, refinement decisions and exports, with fewer Go allocations. No visible feature or playback speedup is promised.

## Start the development UI

Run from the reviewed branch's checkout:

```sh
npm run dev -- --port 5177 --strictPort
```

Keep that process running, then follow the links below. Each link restores the complete preset, including its layers, camera and animation. Linked studies appear as **Custom study**, which is expected. If using a different port, replace 5177 in the URL. ## Experience the change

1. Open **A cord twisted round a spring**. In **Sampling & definition**, confirm **Refine between samples** and **Refine the surface too** are enabled. Six smooth strands should wind around the five-coil tube, with points and surface columns reported beneath the options.
2. Play its existing 14-second back-and-forth animation. The strands unwind, then wind back. Pause, resume, and scrub to the middle: the strands are untwisted there and the added-point count is much smaller. Scrub back to the beginning and check the opening shape returns.
3. Turn refinement off, wait for calculation, then on again. The coarse drawing should recover its original smooth form, with no stale geometry or connected gaps. Reopen the spring link to restore the entire preset.
4. Open **A beaded trefoil wound with spiral stripes**. Inspect the twelve smooth stripes over the beads. Toggle surface refinement to see why it matters on the concave side, then reopen the link to restore it.
5. Open **A spring folded into a cusp**. This zoomed composed curve exercises the shared point storage away from the main example. Its small coils and existing gap at the cusp should remain stable while you orbit or zoom.
6. Revisit the spring and trefoil, switch between light and dark themes, and export a PNG. Check the exported geometry and colors agree with the live view.

These are human visual checks; they do not measure the allocation improvement. Measure that separately with:

```sh
go test ./engine3 -run '^$' -bench '^BenchmarkSpringRefinement$' -benchmem
```

The integrated arm64 build measured about 6,031 allocations and 15.16 MB per frame. Results depend on compiler and architecture. The regression tests allow 8,000 allocations for the spring and 500 for the isolated winding path.
