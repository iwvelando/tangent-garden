# Architecture and extension boundaries

## Current shape

`expression text or roulette, Lissajous, Fourier, pursuit, or vector-field generator → planar curve evaluator → optional derived input (evolute, pedal family, or offset) → numerical construction → sampled geometry → SVG`

An implicit curve takes a separate path: `F(x, y) → grid and marching squares → contours → SVG`, with no construction. So does an iterated map: `map and start → iterates → visit counts in a grid → PNG image embedded in the SVG`.

The `engine` package has no browser, React, filesystem, or network dependency. It can run natively in Go tests or in WASM unchanged. `cmd/wasm` is the only package importing `syscall/js`. The bridge takes one JSON request and returns one JSON result/error; the TypeScript types mirror that schema. The one exception is an implicit surface's mesh, whose arrays travel typed beside its JSON (below).

A classic Web Worker loads the matching Go runtime and WASM module. Requests are debounced and numbered; stale responses cannot overwrite newer studies. The UI remains usable during calculations. The initial build uses ordinary Go, not TinyGo, to minimize numerical and runtime compatibility surprises. See [Go's WebAssembly documentation](https://go.dev/wiki/WebAssembly) for the compiler/runtime pairing requirement.

`EngineClient` correlates worker requests and rejects failed/timed-out requests. The worker resolves scalar expressions using the Go `tangentGardenScalars` bridge before calling `tangentGardenCompute`; curve geometry and expression semantics stay in Go. Editor bounds retain their original text, while returned frames carry the resolved numerical configuration. Numeric parameter fields (`ScalarInput`) do the same through `tangentGardenScalars` directly: each keeps its text and applies only the resolved finite value, reporting pending evaluations (which count as busy) and parser errors (named in the alert) to the app. Because resolution is asynchronous, configuration changes are functional updates of the latest state, the source-coordinate conversion awaits pending evaluations, and choosing a preset drops evaluations begun before it. Readiness is tied to the exact input revision so export and playback cannot consume a stale frame during a debounce.

`AnimationPanel` owns a cancellable playback session with immutable original and endpoint frames. Reveal playback slices the precomputed geometry; ray `sampleIndex` values associate construction lines with the same sample grid. Parameter playback interpolates inputs and asks Go for new geometry. It never interpolates output curves across potential singularities. An epoch invalidates in-flight results on stop, pause, or edits; the live loop awaits one frame at a time and derives progress from a monotonic clock. Exact cached endpoints prevent accumulated interpolation error at completion. Discrete counts are rounded; categorical controls remain fixed. Curve parameter `a` is bound as a number by the expression parser, not substituted into expression text.

The plot's automatic animation camera is separate from manual camera state. Holding the current view snapshots the effective center and scale after manual pan/zoom (and the grid span), shared by playback and export. Holding the final view fixes both center and scale; following fixes scale only; fitting uses each current frame. Ray lengths during animation use the final reference span so choosing a camera cannot change the world-space ray lengths. Stopping removes the automatic override and restores the manual view.

Animation export reuses the session sampler and lazily loads `export-animation.tsx`. React's static renderer produces the same `Plot` SVG independently of the live DOM, then an opaque sRGB canvas rasterizes each frame. The rendering loop is independent of format and hands each canvas to a frame sink. For WebP, the browser supplies a still WebP bitstream and `animated-webp.ts` packages full frames according to the [WebP RIFF specification](https://developers.google.com/speed/webp/docs/riff_container), with explicit millisecond durations and a finite or infinite loop count. For MP4, WebCodecs `VideoEncoder` produces H.264 and `mp4-video.ts` writes a video-only ISO/IEC 14496-12 file (`ftyp`, `moov`, `mdat`, index first so playback can start immediately) with a millisecond timescale and each frame's exact duration. The encoder uses Constrained Baseline, which cannot contain B-frames, so decode order is display order and the writer needs no composition offsets; it rejects dropped or reordered output rather than guess. Output is matched to input by timestamp within half a millisecond, the file's timing precision, because WebKit rounds `VideoFrame` timestamps (8,033,000 µs becomes 8,032,999); frame durations always come from the export timing, never from the encoder. The H.264 level is the smallest whose frame-size, macroblock-rate, and bitrate limits fit the export, and the quality slider maps exponentially to bits per pixel. Keyframes fall every two seconds, the encoder backlog is bounded, and each `VideoFrame` is closed once submitted. The encoder's reported colour space is written as an `nclx` box only when every code point is known. `export-formats.ts` detects support before offering a format: canvas WebP by what `toDataURL` actually returns (Safari returns PNG), MP4 by `VideoEncoder.isConfigSupported` for the exact size, frame rate, and bitrate. There is no screen capture, server, or additional codec dependency. Frames are calculated ahead of drawing through `lookahead.ts`, which yields results in frame order with a bounded number in progress, so engine calculation overlaps SVG rasterization and encoding. Parameter-animation exports whose frames need calculation add up to three temporary engine workers (leaving a core free for drawing; at most one on devices whose primary pointer is touch, since each can hold ~100 MB), assigned round-robin; they run the same WASM engine on the same inputs, so frames are identical to a sequential export. The temporary engines exist only for that export and are terminated on completion, cancellation, error, or an input edit; each can hold on the order of 100 MB for expert-scale studies while it runs. Live playback keeps at most one calculation in flight per engine (`playback.ts`). 3D parameter playback adds one helper engine where an export could (`playbackEngineCount`): it prepares the final endpoint while the app's engine prepares the first, then the two alternate, each request spaced by the measured round trip divided between them, so one calculates while the other's frame is drawn. A reply older than the frame on screen is dropped, so progress only rises. The helper exists only while playing; pause, stop, completion, an edit or failure terminate it, and scrubbing and export keep a single engine. Only compressed frames accumulate, bounded by a frame-count limit and a compressed-size limit. Abort signals and the session epoch suppress stale frames and downloads; a canceled in-flight calculation/encode may finish but its result is discarded. The selected theme/layers are snapshots. Export uses deterministic sample progress rather than real elapsed time, so slow calculations do not shorten or lengthen the saved animation. Browser integration tests independently decode the actual downloaded files to check frames, timing, dimensions, and colors: WebP through Chromium's `ImageDecoder`, MP4 through `ffprobe` (codec, profile, frame count, per-frame times and durations) and a Chromium `<video>` element (duration, endpoints, background colour). The `<video>` check runs on a blank page, because the app's policy has no `media-src` and the app itself never plays media. CI installs ffmpeg; local runs without `ffprobe` skip only those assertions and note it in the report.

Theme preference is a three-state value (system/light/dark). The system mode listens for media-query changes; explicit choices use local storage, with an in-memory fallback when storage is denied. Collapsible sections (Animation, Export settings, the expression and refractive-index references, and numerical notes) remember whether they were left open, under the same fallback rule; Animation and Export settings start collapsed. Field explanations sit behind per-field help toggles rather than hover tooltips, so they work on touch screens. Side-by-side fields (`.pair`) lay out as a CSS subgrid with shared label, control, and help rows: labels align to the bottom of their row, so a wrapped label keeps the controls level, and opening one field's help adds space below both controls without moving either. The sidebar and article have independent scroll containers on desktop, while mobile retains ordinary document scrolling. On mobile the page reads drawing, controls, then the explanation ("Behind the lines", or "Behind the folds" in 3D, numerical notes, and the closing line), so the interactive controls follow the drawing directly; wide layouts keep the explanation under the drawing in the right column. Because mobile places the controls below the drawing, starting or resuming playback jumps the drawing into view when it is not fully visible (instantly rather than smoothly, so no opening frames are missed; both notebooks share `web/revealDrawing.ts`), and the playback controls (buttons, progress, status) dock to the bottom of the screen while an animation is active.

Study links (`web/study-link.ts`) carry a notebook's study in the URL fragment as base64url of raw-deflated JSON, `{ v, notebook, study }`, through the browser's `CompressionStream`, with no server and no new resource category. The envelope is read before any notebook loads. `Notebook` in `main.tsx` then hands the unchecked study to its notebook, which conforms it with its own link module (`planar-link.ts`, `spatial/link.ts`, `tesseract/link.ts`). Each module's schema is typed `SchemaOf<T>` against the notebook's configuration type, so adding a field without deciding how links validate it fails `tsc`. The schema bounds text length and list sizes, closes every option set, and requires exact tuple lengths. It also refuses unknown fields, naming each one, and fills fields a link predates from the notebook's defaults; the 4D module uses the object descriptor's defaults. Animation tracks must name targets the linked study offers. Go still validates every numerical limit as for typed input. A notebook applies a link through the same replacement path as a preset. It advances the scalar generation, then restores its layers and passes the manual camera to the plot for that reset. The animation setup goes to the panel only once the frame belongs to the linked study, so the panel's target filter cannot drop the linked tracks. The encoded fragment is bounded at 32 KB and its inflated JSON at 256 KB.

React owns form state and presentation. SVG provides equal x/y scale, and supports inspectable vector export without rasterizing. The exported SVG records its inputs in a description element and includes explicit colors. PNG export (`export-image.ts`) clones the live SVG, sets its intrinsic size to the chosen still size (2000 × 1520 by default), and rasterizes it onto an opaque canvas, or one with alpha when the background is left out of the clone, so the PNG is drawn from vectors at its final size rather than upscaled from the screen. The size and background are settings of the shared `ExportImageMenu`, as multiples of each notebook's page; the 3D notebook draws its transparent stills over black and white and recovers alpha with `matte.ts` (see [mathematics](mathematics.md#still-exports-size-and-transparent-background)). The SVG uses only inline attributes, so it renders identically outside the page; browser tests compare the PNG with the exported SVG rasterized independently. Curve and optical computations remain in Go; frontend source-coordinate conversions only change the editor representation. Sample and line counts up to 32,768 and 2,048 permit dense drawings, with explicit workload limits and possible responsiveness costs.

Refinements first built for the 3D notebook are shared where they apply to the 2D and 4D notebooks, rather than copied. Live playback in every notebook runs on `web/playback.ts`'s `play()`, which spaces requests across one or two engines ("lanes") and drops replies older than the frame on screen; the 2D and 4D notebooks add a helper engine only while calculated frames play, and the 2D helper prepares the end beside the start. Line weights (`web/line-weight.ts`, the control `LineWeightField`) hold the choices, scale, link schema and help; the 3D renderer draws them as WebGL strokes and the 2D and 4D drawings through `svgStroke`, which leaves a regular stroke's width untouched so existing drawings are byte-identical. Refinement between samples is one Go package, `engine/refine`, generic over the point type: `engine3` and `engine` each supply a distance from a point to a chord and adapt its result to their JSON (`RefinedPath`), and `web/refinement.ts` and `RefineBetweenSamples` give both notebooks the reveal cut, readout and control. The 3D and 4D turntables share named views and the orientation indicator: `web/named-views.ts` is their descriptor (labels, help, yaw and pitch, `turnTo`, `turntableBasis`) and `web/Orientation.tsx` draws both under the drawing's frame. The 4D app turns its shadow's `view` state; the 3D camera lives in `SpatialPlot`, which applies a `turn` prop to the shown camera and reports each drawn view, whose rows `scene.ts`'s `viewBasis` reads from `camera`, through an `OrientationFeed` to `LiveOrientation`, so orbiting re-renders only the indicator. The axis inks live in `palette.ts` as `axisInks`. The parameter probe's notebook-independent parts (`web/probe.ts`: the sample index, plot scale, inks and how a curve probe holds its place while parameters vary; `ProbePlot`) serve the 3D `ProbePanel` and the 2D `PlanarProbePanel`; the 2D diagnostics come from `engine/diagnostics.go`, asked by the worker's `diagnostics` flag, and the plot draws the probe at the sample the live probe or the animation view gives it.

Vite generates a static bundle with relative paths. There is no hosting provider integration; the output can be served by an ordinary static host. Dependencies are recorded in `package-lock.json`.

## Adding a 2D construction

1. Define the mathematical convention and independent analytic expectations.
2. Add pure Go geometry and tests. Preserve null gaps and diagnostics.
3. Extend the request/result schema deliberately on both sides of the bridge.
4. Add controls and a verified preset. Keep rendering separate from computation.
5. Run `make thumbnails` so the example gallery can show the new or changed preset.
6. Run `make check` and `make test-browser`.

## 3D without premature generalization

Keep `Vec` and the current 2D engine honest about their dimension. A future `geometry3` or `engine3` package should define a separate `Vec3`, space curves, parametric surfaces, and meshes. Do not append a dummy z coordinate to the present SVG API.

Reflection/refraction formulas generalize to 3D with a surface normal. Involutes of regular space curves also admit `r−sT`. However, a planar evolute does not transfer as a unique envelope curve of all normals in space, and a two-parameter surface ray family generally forms a caustic surface. Those objects need their own definitions and singularity handling. Projecting rays onto a receiver surface is another operation, with a separate result type.

Reusable boundaries are expression parsing, numerical policies, pure Go geometry, a versioned transport adapter when needed, and worker execution. WebGL coexists with SVG through separate rendering contracts. Piecewise definitions, adaptive sampling, and saved studies remain prospective features.

Source coordinate choice is independent of curve format. Optional source `coordinates`, `radius`, and `theta` preserve existing Cartesian requests; polar requests are converted by Go and return `sourcePosition`, which the worker copies into the resolved frame configuration. Animation target availability follows the source coordinate choice, so switching modes invalidates incompatible tracks.

Framing derives robust bounds independently for base, derived, and each offset stack member (plus circle extents, a roulette's fixed and rolling circles, a Lissajous figure's guides and a Fourier curve's circles, each pursuer's path and each vector-field trajectory, the rolling construction's circles, and the circle enclosing a rolling curve at each placement), then unions the surviving extrema. Outer Tukey fences reject isolated asymptotic tails without using the base curve as a distance cutoff for derived points. Short prefixes retain both families even with a large involute offset. The policy is explicitly heuristic; manual framing remains the way to examine distant branches.

Export quality controls intrinsic SVG rasterization size (1000 × 760 or 2000 × 1520) and canvas encoder quality (0.95 or 1.0). The shared viewBox and camera do not change. No promise of lossless encoding is made across browsers. Scrubbing keeps the timeline enabled and its thumb under the pointer, calculates at most one frame at a time, and renders only the latest requested position, so a fast drag cannot build a backlog. Completed animation sessions keep the final frame and scrub support but unlock their settings; editing invalidates that preview before preparing a new session.

Brand assets live in `public/tangent-garden.svg`, shared by the header, favicon, and README. Package, Go module, bridge symbols, titles, and download filenames use the Tangent Garden name. The browser theme preference is stored under `tangent-garden.theme`.

Pedal-family constructions (`pedal`, `contrapedal`, `orthotomic`) use an independent `pole` vector in the request/configuration, not the optical `source`. `engine/pedal.go` projects onto a stable first-derivative tangent, permitting zero curvature and C1 curves. Each is a separate `kind` string end to end, so Go dispatch, export filenames, and metadata stay explicit; `usesPole` in `engine/pedal.go` and `web/types.ts` names the family, and the UI groups it behind one tab with a Projection selector. Representative origin/target samples identify the tangent or normal foot; for orthotomics, the target is the reflected point and the renderer recovers the foot as the midpoint of the pole and target, drawing the reflected half dashed. The renderer adds the pole-to-foot perpendicular and pole marker for the family. Pole tracks (`poleX`, `poleY`) reuse the common animation sampler and export path, and worker validation rejects nonfinite coordinates before JSON could turn them into null.

Offsets (`kind: "offset"`) carry a signed `distance`, deliberately separate from the involute's `offset` string length so neither control or animation track can leak into the other. `engine/offset.go` moves each point along the left unit normal. Like the pedal family it needs only a stable first derivative (`derivativeOrder` in `engine/engine.go`), and it keeps cusps where the offset's own speed vanishes. Representative origin/target samples are the normal segments; the `distance` track reuses the common animation sampler and export path. Framing fits base and offset independently, so a short arc with a large offset stays in view. An offset stack (`stack.enabled`) returns its members in `Result.family`, each a `Path` with its distance and base-indexed points with null gaps, and leaves `derived` empty; `Result.circles` carries generating circles (center, radius, and sample index) when `circles` is requested. Both arrays are always present, empty for other constructions. These are the first multiple-path and circle result types; circles are deliberately not `Ray`s. The renderer draws members in the derived colour and circles with the construction lines; reveal slices every member and filters circles by sample index, preserving sample identity. Framing fits each member independently and includes the four extreme points of every circle, whether or not the construction layer is visible, so toggling it never reframes. The `stackFrom`, `stackTo`, and `stackCount` tracks replace `distance` when a stack is enabled; counts round like samples and lines. Animation tracks interpolate as `from·(1−p) + to·p`, which returns each entered endpoint exactly. Roulettes are the first explicit generator: `curve.format: "roulette"` with a `curve.roulette` block (`roll`, `fixedRadius`, `radius`, `arm`, `phase`) replaces the expression parser with `engine/roulette.go`'s closed-form rolling-circle evaluator, so the result is an ordinary base curve and every construction applies unchanged. The expressions and `a` stay in the configuration but are ignored. `Result.roulette` is present only for roulettes (omitted otherwise, like `sourcePosition`): the roll, the fixed radius (0 on a line), closure `turns`/`lobes` computed in Go, and `positions`, one `Rolling` (a `Circle` plus contact and tracing point) per representative sample, recorded even where the construction has a gap. The renderer draws the fixed circle or line and the last position with the construction lines; reveal filters positions by sample index, so the circle rolls along the trace. Framing fits the fixed circle's extremes and the rolling circles' extremes as separate families, so neither is discarded as an outlier of the other; a line is unbounded and is framed only through the rolling circles. The `rollArm`, `rollPhase`, `rollRadius`, and `rollFixed` (not on a line) tracks replace `a`. The rolling construction (`kind: "rolling"`, `engine/rolling.go`) is a construction on any base curve, including a roulette: a `rolling` request block (`side`, `radius`, `arm`, `phase`) and `Result.rolling`, a list of `Rolling` positions at representative samples, always present and empty for other constructions. It shares the involute's Simpson arc length and stop-on-break rule in `Compute`, rolls back out of a cusp instead of stopping (`travel` in `engine/rolling.go` locates each reversal within a sample step by bisection, splits the arc length there, and places the circle with the tangent's reversals undone and a signed arc length), and is first order like the offset. Its rays run from the contact to the tracing point. The renderer draws its last position with the same rolling-circle drawing as a roulette, in a separate group so both can appear together, and reveal and framing treat its positions like a roulette's. The `rollingArm`, `rollingPhase`, and `rollingRadius` tracks join the base curve's own tracks. A rolling curve (`rolling.shape: "curve"`, `engine/rolling_curve.go`) is the same construction with a second curve definition in the `rolling` block (`curve` with `x`, `y`, `min`, `max`, `start`, and a frame `point`); circle fields stay in the configuration but are ignored, and a missing shape means a circle. Go compiles it with the base's parser and `a`, tabulates its Simpson arc length once, and matches each base arc length by interval search and Newton's method. `Result.moving`, present only for a rolling curve, carries the curve's frame path (with gaps), whether it is closed, and a `Placement` (frame origin image, rotation angle, contact, tracing point) per representative sample; `Result.rolling` stays empty. The renderer carries the frame path by the last placement rather than receiving a transformed copy per sample, and framing encloses the path in a circle and frames that circle at every placement. Reveal filters placements by sample. The `rollingPointX`, `rollingPointY`, and `rollingStart` tracks replace the circle's. Line envelopes (`kind: "envelope"`, `engine/envelope.go`) take an `envelope` block (`mode` "angle" or "chord", an `angle` expression, a second endpoint `x`, `y`, and `extend`), compiled with the base's parser, domain, and `a`. They are first order and reuse `Envelope` from the ray construction on the line's unit direction, aligned across the stencil because lines are unoriented. Every defined line is a `Ray` (origin on the base, unit `direction`, `target` or null), even where it touches no finite envelope; a chord's ray adds `end`, and `Result.second`, present only for chords, carries every sample's far endpoint. Unextended chords mark touching points beyond their segments as `virtual`, which the renderer dashes like virtual caustics. The renderer draws chords between their endpoints and unbounded lines clipped to a rectangle well beyond the view, so a wider panel still shows them reaching its edges; the second endpoints are drawn with the base curve. Framing includes the second endpoints but never unbounded lines. Reveal slices `second` like `base`. There are no new numeric fields: the multiplier is `a`, so its existing track animates the multiplication tables. Circle envelopes are the same kind with `envelope.mode: "circle"` and a `radius` expression. They return their two branches in `Result.family`, each `Path` naming its `branch` ("left" or "right", omitted for offset stacks), and leave `derived` empty like a stack. `Result.circles` carries every representative circle with a positive radius, touching its envelope or not, and each touching point adds a `Ray` from the center (origin to target, no direction), drawn as a radius. The renderer labels the branch group separately from an offset stack, and reveal, framing, and collapsed-branch dots reuse the stack's handling. Inversion (`kind: "inversion"`, `engine/inversion.go`) takes an `inversion` request block (`center`, `radius`) and inverts the request's input (below). `inverter` bisects between samples on that input, evaluated at any t. The image is `derived`, as for any construction; each representative sample adds a `Ray` from the input's point to its image. `Result.inversion`, present only for inversions, carries the circle and `breaks`, the samples before which the image is open although both neighbours are finite. Breaks come from bounded bisection between samples, so they follow the mathematical curve rather than the renderer's long-jump heuristic, which remains as a backstop. `pathData` in `web/Plot.tsx` honours them. The renderer draws the dashed circle and segments with the construction lines and a center marker. Framing fits the circle as its own family. The `inversionX`, `inversionY`, and `inversionRadius` tracks lead.

Every construction acts on the request's `input` (`engine/input.go`): `"curve"` (or empty) for the base, or `"evolute"`, `"pedal"`, `"contrapedal"`, `"orthotomic"`, or `"offset"`, reusing those constructions' Go functions with the request's own `pole` and `distance`. It generalizes inversion's former `of` field, which it replaces. `inputCurve` returns a `curveFunc` that evaluates the derived curve at any t from the base evaluator and its stencil derivatives, at a stencil spacing three times the base's (`stencil` in `engine/curve.go` carries a spacing), and `Compute` hands that function to the construction in place of the base: stencils, arc length, directions, chord and circle families, the rolling contact, and inversion's bisection all differentiate or evaluate the input. The base is still sampled for drawing and for generators' own geometry (roulette circles, epicycles, pursuit polygons, trajectories). `derivativeOrder` checks the base at the input's order, `constructionOrder` the input at the construction's, and `validateInput` refuses combinations whose orders sum past three (an evolute feeding the evolute or a caustic); `inputAllowed` in `web/types.ts` mirrors that rule so the interface disables them, and switching to such a tab resets the input to the curve. `Result.input`, present only for a derived input, carries it indexed like `base`; the renderer draws it faintly with the base (`construction-input`), reveal slices it like `base`, framing fits it as its own family, and the pole marker appears for a pedal-family input. Tracks for the input's pole or distance follow the construction's own, unless it has them already. **Construct on**, the last control of the curve section, sets it, showing the input's pole or distance fields when the construction's section does not; a note under the description names the input. Export names include it (`studyName`, for example `tangent-garden-pedal-of-pedal.svg`). Offsets, the involute, and circle envelopes, which are oriented by the tangent, are left open where it reverses within a sample step (`reverses` in `Compute`), with a note; other constructions are unaffected. Composition multiplies evaluations: in WebAssembly at 32,768 samples, a circle rolling on an ellipse's evolute took about 1.6 s here (0.3 s on the ellipse), a catacaustic of its pedal 3.0 s, a vector field's catacaustic of its pedal 6.7 s (1.6 s on the field), and a 16-pursuer chase's catacaustic of its pedal 33 s (5.6 s on the chase), past the client's 30 s calculation limit, which reports a timeout; fewer samples resolve it. Harmonic curves (`engine/harmonic.go`) are two more generators on the roulette pattern: `curve.format: "lissajous"` with a `curve.lissajous` block (`amplitudeX`, `amplitudeY`, `frequencyX`, `frequencyY`, `phase`) and `"fourier"` with `curve.terms`, a list of 1–16 `Term`s (`frequency`, `radius`, `phase`), evaluated in closed form. `Result.harmonic`, present only for these formats, carries the exact `period` computed in Go (0 when the frequencies are not commensurate within bounds), `whole` and `constant` flags, a Lissajous figure's fixed `guides` (as `Circle`s), a Fourier curve's term `radii`, and `positions`, one `Epicycles` (the `joints` where the vectors start or the guide points, and the traced `point`) per representative sample, recorded at construction gaps too. The renderer draws the guides, and the circles, vectors, and projections of the last position, with the construction lines; reveal filters positions like a roulette's. Framing fits the guides and every position's circles as their own families. The UI keys the closure note on the frequencies that move the curve, so it stays while amplitudes and phases recompute. Tracks `lissajousPhase`, `lissajousM`, `lissajousN`, `lissajousA`, `lissajousB`, and, for each Fourier term n, `term<n>Phase`, `term<n>Radius`, `term<n>Frequency` replace `a`; term tracks are named by number, a track for a removed term is dropped, and labels come from `targetLabel`. Adding or removing a term waits for pending field evaluations, since the fields after it are renumbered. Cyclic pursuit (`engine/pursuit.go`) is the first generator integrated rather than evaluated in closed form, and the first with several trajectories: `curve.format: "pursuit"` with `curve.pursuit` (`pursuers`, 2–16 of `x`, `y`, `speed`, and `capture`). Go integrates the chase once per request with adaptive Dormand–Prince steps under a step budget, keeps every accepted state, and evaluates any t by one step from the state before it, so the base curve is the first pursuer's path and constructions differentiate it like any other. `Result.pursuit`, present only for pursuits, carries every pursuer's path indexed like `base` (null outside the chase), `polygons`, one `Polygon` of all positions per representative sample, and why the chase ends: `capture` (time, pursuer, and target, counting from 0) or null, `exhausted`, and `end`, the last time known. These are deliberately separate trajectories, not a `family` of derived paths or `Ray`s. Reveal slices the paths like `base` and filters polygons by sample, so a sample index is a time. The renderer draws every path with the base curve and the polygons and final positions with the construction lines; framing fits each path as its own family. Tracks `pursuer<n>Speed`, `pursuer<n>X`, `pursuer<n>Y`, and `pursuitCapture` replace `a`, and adding or removing a pursuer waits for pending field evaluations like a term.

Vector-field trajectories (`engine/field.go`) are defined by `curve.format: "field"` with `curve.field`:

- `x` and `y`: the expressions for dx/dt and dy/dt;
- `seeds`: 1–16 points, each an `x` and `y`;
- `escape`: the escape radius.

The expression parser (`engine/expr`) has a planar field mode (x, y, t) for them and a spatial one (x, y, z, t, `ParseSpatialField`) for `engine3`. It evaluates without allocating and reports whether an expression reads `t`. Curve expressions keep one variable, `t` (or `x` for a graph), and constant expressions reject `y` and `z` as well.

The pursuit and the trajectories, planar and spatial, share the dimension-free `engine/ode` package, and both pursuits share `engine/cyclic`, which runs a chase of any dimension with its capture policy, step control, and budget. The `engine/ode` package holds:

- the Dormand–Prince step, with stage times;
- a `Solution` of accepted states, evaluated at any t by one step from the state before it, into reused buffers (`Stages`), since a derived input evaluates it hundreds of times per sample.

Step-size control and events stay with each caller, which knows its own error norm and stopping rule.

Go integrates each seed separately, once per request, with its own adaptive steps, step budget, and termination event.

`Result.field` is present only for fields. It carries:

- `paths`: every trajectory, indexed like `base` and null outside it;
- `arrows`: each trajectory's position and velocity at each representative sample;
- `ends`: each trajectory's end time and reason (`end`, `escape`, `singular`, or `exhausted`);
- `timed`: whether the field reads `t`;
- `grid`: a lattice `spacing` and its nonzero finite directions, empty for a timed field.

Reveal slices the paths like `base` and filters arrows by sample. Every trajectory shares the base's sample times, so a revealed prefix is the same span of time on each, whatever steps each took. The renderer draws:

- with the base curve: every trajectory;
- with the construction lines: the chevrons, the seeds, the dashed escape circle, and the grid's arrows, at a fixed fraction of the lattice spacing.

Framing fits each trajectory as its own family and never the escape circle or the grid. Tracks `seed<n>X`, `seed<n>Y`, and `fieldEscape` join `a`, which a field keeps. Adding or removing a seed waits for pending field evaluations.

Implicit curves (`engine/contour.go`) are defined by `curve.format: "implicit"` with `curve.implicit`:

- `f`: the expression F(x, y), parsed in the three-variable mode and rejected if it reads `t`;
- `level`: the level c;
- `family`: `enabled`, `from`, `to`, and `count`, for evenly spaced extra levels;
- `window`: `xMin`, `xMax`, `yMin`, `yMax`;
- `cells`: the grid's cells along the window's longer side.

A level set has no parameter, so `Compute` returns before any construction: `base`, `derived`, and `virtual` are empty, the request's `kind` is ignored, and the domain bounds are not checked. `Result.contours` carries:

- `window`, `columns`, and `rows`: the grid;
- `curve` and `family`: level sets, each a `level` and its `contours`, each a list of `points` and whether it is `closed`;
- `normals`: points on the curve with F's gradient there;
- `discontinuities`: where F changes sign along a grid edge without reaching a level, one per edge;
- `nonfinite`: the number of grid points where F is not finite.

In the UI the construction tabs are disabled and every construction section is hidden while the format is implicit, and the animation targets are the level, window edges, family, grid cells, `a`, and the number of normals; `kind` stays in the configuration for when another format is chosen. The worker checks the implicit fields are finite and the counts whole. Reveal draws each contour along by the same fraction of its points, open until complete, and the normals in order. The renderer draws:

- with the base curve: the curve's contours;
- with the derived curve: the family's contours;
- with the construction lines: the dashed window, the normals as arrows of a fixed fraction of the window, and a cross at each discontinuity.

Framing is the window itself, so the drawing holds still while contours split and join. Export filenames use `implicit` in place of the construction.

Iterated maps (`engine/attractor.go`) are defined by `curve.format: "attractor"` with `curve.attractor`: `map` (`clifford`, `dejong`, or `henon`), coefficients `a`–`d`, `start`, `discard`, `iterates`, `fit`, `window`, and `cells`. Like an implicit curve, `Compute` returns before any construction with empty paths, and `Result.attractor` carries:

- `window`, `columns`, and `rows`: the grid, fitted or given, shaped as for implicit curves;
- `counts`: visits per cell, row-major from the lower-left corner with rows upward, and `max`;
- `accumulated`, `outside`, and `escape`: the iterates counted, those beyond the window, and the number of the iterate that left ±100000, or 0;
- `orbit`: the start and the first `lines` iterates.

A fitted window iterates the accumulated span twice, once to bound it and once to count it, so memory is only the grid (at most 1,024² cells). Budgets are 1,000,000 discarded and 5,000,000 accumulated iterates; the reference study takes about 150 ms in WebAssembly and the largest about 0.7 s.

The browser turns counts into an RGBA image (`web/attractor.ts`: one pixel per cell, top row first, the base colour at opacity `log(1 + n)/log(1 + max)`) and a PNG data URL through a canvas, cached per result and colour. The SVG draws it as an `<image>` over the window with `image-rendering="pixelated"`, so still and animated exports, which rasterize the same SVG at their target size, show the same cells with square edges, and an SVG export carries the density as an embedded PNG. The Content-Security-Policy already allows `data:` images (`img-src 'self' blob: data:`), so no policy change was needed here or in `iwvelando/cloud-accounts`. Reveal cannot cut back a density, so each revealed frame recomputes the first `round(p·N)` iterates in the finished drawing's window with fitting off; live playback and export sample identically. Tracks are the coefficients, start, both counts, the window edges when not fitted, grid cells, and `lines`; `a` is not offered. Export filenames use `attractor`.

## Spatial curve constructions

`engine3` implements torus-knot generators and bounded parametric space-curve expressions with separate `Vec3`, `Curve`, `Request`, `Result`, `Vertex`, and `Ruling` types. Go computes derivatives, singularity guards, ruling endpoints, normals, and mesh topology. Torus derivatives are analytic; custom curves reuse the bounded Go expression parser with endpoint-safe five-point derivative stencils and half-step stability checks. Nullable paths and explicit interval breaks preserve discontinuities. Surface vertices and rulings carry sample indices for reveal playback. Each curve family is framed independently with robust bounds; no planar vector or SVG contract gains dummy coordinates.

The additive `tangentGardenSpatial` WASM entry point is transport only. The worker and `EngineClient.computeSpatial` carry a separate schema mirrored by `web/spatial/types.ts`. The worker rejects nonfinite inputs before serialization, and Go validates geometric/workload bounds. `ScalarInput` retains expressions and applies functional updates. Preset generations invalidate pending evaluations; switching a generated knot to expressions awaits those evaluations. Readiness follows the exact configuration revision. Meshes have at most 28,800 vertices and 240 rulings.

The involute construction (`engine3/involute.go`) reuses the same sampling, derivatives, and interval breaks, then adds a typed `InvoluteResult`: nullable member paths indexed like the base, a collapsed flag, representative strings with sample indices, and an unreached count. It leaves the developable's boundaries, mesh, and rulings empty rather than overloading them, and does not validate the developable's tangent reach. Arc length is accumulated once per request from the anchor on the final grid; reveal truncates it and parameter playback recomputes it. Families are bounded at 24 members and 48,000 points.

Tangent-foot and orthotomic constructions (`engine3/projection.go`) use the independent request `pole: Vec3` and only the base's first derivative. `ProjectionResult` carries the pole marker, nullable `points` and `feet` paths, `collapsed` and image `invalid` diagnostics, and typed `ProjectionConstruction` records (`contact`, `foot`, `image`, `sampleIndex`). These geometric connectors are distinct from rulings, strings, and optical rays. The developable and involute outputs stay empty. Paths share the base's interval breaks; reveal slices both paths and filters constructions by sample. Bounds fit the base, feet, image and pole independently. `poleX`, `poleY`, and `poleZ` tracks update the independent coordinates; tangent reach is neither used nor validated. The renderer adds derived-path, connector/foot, and pole layers and uses the same batches for live and exported drawings.

Sphere inversion (`engine3/inversion.go`) takes `inversion: {center, radius, input}`, with `input` one of `base`, `tangent-foot`, or `orthotomic`. A derived input composes with the pointwise evaluator `project(kind, pole, r, T)` that the projections also use, rather than differentiating a displayed path; composition is limited to that one level, and involutes are not an input. `InversionResult` echoes the center, radius, input, and (for a derived input) the pole, and carries nullable `source` and `points` paths indexed like the base, its own `breaks`, typed `InversionCorrespondence` records (`sampleIndex`, `source`, `image`), a `collapsed` flag, and `invalid` and `crossings` counts. Its `breaks` are the base's plus every interval where the source passes through the center; the renderer draws the image with these, never the base's alone. Other construction outputs stay empty. Bounds fit the base, source, image, and center independently. Tracks `centerX`, `centerY`, `centerZ`, and `sphere` (the radius) join the pole tracks when the input is derived. The renderer adds image, correspondence, sphere (three great circles and a center cross), and source/pole layers.

A construction built on a curve takes the request's top-level `input` (`engine3/composition.go`): `base` (or empty), `tangent-foot`, or `orthotomic`, from the shared `pole`, or `involute`, described by `unwinding: {anchor, offset}`. `Request.composed` is true only for the developable, involute, framed, ruled and canal constructions; the projections, inversion (with its own `inversion.input`) and `none` ignore it, and Compute returns their results unchanged. A derived input replaces `Compute`'s evaluator with `composedEvaluation`, which evaluates `project` pointwise from the base's evaluator and differentiates it with the expression curve's stencils, so every construction, probe and guard runs unchanged on the derived curve, which fills `Base`. `baseSamples` first samples the base by the sampling loop's own rules, and the loop breaks the derived curve wherever the base breaks; the chord (asymptote) guard is not applied to the derived curve itself, which is finite wherever the base is. `Request.analytic` reports that its derivatives are numerical, so the knot's and harmonic curve's closed-form r‴ and r⁗ and their tolerances are not applied to it. `CompositionResult` carries the input and pole, the base's own `curve` and `breaks` (sampled by the same rules), representative `ProjectionConstruction` records from base point to foot to input point, and `cusps`; the base curve and pole join the bounds as their own families. The TypeScript mirror is `SpatialConfig.input` and `SpatialResult.composition` (`takesInput` and `composes` in `web/spatial/types.ts`); the scene draws the base as the `parent` layer in the receding ink, reuses the projections' `connectors` and `pole` layers for its connectors, and the reveal slices the composition with the curve. The link schema carries `config.input`; older links take `base`. Pole tracks follow the construction's own tracks when the input is derived.

The involute input (`engine3/unwinding.go`) replaces the evaluator with `UnwindingRequest.evaluation`, which tabulates arc length outward from the anchor on the sample grid (stopping at base breaks, as the involute construction does), completes it at any t by Gauss–Legendre quadrature, and writes I′ and I″ from the base's own derivatives rather than differencing I. It returns the reached samples; `composition` counts the rest as `unreached`, leaves them out of the cusp runs, records strings (foot equal to contact) as its constructions, and leaves `pole` zero. `Request.projected` distinguishes the projections, whose pole is validated and framed, from the involute, whose pole is ignored. Compute treats a closed base's involute as open. TypeScript: `SpatialConfig.unwinding`, `CompositionResult.unreached`, `projectsInput`/`unwindsInput`/`curveDomain` (`types.ts`); the scene draws strings contact → image with no feet or pole; tracks `inputOffset` and `inputAnchor`; the link schema carries `config.unwinding`, with the preset default for older links, which only the involute input reads. `InversionInput` excludes the involute.

Refining between samples (`engine3/refine.go`) is a request flag, `adaptive`, read only by curves given by a formula (`Request.refines`: a torus knot, harmonic or custom curve). `refinePath` takes a drawn path's uniform samples and breaks and a pointwise evaluator, and returns a `RefinedPath`: the samples, unchanged and at whole positions in `at`, with points bisected in between at fractional positions, nulls at every break, and its `tolerance`, `inserted`, `breaks`, `unresolved` and `exhausted` report. A priority queue bisects the worst piece first, so a budget that runs out leaves the error spread evenly, and the order is deterministic. `Compute` refines the base right after its sampling loop's breaks and before the developable's mesh, so breaks it finds join `Result.Breaks` and every surface built on the curve leaves them open. It refines the composition's base curve, the projection and the inversion image after their own results, the image replacing the midpoint passage test. `Request.position` gives each path's evaluator: a custom curve's expressions are evaluated alone, without the derivative stencils, and a projected input from the base's position and tangent. `Result.adaptive` (`AdaptiveResult`) holds the four optional paths. Nothing else in the result changes: framing, construction lines, probe diagnostics and animation tracks stay on the uniform samples, so a study without the flag is byte-identical. TypeScript: `SpatialConfig.adaptive`, `RefinedPath` and `AdaptiveResult` (`types.ts`); the scene draws a refined path, joined except beside a null, in place of the samples of the `base`, `parent`, `projection` and `inverse` batches, so the WebGL drawing, the line drawing and every export share it; `reveal` keeps each refined path's points up to the last revealed sample by `at`, and leaves the bounds as they were. The link schema carries `config.adaptive`; older links take the first preset's `false`. **Refine between samples** in **Sampling & definition** sets it, for every format but fields, chases, surfaces, mirrors and level sets, and a readout under it totals the report. Measured natively, the worst cases found (every refinable path of a 2400-sample curve exhausting its budget, with numerical derivatives under a derived input) take about 0.14 s; the two presets take under 10 ms.

Spatial harmonic curves (`engine3/harmonic.go`) are a third curve definition, `format: "harmonic"` with `harmonic: {center, terms, min, max}` (1–8 `HarmonicTerm`s of `frequency`, `cosine` A, and `sine` B), evaluated with exact derivatives in `compile`. Closure uses `engine/closure`, a small package shared with the planar harmonic curves and roulettes; `compile` reports the curve closed only when the domain spans whole periods, which makes `Compute` share the seam sample. `HarmonicResult`, present for this format under every construction, echoes the center and terms and carries `period`, `whole`, `closed`, and `positions` (`sampleIndex`, `joints`, `point`) at the representative samples. Framing appends each term's joints and ellipse extents as their own families to whatever the construction fits. Tracks `c0x`, `c0y`, `c0z`, and `harmonic<n>Frequency`, `harmonic<n>Ax`…`harmonic<n>Bz` per term (named by number, dropped when the term is removed), plus `min` and `max`, which move the harmonic domain for this format, join the construction's tracks. Adding or removing a term awaits pending field evaluations. The renderer adds vector-sum and ellipse layers for this format; reveal filters positions by sample and frames them as Go does. `web/spatial/harmonic.ts` holds the closure key and note and the next-term rule.

Framed ribbons (`engine3/frame.go`) take `frame: {kind, reference, angle, twist, offset, width, strands, closure}` under `construction: "framed"`. `frames` runs after the shared sampling pass and uses its tangents, speeds and midpoint speeds (Simpson arc length), and, for the Frenet diagnostic, the developable's binormals and normal-validity flags. It fills the result's `mesh`, `minus`, `plus`, and `rulings` with the ribbon, its edges, and cross-lines, so the developable's surface, rulings, and edges layers draw it, and adds a typed `FrameResult`: `frames` (glyphs with `sampleIndex`, `point`, `tangent`, `normal` U, `binormal` V at the representative samples), nullable `strands` indexed like the base, its own `breaks` (the base's plus Frenet flips), `length`, `pieces`, `undefined`, `flips`, `fallbacks`, `closed`, `holonomy`, `correction`, and an optional `seam` (`point`, `start`, `end`, `angle`). The renderer draws the ribbon edges with `frame.breaks`, never the base's alone. Bounds fit the base, ribbon edges, and each strand independently. Tracks `angle`, `twist`, `width`, `distance` (the strand offset), `strands` (rounded), and, for the transported frame, `normalX`, `normalY`, `normalZ` join the curve's tracks; the tangent reach is neither used nor validated. Reveal slices strands and breaks, filters glyphs, and keeps the seam only once the whole loop is shown. `web/spatial/frame.ts` words the note about the frame, the seam and diagnostics.

Ruled surfaces (`engine3/ruled.go`) take `ruled: {partner, thread, rate, shift}` under `construction: "ruled"`, with `partner` either `chord` or `thread`. Before sampling, `RuledRequest.partner` builds the partner evaluator from the curve's own `compile` evaluation (wrapping on a closed curve) or from the parsed thread (through `sampled`, the stencil evaluator it shares with custom curves). `ruledSurface` runs after the shared sampling pass and uses its tangents and speeds for `a′`. It writes the partner's nullable points to the result's `plus` (leaving `minus` empty) and fills `mesh` and `rulings`, so the developable's surface, rulings, and edges layers draw it. Its mesh is four strips per interval, with vertex normals from `S_t × S_u` and face normals where those vanish. It also adds a typed `RuledResult`: `partner`, its own `breaks` (the base's plus the partner's gaps and jumps, shared with the jump rule `jumps` in `Compute`), `closed`, `gap`, and the counts `outside`, `coincident` and `singular`, with `developable` and `deviation`. The renderer draws the partner with `ruled.breaks`, never the base's alone. Bounds fit the base and the partner independently. Tracks `shift` and `rate` join the curve's tracks, and the tangent reach is neither used nor validated. Reveal slices the partner and the breaks, and `web/spatial/ruled.ts` words the note. The mesh has at most 57,600 vertices.

Canal surfaces (`engine3/canal.go`) take `canal: {radius, profile, meridians}` under `construction: "canal"`, with the angle carried by the request's `frame`. `CanalRequest.frame` forces the rotation-minimizing kind and clears the ribbon and strand fields, so they are neither drawn nor validated. `Compute` runs `frames` with that request, which now returns its carried field (U, V, arc length and the offset direction), and then `canalSurface` builds the contact circles from R and R′, evaluated through `sampled` like a custom curve. It fills `mesh` with normals `q/R` and sets the result's `frame` (glyphs, holonomy and seam for the meridians) and a typed `CanalResult`. That result holds representative `circles` (`sampleIndex`, `real`, `sphere`, `center`, `radius`, closed `points`), nullable `meridians`, its own `breaks`, `constant`, `closed`, `gap`, `steepest`, and the counts `undefined`, `imaginary`, `between`, `collapsed` and `folded`. `minus`, `plus`, and `rulings` are empty. Bounds fit the base, each meridian, and the circle points, the same families reveal fits. The renderer adds contact circle (with grey great circles for spheres without one) and meridian layers, and reuses the surface, frame, and seam layers. Tracks `sphereRadius`, `angle`, `twist`, `meridians` (rounded), and `normalX`–`normalZ` join the curve's tracks. Reveal slices meridians and breaks and filters circles, and `web/spatial/canal.ts` words the note. The mesh has at most 69,120 vertices outside dense gaps.

Curve diagnostics (`engine3/diagnostics.go`) run for any curve format and construction when the request sets `diagnostics: true`; surface, ray and implicit studies ignore it. `diagnose` reads the shared sampling pass's velocities, accelerations and binormal guard (the same `valid` flags the developable and the Frenet frame use) before the construction branches, and a thin `Compute` wrapper clips osculating centres against the finished study radius once, whichever branch returned. r‴ is analytic for knots (`knotJerk`) and harmonic sums (`harmonicJerk`), otherwise `jerk` differences the evaluator's own r″ (`jerkStep`) at two steps and discards disagreements. The typed `DiagnosticsResult` holds nullable per-sample `curvature`, `torsion`, `tangent`, `normal`, `binormal` and `center` series indexed like the base, with `flat`, `unknown` and `clipped` counts. The flag is off by default, so a result without it is byte-identical to one made before diagnostics existed.

Vector fields (`engine3/flow.go`) take `format: "field"` with `field: {x, y, z, seeds, escape, min, max, a}`. `Compute` parses and integrates every seed once, before `compile`, which returns the first trajectory as the base evaluator: position from the dense solution, velocity from the field, and acceleration from a central difference of the field along the flow. Every construction then runs on it unchanged. `fieldGeometry` adds a typed `FieldResult`, present under any construction like `harmonic`. It holds nullable `paths` indexed like `base` (the first is the base), `arrows` at the representative samples (`sampleIndex`, `seed`, `point`, `velocity`), `ends` (`time`, `reason`, nullable `point`, `steps`), `resting`, and `timed`. Bounds fit every path as its own family. `construction: "none"` draws the curve alone under any definition: it leaves `minus`, `plus`, `mesh`, and `rulings` empty and fits the base and those families. A first trajectory with no regular sample is refused under a construction, and alone only when no trajectory moves. The renderer adds the other trajectories (the gradient ink, with no breaks before their end), fixed-length field directions, and crosses at the seeds and at early stops. Tracks `a`, every seed's `seed{k}{X,Y,Z}`, `escape`, `min`, and `max` replace the curve's tracks. Reveal slices every path at the same index and filters arrows. `web/spatial/field.ts` words the note and places a new seed.

Spatial pursuits (`engine3/pursuit.go`) take `format: "pursuit"` with `pursuit: {pursuers: [{x, y, z, speed}], capture, min, max}`. `Compute` runs the chase through `engine/cyclic` before `compile`, which, as for a field, receives the prepared first-path evaluator: position from the dense state, velocity and acceleration from the pursuit law. `pursuitGeometry` adds a typed `PursuitResult`, present under any construction: nullable `paths` indexed like `base`, closed `polygons` at the representative samples (`sampleIndex`, `points`), `capture` (`time`, `pursuer`, `target`, from 0) or null, `exhausted`, `end`, and `final` positions. Bounds fit every path as its own family. The renderer reuses the trajectories layer for the other pursuers and the seeds layer for the starts and, after an early stop, the final positions, and adds a polygons layer. Tracks `pursuer{k}{X,Y,Z,Speed}`, `capture`, `min`, and `max` replace the curve's tracks. Reveal slices the paths, filters polygons, and marks the final positions only once it passes the stop. `web/spatial/pursuit.ts` words the note and places a new pursuer.

Surface studies (`engine3/surface.go`) take `format: "surface"` with `surface: {kind, a, b, c, uMin, uMax, vMin, vMax, uSamples, vSamples, curves, reverse, offset, reach}`. `Compute` hands them to `surfaces` before anything else, so the curve's samples, lines, construction and generator fields are neither read nor validated, and every curve field of the result is empty. A surface is a different evaluator, not a curve with dummy coordinates. `SurfaceRequest.patch` returns X and its exact first and second partial derivatives; `point` gives the normal, principal curvatures and directions, and umbilic flag at one parameter point. The result is a typed `SurfaceResult` of grid sheets (`SurfaceSheet`: nullable `points` and `normals` indexed `[i][j]` by u and v sample, the joined edges `alongU` and `alongV`, and `faces`), so parameter identities survive for reveal and drawing. It holds the `surface`, the `offset` (null at d = 0), and two `focal` sheets that add `shape` and `clipped`. It also holds normal `lines` (`i`, `j`, `point`, `end`), the representative `uCurves` (v indices) and `vCurves` (u indices), and the `singular`, `umbilics` and `folded` counts. Go decides every edge and face (a focal edge through `continues`); the renderer only splits each face into two triangles, shading a corner without a normal by its triangle's own. Reveal (`web/spatial/animation.ts`) grows every sheet along u, keeping the samples up to the current one with the edges, faces and normal lines among them, and `surfaceBounds` frames them as Go does, so a whole reveal matches the still.

Ray studies (`engine3/rays.go`) take `format: "rays"` with the same `surface` request, read as a mirror (`validatePatch` checks the patch, domain and grid, not the offset or normal reach), and `rays: {light, azimuth, elevation, source, length}`. `Compute` hands them to `rays`, which shares the patch evaluator, the grid helpers (`at`, `positions`, `representatives`, `sheet`, `spans`) and the edge rule `continues` with the surface study. `SurfaceRequest.ray` evaluates one reflection with exact derivatives: the lit flag, R, the reflected wavefront's principal curvatures μ₁ ≥ μ₂ and directions, the stigmatic flag, and the twist for tests. The typed `RaysResult` holds the mirror's `surface` sheet, four `caustics` (`CausticSheet`: a grid sheet with `branch`, `virtual` and `shape`, in the order branch 1 real, branch 1 virtual, branch 2 real, branch 2 virtual), representative `lines` (`i`, `j`, `start`, `point`, `end`, `back`, `virtual`), `uCurves`, `vCurves`, the `source` (null for parallel light), and the counts `singular`, `unlit`, `atSource`, `stigmatic` and `clipped` (per branch). Every curve field of the result is empty. The renderer draws the mirror and its parameter curves on the surface layers, each branch's real part on its focal layer, and adds incident rays with the source, reflected rays, and a virtual layer for the extensions of virtual rays and the virtual parts, drawn only as lines. Tracks for the shape, `azimuth` and `elevation` or `sourceX`–`sourceZ`, `rayLength`, the domain and the grid replace the curve's. Reveal grows every sheet along u and filters the rays, and `raysBounds` frames them as Go does. `web/spatial/rays.ts` words the note.

Refraction shares that path: `rays.interaction` is `"reflect"` or `"refract"`, and a refracting request adds `n1` and `n2`. `SurfaceRequest.ray` writes both outgoing directions as `D = aI + bn`, so the derivatives and the caustic eigenproblem are unchanged, and it flags samples beyond the critical angle (`Total`), which `traced()` excludes from caustics, edges and receivers. `RaysResult` adds `total` and each `Ray` a `total` flag, its end along the totally reflected ray. The receiver (`engine3/receiver.go`) is its own request, `rays.receiver: {plane, at, c1, c2, size, bins}` with `plane: "none"` for none, and its own result type, `Receiver` (`plane`, `corners`, `size`, `irradiance[a][b]`, `peak`, and the fluxes `emitted`, `received`, `outside`, `away`, `total`, `edge`), never merged with the caustic sheets. `receive` weights each cell by its midpoint and spreads the flux over its corners' crossing triangles with `raster`, which accumulates exact edge coverage into per-row differences and a running sum, so its work grows with the bins edges cross rather than those covered. The corners fit as their own family, never fenced. The renderer draws the receiver as flat quads whose phase carries the log shade (ink 7, unshaded and without hue) and its window outline, on the **Receiver irradiance** layer; totally reflected rays are grey with the transmitted ones. Reveal withholds the receiver until every column is shown, since it belongs to the whole family. Tracks add `n1`, `n2`, `receiverAt` and `receiverSize`. The largest receiver, a 240 × 60 torus with 240² bins, adds about 14 ms to the study natively and carries about 7.2 MB of JSON in all.

Implicit surfaces (`engine3/implicit.go`) take `format: "implicit"` with `implicit: {f, a, level, box: {xMin, xMax, yMin, yMax, zMin, zMax}, cells, refine, sections: {normal, from, to, count}}`, and every other field is ignored. `F` is parsed by the existing `expr.ParseSpatialField` binding (x, y, z, t and `a`), and a request that reads `t` is refused. `field` samples `F − c` on the box's grid, and `march` meshes each cube's six tetrahedra, solving each crossed edge once through a map from edge (or grid point) to vertex, so the result is an indexed mesh: `ImplicitResult` holds flat `positions`, `normals` and `triangles` arrays, the `cut` and `open` boundary edges as vertex-index pairs, `components` with their Euler characteristics, `sections`, `marks` at discontinuities, and the counts `nonfinite`, `discontinuities`, `ambiguous`, `singular`, `sectionDiscontinuities` and `sectionsSkipped`, with `truncated`. It is a new result type; nothing in it is a curve sample or a surface-patch grid, and it never feeds the curvature or ray studies. Sections reuse the planar engine's contour tracer through `engine.TraceLevel`, which traces and refines one level of a field given as a Go function, with a `ContourBudget` carried from plane to plane; the 2D implicit curve and a spatial section therefore share one implementation. Bounds fit the mesh's vertices, the section points and the box's corners as separate families, so the box frames the study and a level track keeps the camera still. The renderer draws the mesh by index from the engine's shared vertices (`implicitMesh`; a corner without a normal is a copy of its vertex shaded by the face, and without the `OES_element_index_uint` extension the mesh is drawn corner by corner; the phase is decorative, by height), the sections in the base ink, the plane polygons and box in grey, the cut edges in teal, and the open edges and discontinuity crosses in rust, on the **Level surface**, **Section curves**, **Section planes** and **Box, cuts & open edges** layers. Reveal keeps what lies below a height rising through the box, splitting section paths there, without recomputing. Tracks are `level`, `implicitA`, `sectionFrom`, `sectionTo`, `cells` and `sectionCount`; `refine` is not a track. The worker refuses nonfinite box, level, `a` and, with sections, the normal and offsets, fractional cell or plane counts, and fractional refinement levels.

With `refine` above 0, `engine3/adaptive.go` meshes instead of the uniform loop. It still starts from the grid's samples.

- `refiner` holds binary trees of tetrahedra on an integer lattice. A cube gets trees only when one of its tetrahedra is split, or when a split grid edge borders it. An edge-to-leaves map finds the tetrahedra that share an edge, for the closure.
- `adaptive` keeps `F − c` in three places:
  - the grid's own array;
  - an array for the midpoints of grid edges, which are also face and cube centres;
  - a map for finer points.
- It flags and splits generation by generation, then marches each cube: an unrefined cube as the grid's six tetrahedra, and a refined one leaf by leaf.

Vertices are keyed by lattice edge rather than grid index, and both paths share `marchTet`, the triangle construction. The uniform path is unchanged, and meshes every study without refinement bit for bit as before. `field.vertex` keeps its own copy of the vertex and normal steps, because sharing them changed how the compiler fuses their arithmetic, and with it the last bit of some normals. `ImplicitResult.refinement` reports `{levels, reached, bisected, unresolved, exhausted}` in the JSON.

The mesh's five arrays do not go through JSON. `cmd/wasm/mesh.go` copies `positions` and `normals` (float64) and `triangles`, `cut` and `open` (int32) into one `ArrayBuffer` and returns `{ json, positions, normals, triangles, cut, open }`, typed views on that buffer, with `null` for each array in the JSON; every other reply, including an implicit request's error, is JSON alone. The worker puts the views back into the result and transfers the buffer to the page instead of copying it, and `ImplicitResult` types them as `Float64Array` and `Int32Array`. The values are the float64 and int32 numbers Go computed, exactly what JSON's round trip gave. A field added to `ImplicitResult` travels in the JSON unless it is added to the mesh reply on both sides. Transport had been a tenth to a fifth of each frame's time; Go's work is the rest.

**Measuring.** `make bench` (`scripts/bench-implicit.mjs`) times the largest implicit studies through a WASM engine as the worker calls it: the bridge call, decoding, the copy posting to the page would make, and the bytes transferred. `--compare <URL or directory>` times another build's engine, such as the deployed site, beside the local one and prints each study's speedup; it reads either reply shape. `scripts/playback-probe.js`, pasted into the console of any build, times an animation in the page: the interval between drawn frames and the frames drawn per second, each engine's request to reply, the reply to the first draw after it, and how many engines answered. Compare with `make preview`, since the development server's React and worker are slower.

### Where errors are shown

Line weights live in the same descriptor: `Sight.weight`, `lineWeights`, `weightScale`, `strokeUnit`, `inkWeight` (each ink's regular weight; a `Batch` may set its own `weight`), `strokeWidth`, `sheetOffset` and the export record `strokeRecord`, present only for strokes. The renderer draws hairlines with its original program and `gl.LINES`, unchanged. For strokes it links a second program (the same fragment source with `STROKE` defined) that draws each line batch's existing buffer with `ANGLE_instanced_arrays`: six corners per instance at location 0, the segment's ends and phase read from the batch's 7-float vertices at a 56-byte stride, arc lengths from the dash buffer when dashed, and each end's neighbor across its joint from a buffer made by `strokeJoins` when the batch is first stroked (eight attributes, WebGL's minimum). Divisors are reset after each stroke draw, since the other programs share the locations. Strokes two pixels wide or more use alpha to coverage when the canvas is multisampled; thinner and hidden strokes blend with butt ends, their mitred joints neither overlapping nor parting, and thin ones write no depth. With strokes, every sheet is drawn before any line, wide strokes before thin ones. `sheetOffset` sets the sheets' polygon offset from the widest stroke, and `linework` takes `weight` to give each path its `stroke-width` and to sample hiding with the same offset. Without instancing, `strokes()` is false and every weight draws hairlines; the panel says so through `SpatialPlot`'s `onStrokes`, and the canvas's `data-strokes` names the weight only while strokes are drawn. Links made before weights open with `hairline` (`legacyWeight`).

A validation error about one field is a `FieldError` (`engine`, `engine3` and `engine4` each define one) whose `Field` is the request's JSON path (`curve.roulette.radius`, `unwinding.offset`, `lift.center.1`); validators shared between fields, such as the 2D curve compiler, report a path relative to what they validate and their callers prefix it. `cmd/wasm` adds it to the error reply as `field`, the worker forwards it (and tags its own whole-number checks the same way), and `EngineClient` rejects with an `EngineError` carrying it. Each notebook maps the path to the name of the control that edits it: `web/planar-fields.ts` (a field's help topic where it has one, else its label), `web/spatial/fields.ts` (mostly through the animation tracks' labels) and `web/tesseract/fields.ts` (from the object descriptors, with the labels every 4D object shares). The 2D, 3D and 4D apps provide the target through `FieldErrorContext` (`web/Field.tsx`): a `Field` whose control has the failing scalar input's id, or whose label is the engine error's, shows the message under its control with `role="alert"` and `aria-invalid`, opens any closed section around it, scrolls it into view if needed, and claims it before paint, so the notebook's own alert appears only when no field can show it. That alert (`StudyError`) is compact, stands after the study's controls and is brought into view the same way, since the controls can end below the screen or the sidebar's scroll. The animation panels are outside the provider, so their own fields' errors use that alert. Every notebook keeps its previous valid drawing while the study is invalid, marked **Previous valid study** outside the geometry, and asks for a definition only when there is no drawing yet. An error about the study as a whole (no field) goes under the control last changed. The cut and see-through panels receive the target without its label, so a label they share with a study control (**Offset d**, **Normal x**) only ever shows their own inputs' errors. In a `.pair`, the error has its own subgrid row between control and help, so it never moves the neighbouring control.

`engine4/weave.go` evaluates Clifford-torus and Hopf-fiber circles on S³, rotates them in 4D and clips each circle against the stereographic window analytically before sampling. The optional `weave` request and diagnostics extend the existing WASM/worker transport; the worker validates only the active weave fields and ignores spread for a single latitude. Its descriptor supplies the family choice, count fields (`countFields`), latitude key text (`sectionKey`), rotation and latitude motions, readouts and notes. The shared renderer colours paths by latitude through the same section index used by curved sections, without section selection. The tesseract's stereographic clipped-count sentence now comes from its own descriptor, not from a mode check in the component. See [spherical weave contracts](tesseracts.md#spherical-ring-weave).
