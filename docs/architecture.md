# Architecture and extension boundaries

## Current shape

`expression text or roulette, Lissajous, Fourier, or pursuit generator → planar curve evaluator → numerical construction → sampled geometry → SVG`

The `engine` package has no browser, React, filesystem, or network dependency. It can run natively in Go tests or in WASM unchanged. `cmd/wasm` is the only package importing `syscall/js`. The bridge takes one JSON request and returns one JSON result/error; the TypeScript types mirror that schema.

A classic Web Worker loads the matching Go runtime and WASM module. Requests are debounced and numbered; stale responses cannot overwrite newer studies. The UI remains usable during calculations. The initial build uses ordinary Go, not TinyGo, to minimize numerical and runtime compatibility surprises. See [Go's WebAssembly documentation](https://go.dev/wiki/WebAssembly) for the compiler/runtime pairing requirement.

`EngineClient` correlates worker requests and rejects failed/timed-out requests. The worker resolves scalar expressions using the Go `tangentGardenScalars` bridge before calling `tangentGardenCompute`; curve geometry and expression semantics stay in Go. Editor bounds retain their original text, while returned frames carry the resolved numerical configuration. Numeric parameter fields (`ScalarInput`) do the same through `tangentGardenScalars` directly: each keeps its text and applies only the resolved finite value, reporting pending evaluations (which count as busy) and parser errors (named in the alert) to the app. Because resolution is asynchronous, configuration changes are functional updates of the latest state, the source-coordinate conversion awaits pending evaluations, and choosing a preset drops evaluations begun before it. Readiness is tied to the exact input revision so export and playback cannot consume a stale frame during a debounce.

`AnimationPanel` owns a cancellable playback session with immutable original and endpoint frames. Reveal playback slices the precomputed geometry; ray `sampleIndex` values associate construction lines with the same sample grid. Parameter playback interpolates inputs and asks Go for new geometry. It never interpolates output curves across potential singularities. An epoch invalidates in-flight results on stop, pause, or edits; the live loop awaits one frame at a time and derives progress from a monotonic clock. Exact cached endpoints prevent accumulated interpolation error at completion. Discrete counts are rounded; categorical controls remain fixed. Curve parameter `a` is bound as a number by the expression parser, not substituted into expression text.

The plot's automatic animation camera is separate from manual camera state. Holding the current view snapshots the effective center and scale after manual pan/zoom (and the grid span), shared by playback and export. Holding the final view fixes both center and scale; following fixes scale only; fitting uses each current frame. Ray lengths during animation use the final reference span so choosing a camera cannot change the world-space ray lengths. Stopping removes the automatic override and restores the manual view.

Animation export reuses the session sampler and lazily loads `export-animation.tsx`. React's static renderer produces the same `Plot` SVG independently of the live DOM, then an opaque sRGB canvas rasterizes each frame. The rendering loop is independent of format and hands each canvas to a frame sink. For WebP, the browser supplies a still WebP bitstream and `animated-webp.ts` packages full frames according to the [WebP RIFF specification](https://developers.google.com/speed/webp/docs/riff_container), with explicit millisecond durations and a finite or infinite loop count. For MP4, WebCodecs `VideoEncoder` produces H.264 and `mp4-video.ts` writes a video-only ISO/IEC 14496-12 file (`ftyp`, `moov`, `mdat`, index first so playback can start immediately) with a millisecond timescale and each frame's exact duration. The encoder uses Constrained Baseline, which cannot contain B-frames, so decode order is display order and the writer needs no composition offsets; it rejects dropped or reordered output rather than guess. Output is matched to input by timestamp within half a millisecond, the file's timing precision, because WebKit rounds `VideoFrame` timestamps (8,033,000 µs becomes 8,032,999); frame durations always come from the export timing, never from the encoder. The H.264 level is the smallest whose frame-size, macroblock-rate, and bitrate limits fit the export, and the quality slider maps exponentially to bits per pixel. Keyframes fall every two seconds, the encoder backlog is bounded, and each `VideoFrame` is closed once submitted. The encoder's reported colour space is written as an `nclx` box only when every code point is known. `export-formats.ts` detects support before offering a format: canvas WebP by what `toDataURL` actually returns (Safari returns PNG), MP4 by `VideoEncoder.isConfigSupported` for the exact size, frame rate, and bitrate. There is no screen capture, server, or additional codec dependency. Frames are calculated ahead of drawing through `lookahead.ts`, which yields results in frame order with a bounded number in progress, so engine calculation overlaps SVG rasterization and encoding. Parameter-animation exports whose frames need calculation add up to three temporary engine workers (leaving a core free for drawing; at most one on devices whose primary pointer is touch, since each can hold ~100 MB), assigned round-robin; they run the same WASM engine on the same inputs, so frames are identical to a sequential export. The temporary engines exist only for that export and are terminated on completion, cancellation, error, or an input edit; each can hold on the order of 100 MB for expert-scale studies while it runs. Live playback still keeps exactly one calculation in flight. Only compressed frames accumulate, bounded by a frame-count limit and a compressed-size limit. Abort signals and the session epoch suppress stale frames and downloads; a canceled in-flight calculation/encode may finish but its result is discarded. The selected theme/layers are snapshots. Export uses deterministic sample progress rather than real elapsed time, so slow calculations do not shorten or lengthen the saved animation. Browser integration tests independently decode the actual downloaded files to check frames, timing, dimensions, and colors: WebP through Chromium's `ImageDecoder`, MP4 through `ffprobe` (codec, profile, frame count, per-frame times and durations) and a Chromium `<video>` element (duration, endpoints, background colour). The `<video>` check runs on a blank page, because the app's policy has no `media-src` and the app itself never plays media. CI installs ffmpeg; local runs without `ffprobe` skip only those assertions and note it in the report.

Theme preference is a three-state value (system/light/dark). The system mode listens for media-query changes; explicit choices use local storage, with an in-memory fallback when storage is denied. Collapsible sections (Animation, Export settings, the expression and refractive-index references, and numerical notes) remember whether they were left open, under the same fallback rule; Animation and Export settings start collapsed. Field explanations sit behind per-field help toggles rather than hover tooltips, so they work on touch screens. Side-by-side fields (`.pair`) lay out as a CSS subgrid with shared label, control, and help rows: labels align to the bottom of their row, so a wrapped label keeps the controls level, and opening one field's help adds space below both controls without moving either. The sidebar and article have independent scroll containers on desktop, while mobile retains ordinary document scrolling. On mobile the page reads drawing, controls, then the explanation ("Behind the lines", numerical notes, and the closing line), so the interactive controls follow the drawing directly; wide layouts keep the explanation under the drawing in the right column. Because mobile places the controls below the drawing, starting or resuming playback scrolls the drawing into view when it is not fully visible, and the playback controls (buttons, progress, status) dock to the bottom of the screen while an animation is active.

React owns form state and presentation. SVG provides equal x/y scale, and supports inspectable vector export without rasterizing. The exported SVG records its inputs in a description element and includes explicit colors. PNG export (`export-image.ts`) clones the live SVG, sets its intrinsic size to 2000 × 1520, and rasterizes it onto an opaque canvas, so the PNG is drawn from vectors at its final size rather than upscaled from the screen. The SVG uses only inline attributes, so it renders identically outside the page; browser tests compare the PNG with the exported SVG rasterized independently. Curve and optical computations remain in Go; frontend source-coordinate conversions only change the editor representation. Expert counts permit denser drawings, with explicit workload limits and possible responsiveness costs.

Vite generates a static bundle with relative paths. There is no hosting provider integration; the output can be served by an ordinary static host. Dependencies are recorded in `package-lock.json`.

## Adding a 2D construction

1. Define the mathematical convention and independent analytic expectations.
2. Add pure Go geometry and tests. Preserve null gaps and diagnostics.
3. Extend the request/result schema deliberately on both sides of the bridge.
4. Add controls and a verified preset. Keep rendering separate from computation.
5. Run `make check` and `make test-browser`.

## 3D without premature generalization

Keep `Vec` and the current 2D engine honest about their dimension. A future `geometry3` or `engine3` package should define a separate `Vec3`, space curves, parametric surfaces, and meshes. Do not append a dummy z coordinate to the present SVG API.

Reflection/refraction formulas generalize to 3D with a surface normal. Involutes of regular space curves also admit `r−sT`. However, a planar evolute does not transfer as a unique envelope curve of all normals in space, and a two-parameter surface ray family generally forms a caustic surface. Those objects need their own definitions and singularity handling. Projecting rays onto a receiver surface is another operation, with a separate result type.

Reusable boundaries are expression parsing, numerical policies, pure Go geometry, a versioned transport adapter when needed, and worker execution. A later WebGL renderer can coexist with SVG. General implicit curves, piecewise definitions, adaptive sampling, saved studies, and video-format export are prospective features, not claims about the current prototype.

Source coordinate choice is independent of curve format. Optional source `coordinates`, `radius`, and `theta` preserve existing Cartesian requests; polar requests are converted by Go and return `sourcePosition`, which the worker copies into the resolved frame configuration. Animation target availability follows the source coordinate choice, so switching modes invalidates incompatible tracks.

Framing derives robust bounds independently for base, derived, and each offset stack member (plus circle extents, a roulette's fixed and rolling circles, a Lissajous figure's guides and a Fourier curve's circles, each pursuer's path, the rolling construction's circles, and the circle enclosing a rolling curve at each placement), then unions the surviving extrema. Outer Tukey fences reject isolated asymptotic tails without using the base curve as a distance cutoff for derived points. Short prefixes retain both families even with a large involute offset. The policy is explicitly heuristic; manual framing remains the way to examine distant branches.

Export quality controls intrinsic SVG rasterization size (1000 × 760 or 2000 × 1520) and canvas encoder quality (0.95 or 1.0). The shared viewBox and camera do not change. No promise of lossless encoding is made across browsers. Scrubbing keeps the timeline enabled and its thumb under the pointer, calculates at most one frame at a time, and renders only the latest requested position, so a fast drag cannot build a backlog. Completed animation sessions keep the final frame and scrub support but unlock their settings; editing invalidates that preview before preparing a new session.

Brand assets live in `public/tangent-garden.svg`, shared by the header, favicon, and README. Package, Go module, bridge symbols, titles, and download filenames use the Tangent Garden name. The browser theme preference is stored under `tangent-garden.theme`.

Pedal-family constructions (`pedal`, `contrapedal`, `orthotomic`) use an independent `pole` vector in the request/configuration, not the optical `source`. `engine/pedal.go` projects onto a stable first-derivative tangent, permitting zero curvature and C1 curves. Each is a separate `kind` string end to end, so Go dispatch, export filenames, and metadata stay explicit; `usesPole` in `engine/pedal.go` and `web/types.ts` names the family, and the UI groups it behind one tab with a Projection selector. Representative origin/target samples identify the tangent or normal foot; for orthotomics, the target is the reflected point and the renderer recovers the foot as the midpoint of the pole and target, drawing the reflected half dashed. The renderer adds the pole-to-foot perpendicular and pole marker for the family. Pole tracks (`poleX`, `poleY`) reuse the common animation sampler and export path, and worker validation rejects nonfinite coordinates before JSON could turn them into null.

Offsets (`kind: "offset"`) carry a signed `distance`, deliberately separate from the involute's `offset` string length so neither control or animation track can leak into the other. `engine/offset.go` moves each point along the left unit normal. Like the pedal family it needs only a stable first derivative (`derivativeOrder` in `engine/engine.go`), and it keeps cusps where the offset's own speed vanishes. Representative origin/target samples are the normal segments; the `distance` track reuses the common animation sampler and export path. Framing fits base and offset independently, so a short arc with a large offset stays in view. An offset stack (`stack.enabled`) returns its members in `Result.family`, each a `Path` with its distance and base-indexed points with null gaps, and leaves `derived` empty; `Result.circles` carries generating circles (center, radius, and sample index) when `circles` is requested. Both arrays are always present, empty for other constructions. These are the first multiple-path and circle result types; circles are deliberately not `Ray`s. The renderer draws members in the derived colour and circles with the construction lines; reveal slices every member and filters circles by sample index, preserving sample identity. Framing fits each member independently and includes the four extreme points of every circle, whether or not the construction layer is visible, so toggling it never reframes. The `stackFrom`, `stackTo`, and `stackCount` tracks replace `distance` when a stack is enabled; counts round like samples and lines. Animation tracks interpolate as `from·(1−p) + to·p`, which returns each entered endpoint exactly. Roulettes are the first explicit generator: `curve.format: "roulette"` with a `curve.roulette` block (`roll`, `fixedRadius`, `radius`, `arm`, `phase`) replaces the expression parser with `engine/roulette.go`'s closed-form rolling-circle evaluator, so the result is an ordinary base curve and every construction applies unchanged. The expressions and `a` stay in the configuration but are ignored. `Result.roulette` is present only for roulettes (omitted otherwise, like `sourcePosition`): the roll, the fixed radius (0 on a line), closure `turns`/`lobes` computed in Go, and `positions`, one `Rolling` (a `Circle` plus contact and tracing point) per representative sample, recorded even where the construction has a gap. The renderer draws the fixed circle or line and the last position with the construction lines; reveal filters positions by sample index, so the circle rolls along the trace. Framing fits the fixed circle's extremes and the rolling circles' extremes as separate families, so neither is discarded as an outlier of the other; a line is unbounded and is framed only through the rolling circles. The `rollArm`, `rollPhase`, `rollRadius`, and `rollFixed` (not on a line) tracks replace `a`. The rolling construction (`kind: "rolling"`, `engine/rolling.go`) is a construction on any base curve, including a roulette: a `rolling` request block (`side`, `radius`, `arm`, `phase`) and `Result.rolling`, a list of `Rolling` positions at representative samples, always present and empty for other constructions. It shares the involute's Simpson arc length and stop-on-break rule in `Compute`, adds a stop where the tangent reverses within one interval, and is first order like the offset. Its rays run from the contact to the tracing point. The renderer draws its last position with the same rolling-circle drawing as a roulette, in a separate group so both can appear together, and reveal and framing treat its positions like a roulette's. The `rollingArm`, `rollingPhase`, and `rollingRadius` tracks join the base curve's own tracks. A rolling curve (`rolling.shape: "curve"`, `engine/rolling_curve.go`) is the same construction with a second curve definition in the `rolling` block (`curve` with `x`, `y`, `min`, `max`, `start`, and a frame `point`); circle fields stay in the configuration but are ignored, and a missing shape means a circle. Go compiles it with the base's parser and `a`, tabulates its Simpson arc length once, and matches each base arc length by interval search and Newton's method. `Result.moving`, present only for a rolling curve, carries the curve's frame path (with gaps), whether it is closed, and a `Placement` (frame origin image, rotation angle, contact, tracing point) per representative sample; `Result.rolling` stays empty. The renderer carries the frame path by the last placement rather than receiving a transformed copy per sample, and framing encloses the path in a circle and frames that circle at every placement. Reveal filters placements by sample. The `rollingPointX`, `rollingPointY`, and `rollingStart` tracks replace the circle's. Line envelopes (`kind: "envelope"`, `engine/envelope.go`) take an `envelope` block (`mode` "angle" or "chord", an `angle` expression, a second endpoint `x`, `y`, and `extend`), compiled with the base's parser, domain, and `a`. They are first order and reuse `Envelope` from the ray construction on the line's unit direction, aligned across the stencil because lines are unoriented. Every defined line is a `Ray` (origin on the base, unit `direction`, `target` or null), even where it touches no finite envelope; a chord's ray adds `end`, and `Result.second`, present only for chords, carries every sample's far endpoint. Unextended chords mark touching points beyond their segments as `virtual`, which the renderer dashes like virtual caustics. The renderer draws chords between their endpoints and unbounded lines clipped to a rectangle well beyond the view, so a wider panel still shows them reaching its edges; the second endpoints are drawn with the base curve. Framing includes the second endpoints but never unbounded lines. Reveal slices `second` like `base`. There are no new numeric fields: the multiplier is `a`, so its existing track animates the multiplication tables. Circle envelopes are the same kind with `envelope.mode: "circle"` and a `radius` expression. They return their two branches in `Result.family`, each `Path` naming its `branch` ("left" or "right", omitted for offset stacks), and leave `derived` empty like a stack. `Result.circles` carries every representative circle with a positive radius, touching its envelope or not, and each touching point adds a `Ray` from the center (origin to target, no direction), drawn as a radius. The renderer labels the branch group separately from an offset stack, and reveal, framing, and collapsed-branch dots reuse the stack's handling. Inversion (`kind: "inversion"`, `engine/inversion.go`) is the first construction that composes another: an `inversion` request block (`center`, `radius`, and `of`, the curve inverted) selects the base itself or the evolute, pedal family, or offset, reusing their Go functions with the request's own `pole` and `distance`. `inverter` evaluates that curve at any t from the base evaluator and its stencil derivatives, never from the sampled polyline, and `derivativeOrder` applies only the stability checks that curve needs (none for the base). The image is `derived`, as for any construction; each representative sample adds a `Ray` from the inverted curve's point to its image. `Result.inversion`, present only for inversions, carries the circle, the derived curve as `source` (omitted when the base itself is inverted), and `breaks`, the samples before which the image is open although both neighbours are finite. Breaks come from bounded bisection between samples, so they follow the mathematical curve rather than the renderer's long-jump heuristic, which remains as a backstop. `pathData` in `web/Plot.tsx` honours them. The renderer draws the dashed circle and segments with the construction lines, the source curve with the base, and a center marker, plus the pole when a pedal-family curve is inverted. Framing fits the source curve and the circle as their own families, and reveal slices `source` like `base`. The `inversionX`, `inversionY`, and `inversionRadius` tracks lead, followed by the inverted curve's pole or offset distance tracks. Harmonic curves (`engine/harmonic.go`) are two more generators on the roulette pattern: `curve.format: "lissajous"` with a `curve.lissajous` block (`amplitudeX`, `amplitudeY`, `frequencyX`, `frequencyY`, `phase`) and `"fourier"` with `curve.terms`, a list of 1–16 `Term`s (`frequency`, `radius`, `phase`), evaluated in closed form. `Result.harmonic`, present only for these formats, carries the exact `period` computed in Go (0 when the frequencies are not commensurate within bounds), `whole` and `constant` flags, a Lissajous figure's fixed `guides` (as `Circle`s), a Fourier curve's term `radii`, and `positions`, one `Epicycles` (the `joints` where the vectors start or the guide points, and the traced `point`) per representative sample, recorded at construction gaps too. The renderer draws the guides, and the circles, vectors, and projections of the last position, with the construction lines; reveal filters positions like a roulette's. Framing fits the guides and every position's circles as their own families. The UI keys the closure note on the frequencies that move the curve, so it stays while amplitudes and phases recompute. Tracks `lissajousPhase`, `lissajousM`, `lissajousN`, `lissajousA`, `lissajousB`, and, for each Fourier term n, `term<n>Phase`, `term<n>Radius`, `term<n>Frequency` replace `a`; term tracks are named by number, a track for a removed term is dropped, and labels come from `targetLabel`. Adding or removing a term waits for pending field evaluations, since the fields after it are renumbered. Cyclic pursuit (`engine/pursuit.go`) is the first generator integrated rather than evaluated in closed form, and the first with several trajectories: `curve.format: "pursuit"` with `curve.pursuit` (`pursuers`, 2–16 of `x`, `y`, `speed`, and `capture`). Go integrates the chase once per request with adaptive Dormand–Prince steps under a step budget, keeps every accepted state, and evaluates any t by one step from the state before it, so the base curve is the first pursuer's path and constructions differentiate it like any other. `Result.pursuit`, present only for pursuits, carries every pursuer's path indexed like `base` (null outside the chase), `polygons`, one `Polygon` of all positions per representative sample, and why the chase ends: `capture` (time, pursuer, and target, counting from 0) or null, `exhausted`, and `end`, the last time known. These are deliberately separate trajectories, not a `family` of derived paths or `Ray`s. Reveal slices the paths like `base` and filters polygons by sample, so a sample index is a time. The renderer draws every path with the base curve and the polygons and final positions with the construction lines; framing fits each path as its own family. Tracks `pursuer<n>Speed`, `pursuer<n>X`, `pursuer<n>Y`, and `pursuitCapture` replace `a`, and adding or removing a pursuer waits for pending field evaluations like a term. The temporary [expansion roadmap](curve-expansion-roadmap.md) describes later curve families and the staged transition toward explicit generators and multiple-path output.
