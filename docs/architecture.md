# Architecture and extension boundaries

## Current shape

`expression text or roulette, Lissajous, Fourier, pursuit, or vector-field generator → planar curve evaluator → optional derived input (evolute, pedal family, or offset) → numerical construction → sampled geometry → SVG`

An implicit curve takes a separate path: `F(x, y) → grid and marching squares → contours → SVG`, with no construction. So does an iterated map: `map and start → iterates → visit counts in a grid → PNG image embedded in the SVG`.

The `engine` package has no browser, React, filesystem, or network dependency. It can run natively in Go tests or in WASM unchanged. `cmd/wasm` is the only package importing `syscall/js`. The bridge takes one JSON request and returns one JSON result/error; the TypeScript types mirror that schema. The exceptions are the spatial meshes, whose arrays travel typed beside the JSON, and the large numeric arrays of spatial and 4D results, which travel as float64 beside it and are put back where JSON had them (below).

A classic Web Worker loads the matching Go runtime and WASM module. Requests are debounced and numbered; stale responses cannot overwrite newer studies. The UI remains usable during calculations. The initial build uses ordinary Go, not TinyGo, to minimize numerical and runtime compatibility surprises. See [Go's WebAssembly documentation](https://go.dev/wiki/WebAssembly) for the compiler/runtime pairing requirement.

`EngineClient` correlates worker requests and rejects failed/timed-out requests. The worker resolves scalar expressions using the Go `tangentGardenScalars` bridge before calling `tangentGardenCompute`; curve geometry and expression semantics stay in Go. Editor bounds retain their original text, while returned frames carry the resolved numerical configuration. Numeric parameter fields (`ScalarInput`) do the same through `tangentGardenScalars` directly: each keeps its text and applies only the resolved finite value, reporting pending evaluations (which count as busy) and parser errors (named in the alert) to the app. Because resolution is asynchronous, configuration changes are functional updates of the latest state, the source-coordinate conversion awaits pending evaluations, and choosing a preset drops evaluations begun before it. Readiness is tied to the exact input revision so export and playback cannot consume a stale frame during a debounce.

### Reversible journey previews

Every notebook gallery calls `onJourney(journey, restoreFocus, via)`. `useJourneyEntry` in `web/JourneyContext.ts` waits for that notebook's exact current study to settle, including pending scalar evaluations. Invalid drafts and engine errors defer entry with an explanation beside the gallery; their raw text, field errors and editable controls remain mounted. Reopening the gallery or switching notebooks cancels a waiting entry.

`Notebook` in `web/main.tsx` owns the excursion above all three retained notebooks. It never navigates or mounts a target notebook just to preview a step. All previously visited notebooks stay mounted and inert, preserving resolved configurations, raw scalar and bound text, remembered object/definition state, layers, line weights, animation setups, probes, cuts, projections, manual cameras and preset/custom identities. An invalid draft in a dormant notebook is therefore preserved without trying to capture it as link data. Only the originating notebook must settle before entry. Entry invalidates playback and image/motion exports in the retained notebooks; return never resumes them. The 4D notebook also invalidates its custom still-image callback at entry: native PNG encoding may finish later, but neither its file nor its error can surface after cancellation. Theme and palette remain global preferences.

`web/journeys.ts` declares the four authored sequences as `Journey`s of three steps. Each `JourneyStep` names its notebook and existing preset index, short prose, a suggestion and one `JourneyControl`: a numeric configuration field by path (`{ kind: "scalar", label, path }`), labeled as in that study's controls, or the planar probe's point (`{ kind: "probe", label }`). Titles come from the actual preset descriptors. `journeyStudy(step, value?)` uses the target notebook's `presetStudy` and changes only that field or probe position when edited. The 4D object descriptor remains authoritative for capabilities, modes and motion; journey routing adds none.

The experiment uses `ScalarInput` under its own `ScalarStatus` and `FieldErrorContext`, resolving the notebook's constant expressions through the preview worker. An invalid or empty draft stays visible and blocks adoption; the drawing retains the last valid edit. The planar probe moves by sample over the returned diagnostics. Each step keeps its transient edit and raw draft while navigating, and discards them on dismissal. Controls stay mounted in shared sizing cells to preserve drafts and reserve error space.

`JourneyPreview` owns one disposable primary `EngineClient`. Its preparation queue allows one calculation in flight: the requested step/value first, then each remaining example once, nearest first. It retains each example's outcome and each step's latest edited outcome, bounding storage by the journey's step count. Spatial and 4D geometry use the existing typed transport. The dimension renderer loads alongside its first calculation before that outcome is presented; only the presented dimension's plot and player mount. Late calculations or module loads cannot present after dismissal. Only the requested outcome is presented, held as a snapshot so cache eviction cannot remove a completed drawing. Superseded replies stay off screen.

Requesting a step or editing its control stops preview playback. Until the new outcome arrives, the completed artwork and prose stay together. Playback and Open study are inert during a 300 ms grace period, then a longer wait is announced briefly. Computation or WebGL failures are explicit outside the artwork, block adoption and allow return or navigation to a working step. Playback is opt-in: planar and spatial previews reuse their normal animation panels in preview mode, and 4D uses its normal `sample`, loop check, timeline and bounded playback scheduler, with a coalescing `Sampler` for scrubs. Playback sessions dispose their helpers and invalidate pending frames on stop, navigation, edits or dismissal. Previews expose transport controls; the retained notebooks own sharing and export.

The dialog preserves `useQuietFocus` behavior and passes focus between step buttons when one disables itself at an endpoint. Responsive sizing cells reserve authored text and idle playback rows. On phones it fits `window.visualViewport`, reveals recently focused controls by scrolling only the dialog, locks background scrolling and restores the original page scroll on return. Pointer and keyboard return restore the originating gallery trigger with the appropriate focus ring.

`onOpen({ notebook, preset, study, custom }, via)` queues a revisioned adoption for exactly the target notebook. Its normal whole-study operation restores the full study, including the preset's animation, with the one experiment edit if present. A scalar edit makes it a custom study; moving the planar probe keeps the example identity. Other notebooks remain untouched. Cross-notebook adoption uses ordinary notebook navigation and adds one history entry; same-notebook adoption adds none. Preview navigation adds none. A pending lazy target receives only the latest whole-study request: a newer link clears an earlier adoption and adoption clears the target's earlier link. Browser history and incoming links dismiss an excursion. Gallery search, filtering and direct opening retain their ordinary behavior.

### Reversible parameter atlas

`AtlasContext` lets the planar notebook request an atlas from the same `Notebook` owner used by journey excursions. Entry waits for the exact current study and scalar evaluations to settle without errors and for `atlasBudget` to admit its work at 3 × 3. A request that settles after the study changed is checked again, so an unsupported or over-budget result shows the refusal beside the entry instead of opening. Tiered info help lists supported definitions and limits even while entry is disabled. The originating notebook stays mounted and inert, preserving raw scalar text, raw bounds, complete configuration, layers, probe, animation setup, manual camera and preset/custom identity. Entry invalidates playback and still/motion exports through the existing excursion revision. Cancel writes nothing back and never resumes them. Notebook navigation, history, incoming links and replacement studies take precedence over an old excursion.

`web/atlas.ts` owns a curated catalog. Each descriptor declares applicability, two exact request paths, axis labels/symbols and default ranges (preview caps follow the definition, density for an attractor and samples for a curve):

| Pair | Applicability | Columns / rows | Default ranges |
| --- | --- | --- | --- |
| Roulette | A roulette rolling inside/outside a circle or along a line | `curve.roulette.radius` / `curve.roulette.arm` | 0.75–1.25 times each value; zero arm uses 0 to the rolling radius |
| Pedal pole | The construction or its derived input uses a pedal, contrapedal or orthotomic pole; never an implicit curve or density | `pole.x` / `pole.y` | Each coordinate ± the larger of 1 or a quarter of its magnitude |
| Clifford | The active generator is the Clifford map | `curve.attractor.a` / `curve.attractor.b` | Each coefficient ± the larger of 0.25 or a quarter of its magnitude |

Dormant fields never establish support. Several pairs may apply, such as roulette and pole on a roulette's pedal. Pair selection changes no definition, construction or source field. Clifford's coefficients are distinct from the curve's shape parameter `curve.a`; its c, d, start and other settings stay fixed. Subnormal positive roulette defaults widen by one representable step when multiplication would collapse the endpoints. Generated default endpoints use the shortest decimal within one machine epsilon times the largest magnitude of their result and arithmetic operands, removing arithmetic tails such as `0.6499999999999999` while retaining meaningful precision and distinct subnormals. This applies only to arithmetic-generated defaults, never a directly copied source value (such as the zero-arm range's upper radius), the frozen source, user-entered endpoints or raw scalar text. Defaults never clamp an engine-invalid combination into a valid one.

`ParameterAtlas.generate(study, ranges, { pair, size })` clones a complete `PlanarStudy` and creates a row-major 3 × 3 or 5 × 5 matrix, inclusive of exact endpoints. Interior values interpolate with weighted endpoints, avoiding subtraction overflow, and receive rounding-sized cleanup using the endpoint scale. This prevents new arithmetic tails from becoming source values after adoption. A subtraction such as 1.15 − 1 uses the coordinate/half-width scale rather than the small result alone. Only the central midpoint snaps to the frozen value when its difference is at most one machine epsilon times the largest magnitude of that value and either endpoint. Including endpoint rounding preserves symmetric centers near zero, including −0.2 between −1.2 and 0.8; deliberately off-center ranges keep their own midpoint. Each cell is an independent ordinary Go request. `ScalarInput` resolves finite increasing range endpoints through the excursion's own worker; field-specific errors block generation. Individual invalid variants remain visible and unavailable, with ordinary engine reasons outside the artwork. A range edit immediately clears outcomes, before its evaluation finishes; Generate waits for a 300 ms typing pause and all evaluations. Changing pair also drops old scalar evaluations and drafts. Changing size clears affected outcomes; selecting the existing size or pair is a no-op. Grid size is a separate browser preference (`tangent-garden.atlas-size`), validated as 3 or 5 and defaulting to 3. It survives cancellation, adoption, source replacement and reload. One-time storage loading and an in-memory fallback preserve the current choice across excursions when storage is blocked. Initial generation uses that chosen size; it is not reset or silently lowered to satisfy a work limit. When a study fits 3 × 3 but not 5 × 5, the refusal names the 5 × 5 limit and suggests 3 × 3.

Preview settings apply only to cloned numerical requests, never to the frozen source or adoption. Curve previews cap samples/lines at 2,000/128 for 3 × 3 and 1,000/64 for 5 × 5, and turn refinement off. Clifford previews cap accumulated iterates at 50,000, discarded iterates at 1,000 and the density grid's longer side at 128 bins; orbit segments use the same line cap. Smaller requested counts stay smaller. Both preview and original quality are disclosed beside the grid. A preview's attractor need not have the same fine structure as its full-quality result.

One disposable `EngineClient` serves the excursion. At most one numerical request is active, with at most 25 unsent requests including one coalesced priority inspection. Scalars share that worker and wait behind active numerical work. A generation token owns the complete frozen source, pair, size, preview policy and indexed outcome cache: its effective identity is `(generation, cell index, preview/original tier, inspection view)`. No cache is shared across generations or tiers. Range, pair, size, source replacement and cancel release old outcomes and unsent requests; an active obsolete reply is discarded. `inspect(index, view?)` supersedes earlier selections. It always uses original quality, and `candidate()` returns a fresh complete source with only the two selected fields changed. Each delivered frame is cloned into scheduler ownership.

There are at most 25 retained preview results and one full-quality inspection. Curve admission retains the per-study ceiling of 8,000 samples and 256 representative lines. Preflight sums N capped previews and the original-quality inspection: at most 80,000 evaluated uniform samples, 2,560 representative lines, 500,000 retained reserved path points and 80 million weighted work units. A curve's points are `paths × (samples + adaptiveBudget)`, with adaptiveBudget 16,384 when refinement is on for a definition Go refines between samples (not a chase, trajectory, level set or map, where the flag is dormant and its control hidden); paths conservatively counts base, derived, a derived input, and active offset-stack/circle-envelope members, including hidden layers and every trajectory or pursuer path. Representative polygons/arrows and a field’s bounded direction lattice are reserved too. Work adds the integrated generator’s worst-case step budget: eight vector evaluations (speed check plus seven stages) per attempted field step, or seven per chase step, with two coordinates, up to 50,000 steps per trajectory or 40,000 for a chase. Sampling their interpolated states reserves another seven stages and two coordinates per evaluator call. It then multiplies points by 9 for ordinary stencils or 81 for a derived input, 8 for refinement, 16 for integrated involute/rolling constructions and 2 for refinement's reach pass. View-refined inspections reserve two full-quality work/sample/line passes: one to establish the ordinary fit, one refined to the frozen manual camera; the intermediate result is replaced. Density reservations count each grid as at most cells² bins and each fitted density as discard + twice accumulated iterates, with limits of two million retained bins and 20 million evaluated iterations across previews and inspection. The largest supported 5 × 5 Clifford reservation is 1,458,176 bins and 13,525,000 iterations. These conservative counts follow the actual operation and storage paths; they are not timing or heap-size promises. Ordinary Go expression, refinement and integration bounds still apply.

A second limit counts numeric entries in delivered result geometry, including density counts, diagnostics, circles and refinement breaks. A reply exceeding four million entries across the grid and inspection is refused before copying or retaining it. The source, one active reply, worker's ordinary last-result cache and renderer can require transient storage too. Obsolete result references are released rather than kept in an atlas history. Attractor raster caching uses the renderer's existing weak result keys and includes color, so replacing a generation permits collection and changing palette redraws correctly.

An `EngineError` refuses one cell regardless of wording. Any other rejection is a fatal worker failure: drop unsent work and dispose the worker rather than queuing behind timed-out synchronous Go. Failure survives edits, blocks Generate and is shown once; range errors do not duplicate it. Close and reopen to create a fresh worker.

Grid cells use the ordinary `Plot`, current theme, palette, layers and line weight. Independent framing uses `fitFrame` unchanged. `atlasSharedFrame` in `web/atlas-framing.ts` unions the padded rectangles of valid members' ordinary robust fits, then chooses one common center and scalar scale for both axes. Each member's point families are fenced independently before the union: an asymptotic tail cannot erase a coherent distant curve from another member. Invalid members contribute no bounds. Framing changes redraw existing geometry without changing numerical requests or cache identity; pending arrivals use the latest framing. The policy is stated outside artwork. A narrow 5 × 5 grid scrolls horizontally at a minimum width of 640 CSS pixels, preserving readable cells and five columns.

Inspection recomputes at original quality and keeps the frozen manual camera. With zoomed view refinement on a refinable definition it first computes the full-quality fit, then requests its transformed view rectangle; Adopt stays disabled until that second result arrives. This avoids adopting the coarse preview's framing or refinement rectangle. Ordinary diagnostics and a between-sample probe are preserved. The static inspection keeps the animation setup intact. Accessible **Atlas grid** and **Selected variant** tabs retain controls, drafts and grid scroll without recalculating on tab changes. Arrow keys navigate valid cells and tabs; Home/End choose endpoints. `useQuietFocus` governs pointer and keyboard focus. The phone dialog fits the visual viewport and scrolls only its own content above the keyboard. The Parameter pair wrapper owns 16px of trailing padding; its margins and the option fields' margins are zero, preventing doubled 14px margins before Grid size. The range wrapper owns 16px of padding before its first row and after its last row. Atlas-entry help has its own 8px margin, matching ordinary Field help outside the Field styling selector. This keeps first-open portrait spacing independent of subgrid margin relayout.

Only **Adopt variant** queues a revisioned custom planar adoption through the ordinary `openStudy` path. Unchanged controls stay mounted, preserving raw text. Ordinary links, playback and exports use the full-quality candidate. The grid-size preference stays outside the study. Pair, ranges, framing, queue, results and tokens are transient, and none of these atlas values enter a study link. `tests/gallery.spec.ts` covers actual WASM equivalence at declared quality for all pairs/sizes, queue/storage bounds, delayed replies, full-quality density export, view refinement, restoration and responsive artwork. `tests/webkit.spec.ts` covers ranges, grid controls and pointer/keyboard focus.

### Finite planar engravings

A finite engraving is part of the planar study, unlike the atlas. `PlanarStudy.family` (`FamilySettings` in `web/planar-family.ts`) is optional: `{ enabled, target, from, to, count, selected, presentation, allConstruction?, camera?, animation? }`. Links and presets without it, and every link made before it existed, stay ordinary studies. `planarStudy` validates it strictly: count is a whole number from 2 to 32, `selected` names a member, and an enabled family whose target the study does not use is refused as `family.target`. A disabled family keeps its settings, so the source study comes back unchanged when it is turned off and on again. Choosing a preset or opening a link replaces the family with the incoming study's, as it does every other field.

`familyTargets(config)` is the curated applicability descriptor: point-source theta/radius (polar) or x/y (Cartesian) when `availableTargets` offers them; pole x/y when the construction or its derived input uses a pole; and shape `a` only when an expression the study evaluates names it. It refuses implicit curves, iterated maps, vector fields, pursuits, offset stacks and circle envelopes outright. It never changes a definition to make a dormant parameter active. `familyDefaults` opens a track at the study's current value; a theta track opens on a whole turn less one step (see [Finite engravings](mathematics.md#finite-engravings)). Changing the target replaces the range with that target's defaults, so an edited range never carries over to a parameter it was not entered for. **Family from** and **Family to** are `ScalarInput`s resolved by Go. A rejected constant and each setting's refusal (`familyBudget(...).field`) go under their own control through the notebook's `FieldErrorContext`. The aggregate limit names no field and is shown once in the panel.

`familyValues` samples inclusively and exactly (see the mathematics guide). Each member is `applyTracks` on a clone of the complete frozen source with only the selected target set to the member's value, sent through `engine.Compute` at the study's own samples, lines, refinement, view and diagnostics. There is no preview tier. `PlanarFamily` runs on its own disposable `EngineClient`, created when a family turns on and disposed when it turns off or the notebook is left. One request is active at a time; at most 31 member indices wait. A generation token owns the frozen source, settings and member list. Any edit to the configuration, bounds, probe, target, endpoints, count, the refinement view, enabled state or pending scalar evaluation starts a new generation and discards the obsolete reply. Presentation, selection, construction scope, motion settings, layers, weight, palette and the family camera redraw the members already held and never recompute. An `EngineError` makes one member unavailable with its reason. Any other rejection is fatal: the queue is dropped, the worker disposed, and the failure persists until the family is disabled and re-enabled with a fresh worker. A member with no finite derived point is unavailable too.

`familyBudget` refuses before any request: at most 500,000 reserved path points, four million retained numeric entries and 80 million weighted work units across all members. Points are `count × paths × (samples + 16,384 if refined)`, where paths counts base, derived and any derived input. Work multiplies points by 9, or 81 for a derived input, then 8 for refinement, 16 for an involute or rolling construction and 2 for refinement to the view frame. Retained entries reserve 7 per point (16 when refined to the frame), diagnostics at 12 per sample when the probe is on, and each member's representative lines at 40 plus 8 per harmonic term. Delivered geometry is counted again as it arrives (`numericEntries`): a member that would pass four million retained entries across the family is refused and its geometry dropped. Each delivered frame is cloned into scheduler ownership. Only member frames are retained; hidden layers and the selected member are counted once. While a family is on, the ordinary notebook computation is suspended. Its last ordinary frame stays, at most one study's worth, so disabling redraws it while its replacement computes. These counts follow the request and storage paths; they are not timing or heap promises.

`Plot` draws a composition when given `family`: one outer drawing, camera and background, with each member rendered by the ordinary `Plot` into a nested, non-interactive SVG inside its own `<g data-family-member>`. Paths are never joined across members, and each keeps its own gaps. Framing uses `atlasSharedFrame` over the shown members: every member is fitted robustly by `fitFrame`, then the padded rectangles are combined, with one scalar scale for both axes. The complete family draws derived curves, the base once when every member's base, input and refined geometry are equal (otherwise each member's base), and the axes once. Construction and incident-ray layers, backward ray extensions and source/pole markers apply to the fixed selected member by default. The optional saved `family.allConstruction` flag applies the enabled layers to every visible member instead. It defaults to false when absent, preserving older links and preset drawings, and never enables a layer on its own. The signature preset opens with those layers off. During motion, only visible slots draw their construction, under that same scope policy. **Selected member · construction** draws one member exactly as an ordinary study, with its source or pole, rays and derived curve. The legend names the construction drawn. The family camera is `family.camera`, separate from the source study's `camera`, so turning the family off restores the source's manual framing.

Still exports serialize this composition: SVG keeps every member's vectors, PNG rasterizes them at the target size, and a transparent export removes every nested background. The outer `<desc>` records the family settings, each member's id, value and error, and `partial` when any member is unavailable. Copy link and Export image stay disabled until every member has settled and, for the selected presentation, the selected member is valid. When no member is valid, there is nothing to export. While a newer specification computes, such as after a zoom of a family refined to its view, the last settled members stay drawn beneath **Computing…** and export waits, as the ordinary notebook keeps its previous frame. The probe and atlas entry are unavailable while a family is on. Family reveal and moving-window modes use the ordinary `AnimationPanel`, `play`, `ProgressSlider`, timing controls, cancellation and `exportAnimation` pipeline. The ordinary panel remains suspended without rendering controls, preserving its independent unsaved setup. A study opened with a family on keeps its animation setup: the panel receives it only after the family is off and the ordinary frame belongs to that study, so a trace mode is never judged against another frame, and links copied meanwhile record it unchanged. `tests/gallery.spec.ts` covers every member against standalone production requests, each target, reversal, budgets and refusals, scheduler ownership, cancellation, fatal failure and the field errors. `tests/export-equivalence.spec.ts` covers live, PNG and SVG agreement in both presentations under two schemes, and `tests/study-link.spec.ts` covers links. Unchanged controls stay mounted, preserving raw text. Ordinary studies retain their existing playback and export paths.

`family.animation` is optional and conformed independently of the ordinary animation: `{ mode: "reveal" | "window", width, duration, repeat: "once" | "back-and-forth", pace: "steady" | "ease", camera: "hold" | "current" }`. Width is a whole number within the collection; duration is 0.1–3,600 seconds. Absent settings leave older families static and open the motion controls at an eight-second, steady, once-only reveal. The lamp's lace authors an eight-second back-and-forth reveal. Nothing autoplays. A smaller member count clamps the editable window width. Playback position and prepared geometry never enter a link.

`family-motion.ts` owns the pure membership and absolute-time turnaround rules defined in the mathematics guide. `AnimationPanel` captures a `PreparedFamily`: the current owned member array, cloned settings, timing and an effective fixed viewport. It shares those geometry references rather than cloning or retaining a result per animation frame. Hold fits the entire collection once; Current uses `Plot.onViewport`'s effective pan and zoom. `sampleFamily` returns an ordinary `AnimationView` carrying the composition, so the same recursive `Plot` renders live seek, playback, vector stills and movie frames. Reveal starts with member 1 already visible and adds the remaining members at the `n − 1` progress boundaries; moving windows still start with their entire first window. Family frames do not create numerical requests or helper workers. Export lookahead stays bounded and its existing frame/byte limits still apply.

A session's source revision includes the generation, selection, presentation, saved motion, construction scope, ray settings, layers, palette and notebook ownership. Changes cancel playback and abort exports; the drawing also rejects a view whose owner revision is obsolete before effects run. Source generation readiness blocks starts while pending scalar evaluations or replacement members settle. Stop and Back to study restore the static selection and untouched family camera. Completed playback can be explored with its separate animation camera. The normal panel preserves pause/resume, repeated play, bounded seeking and canceled-output disposal for family modes.

### Animation playback and export

`AnimationPanel` owns a cancellable playback session with immutable original and endpoint frames. Reveal playback slices the precomputed geometry; ray `sampleIndex` values associate construction lines with the same sample grid. Parameter playback interpolates inputs and asks Go for new geometry. It never interpolates output curves across potential singularities. An epoch invalidates in-flight results on stop, pause, or edits; the live loop awaits one frame at a time and derives progress from a monotonic clock. Exact cached endpoints prevent accumulated interpolation error at completion. Discrete counts are rounded; categorical controls remain fixed. Curve parameter `a` is bound as a number by the expression parser, not substituted into expression text.

The plot's automatic animation camera is separate from manual camera state. Holding the current view snapshots the effective center and scale after manual pan/zoom (and the grid span), shared by playback and export. Holding the final view fixes both center and scale; following fixes scale only; fitting uses each current frame. Ray lengths during animation use the final reference span so choosing a camera cannot change the world-space ray lengths. Stopping removes the automatic override and restores the manual view.

Animation export reuses the session sampler and lazily loads `export-animation.tsx`. React's static renderer produces the same `Plot` SVG independently of the live DOM, then an opaque sRGB canvas rasterizes each frame. The rendering loop is independent of format and hands each canvas to a frame sink. For WebP, the browser supplies a still WebP bitstream and `animated-webp.ts` packages full frames according to the [WebP RIFF specification](https://developers.google.com/speed/webp/docs/riff_container), with explicit millisecond durations and a finite or infinite loop count. For MP4, WebCodecs `VideoEncoder` produces H.264 and `mp4-video.ts` writes a video-only ISO/IEC 14496-12 file (`ftyp`, `moov`, `mdat`, index first so playback can start immediately) with a millisecond timescale and each frame's exact duration. The encoder uses Constrained Baseline, which cannot contain B-frames, so decode order is display order and the writer needs no composition offsets; it rejects dropped or reordered output rather than guess. Output is matched to input by timestamp within half a millisecond, the file's timing precision, because WebKit rounds `VideoFrame` timestamps (8,033,000 µs becomes 8,032,999); frame durations always come from the export timing, never from the encoder. The H.264 level is the smallest whose frame-size, macroblock-rate, and bitrate limits fit the export, and the quality slider maps exponentially to bits per pixel. Keyframes fall every two seconds, the encoder backlog is bounded, and each `VideoFrame` is closed once submitted. The encoder's reported color space is written as an `nclx` box only when every code point is known. `export-formats.ts` detects support before offering a format: canvas WebP by what `toDataURL` actually returns (Safari returns PNG), MP4 by `VideoEncoder.isConfigSupported` for the exact size, frame rate, and bitrate. There is no screen capture, server, or additional codec dependency. Frames are calculated ahead of drawing through `lookahead.ts`, which yields results in frame order with a bounded number in progress, so engine calculation overlaps SVG rasterization and encoding. Parameter-animation exports whose frames need calculation add up to three temporary engine workers (leaving a core free for drawing; at most one on devices whose primary pointer is touch, since each can hold ~100 MB), assigned round-robin; they run the same WASM engine on the same inputs, so frames are identical to a sequential export. The temporary engines exist only for that export and are terminated on completion, cancellation, error, or an input edit; each can hold on the order of 100 MB for expert-scale studies while it runs. Live playback keeps at most one calculation in flight per engine (`playback.ts`). Parameter playback in every notebook adds one helper engine where an export could (`playbackEngineCount`): it prepares the final endpoint while the app's engine prepares the first, then the two alternate, each request spaced by the measured round trip divided between them, so one calculates while the other's frame is drawn. A reply older than the frame on screen is dropped, so progress only rises. The helper exists only while playing; pause, stop, completion, an edit or failure terminate it, and scrubbing and export keep a single engine. Only compressed frames accumulate, bounded by a frame-count limit and a compressed-size limit. Abort signals and the session epoch suppress stale frames and downloads; a canceled in-flight calculation/encode may finish but its result is discarded. The selected theme/layers are snapshots. Export uses deterministic sample progress rather than real elapsed time, so slow calculations do not shorten or lengthen the saved animation. Browser integration tests independently decode the actual downloaded files to check frames, timing, dimensions, and colors: WebP through Chromium's `ImageDecoder`, MP4 through `ffprobe` (codec, profile, frame count, per-frame times and durations) and a Chromium `<video>` element (duration, endpoints, background color). The `<video>` check runs on a blank page, because the app's policy has no `media-src` and the app itself never plays media. CI installs ffmpeg; local runs without `ffprobe` skip only those assertions and note it in the report.

### Planar animation phrases

`PlanarAnimation.phrase` is an optional bounded `Phrase` (`web/phrase.ts`), with one consumed continuous target, an opening base/construction/derived reveal triple, and 1–12 labeled phases. Each phase has a finite duration of at least 0.1 seconds, a steady/eased pace, an optional scalar-expression endpoint, optional discrete layer events, optional reveal endpoints, and an optional camera `view`: a key view `{ x, y, zoom }` (zoom 0.1–1,000, as a planar camera path's) or `"entry"`. Total duration is at most 3,600 seconds. Counts, categorical choices and iterated-map densities are unavailable; ray length keys keep the ordinary animation range, 0.01–100. The UI edits durations and the offered keys; it does not rearrange the timeline. A target change resets explicit keys to that target's current study value. Missing phrase settings leave the existing animation modes and links unchanged.

`compilePhrase(config, layers, length, phrase, keys, camera?)` consumes Go-resolved scalar keys and compiles complete boundary states from the immutable entry study, carrying omitted values forward. `camera` is `{ fit, entry }`: the reference fit taken once from the opening study and the entry view (that fit, or `Plot.onViewport`'s effective manual view). Only a phrase with at least one phase view compiles boundary views, so phrases without them keep exactly the R04.1 held camera. `phraseAt(compiled, seconds)` takes absolute phrase seconds and returns configuration/ray length, phase label, visibility, independent reveal fractions and, for a flown phrase, the sampled `view`. One phase locator gives inputs, reveal and camera the same phase and eased progress. Each phase's camera is a two-view steady `planarPathView` leg about the reference fit; boundaries and holds return their stored viewports. It is independent of the numerical worker and request history. [Mathematics](mathematics.md#planar-animation-phrases) defines interpolation, the reference frame and exact boundary ownership. `phraseViewError(phrase, zoomLimit)` refuses a key beyond the drawing's limit (20×, or 1,000× refined to its view) before Play, under that phase's Camera control.

`createPhraseSampler({ phrase, original, view, stop, focus?, probe?, refine?, plain?, rect? })` returns an asynchronous `(seconds, engine) => AnimationView` renderer-input sampler. Playback, seek, loop checks and export all call it; still export captures its live `Plot`. Without phase views the view is frozen once from the entry fit or the effective current pan/zoom, and current-view refinement uses that same fixed rectangle for every numerical request. A flown phrase returns each frame's sampled view as its `heldView`. When the study is refined to its view (`refine`), a zoomed frame is refined to `rect(view)` while the input moves, or to its camera-only phase's `flightPieces` area, cut lazily per phase and bounded by the phase count. `plain`, computed once at start when the entry was refined to a manual view, is drawn at the opening value and fitted zoom or wider. A session's private cache has one latest geometry or pending promise per engine, keyed by the numerical input value and refinement rectangle; the immutable original is reused at its own value, and a ray-length-only change reuses it too. Session-local fixed configuration, focus and reference camera form the rest of that cache's identity. Preflight validates each explicit key at its own end view's refinement.

`revealPhrase` selects the original ordered points and representative geometry independently for base, construction and derived roles, retaining gaps, sample indices and virtual flags. Zero reveals are empty; a fully revealed result is reused directly. Holds preserve equal input endpoints exactly and reuse geometry without another numerical request. No frame cache grows with duration. Playback retains the existing one-request-per-engine scheduling; export retains bounded lookahead, worker count, frame count and compressed output limits.

`AnimationPanel` validates keys through Go, retains invalid drafts, and blocks play, export and link copying until the current draft is valid. Preparation checks explicit numerical endpoints without retaining a phase-sized geometry collection. Its epoch and export abort controller discard obsolete preparation, frames and files on stop, pause, edits or replacement. Editing a phrase's entry layers also cancels its frozen presentation. The `AnimationView.phrase` presentation reaches both the live and static `Plot` renderer, including export metadata, and the surrounding legend uses those effective layers. `AnimationView.phrase` also carries the target and sampled value, formatted once by `PhraseCaption.tsx` for an ordinary, non-announcing caption directly below the viewport. Desktop and mobile use that same stage/counter layout; the playback dock does not duplicate it. `PlanarAnimation.phraseLabelInDrawing` is optional and defaults off for older links and presets. With it on, the same caption moves into Plot’s SVG with bounded wrapping, regular 22-unit type in the theme’s muted caption ink and a thin contrast halo, so SVG/PNG and motion exports include it. An accessible UI copy remains when its visual presentation moves inside. Placement changes preserve the last displayed frame, time and camera and update subsequent samples without numerical work; changes during preparation or export cancel obsolete work/output. Once, back and forth and loop are available. `loops` admits phrases, and `planarLoopGap` renders both ends through the same sampler, so a loop is refused unless value, layers, reveal, camera and caption all return; the authored phrases' reveals do not.

### Study presentation and links

Theme preference is a three-state value (system/light/dark). The system mode listens for media-query changes; explicit choices use local storage, with an in-memory fallback when storage is denied. Collapsible sections (Animation, Export settings, the expression and refractive-index references, and numerical notes) remember whether they were left open, under the same fallback rule; Animation and Export settings start collapsed. Field explanations sit behind per-field help toggles rather than hover tooltips, so they work on touch screens. Side-by-side fields (`.pair`) lay out as a CSS subgrid with shared label, control, and help rows: labels align to the bottom of their row, so a wrapped label keeps the controls level, and opening one field's help adds space below both controls without moving either. The sidebar and article have independent scroll containers on desktop, while mobile retains ordinary document scrolling. On mobile the page reads drawing, controls, then the explanation ("Behind the lines", or "Behind the folds" in 3D, numerical notes, and the closing line), so the interactive controls follow the drawing directly; wide layouts keep the explanation under the drawing in the right column. Because mobile places the controls below the drawing, playback jumps the drawing into view when it is not fully visible, once its first frame is shown or it resumes (instantly rather than smoothly, so no opening frames are missed; both notebooks share `web/revealDrawing.ts`). A start that is refused leaves the page where it is, so its error appears beside Play, and the playback controls (buttons, progress, status) dock to the bottom of the screen while an animation is active.

Study links (`web/study-link.ts`) carry a notebook's study in the URL fragment as base64url of raw-deflated JSON: v1 carries `{ v: 1, notebook, study }`, and v2 carries `{ v: 2, notebook, delta }` against one frozen literal snapshot per notebook. Copy link compresses both eligible candidates, chooses the shorter token (v1 on ties), and snapshots before awaiting compression. Decoding v2 restores the complete raw study from `web/study-link-baselines-v2.ts` before notebook validation; published snapshots and patch semantics require a new version to change. Links use the browser's `CompressionStream`, with no server and no new resource category. The envelope is read before any notebook loads. `Notebook` in `main.tsx` then hands the unchecked study to its notebook, which conforms it with its own link module (`planar-link.ts`, `spatial/link.ts`, `tesseract/link.ts`). Each module's schema is typed `SchemaOf<T>` against the notebook's configuration type, so adding a field without deciding how links validate it fails `tsc`. The schema bounds text length and list sizes, closes every option set, and requires exact tuple lengths. It also refuses unknown fields, naming each one, and fills fields a link predates from the notebook's defaults; the 4D module uses the object descriptor's defaults. Animation tracks must name targets the linked study offers. Go still validates every numerical limit as for typed input. A notebook applies a link through the same replacement path as a preset. It advances the scalar generation, then restores its layers and passes the manual camera to the plot for that reset. The animation setup goes to the panel only once the frame belongs to the linked study, so the panel's target filter cannot drop the linked tracks. The encoded fragment is bounded at 32 KB, its inflated JSON and reconstructed v2 study each at 256 KB. v2 checks prototype keys and literal subtrees before restoration, with depth 32 and 16,384-node budgets on both the patch and restored tree, and charges output bytes during construction. Arrays replace in full; null deletes an object member. See [portable study links](permalinks.md) for baseline versioning, exact patch semantics and measured token lengths.

React owns form state and presentation. SVG provides equal x/y scale, and supports inspectable vector export without rasterizing. The exported SVG records its inputs in a description element and includes explicit colors. PNG export (`export-image.ts`) clones the live SVG, sets its intrinsic size to the chosen still size (2000 × 1520 by default), and rasterizes it onto an opaque canvas, or one with alpha when the background is left out of the clone, so the PNG is drawn from vectors at its final size rather than upscaled from the screen. The size and background are settings of the shared `ExportImageMenu`, as multiples of each notebook's page; the 3D notebook draws its transparent stills over black and white and recovers alpha with `matte.ts` (see [mathematics](mathematics.md#still-exports-size-and-transparent-background)). The SVG uses only inline attributes, so it renders identically outside the page; browser tests compare the PNG with the exported SVG rasterized independently. Curve and optical computations remain in Go; frontend source-coordinate conversions only change the editor representation. Sample and line counts up to 32,768 and 2,048 permit dense drawings, with explicit workload limits and possible responsiveness costs.

Refinements first built for the 3D notebook are shared where they apply to the 2D and 4D notebooks, rather than copied. Live playback in every notebook runs on `web/playback.ts`'s `play()`, which spaces requests across one or two engines ("lanes") and drops replies older than the frame on screen. It asks for at most 30 frames a second, or 60 for animations whose frames come without calculating (each notebook's `redraws`: a reveal, trace, orbit, cut or flight, or the probe at its samples), falling back to an even 30 while those frames come late and trying 60 again after a hold that doubles with each fall; the 2D and 4D notebooks add a helper engine only while calculated frames play, and the 2D helper prepares the end beside the start. Line weights (`web/line-weight.ts`, the control `LineWeightField`) hold the choices, scale, link schema and help; the 3D renderer draws them as WebGL strokes and the 2D and 4D drawings through `svgStroke`, which leaves a regular stroke's width untouched so existing drawings are byte-identical. Refinement between samples is one Go package, `engine/refine`, generic over the point type: `engine3` and `engine` each supply a distance from a point to a chord and adapt its result to their JSON (`RefinedPath`), and `web/refinement.ts` and `RefineBetweenSamples` give both notebooks the reveal cut, readout and control. The 3D and 4D turntables share named views and the orientation indicator: `web/named-views.ts` is their descriptor (labels, help, yaw and pitch, `turnTo`, `turntableBasis`) and `web/Orientation.tsx` draws both under the drawing's frame. The 4D app turns its shadow's `view` state; the 3D camera lives in `SpatialPlot`, which applies a `turn` prop to the shown camera and reports each drawn view, whose rows `scene.ts`'s `viewBasis` reads from `camera`, through an `OrientationFeed` to `LiveOrientation`, so orbiting re-renders only the indicator. The axis inks live in `palette.ts` as `axisInks`. Every legend renders through `web/Legend.tsx`'s `LegendEntries`: each entry is tied to the layer that draws it and is shown only while that layer is on and the drawn study has its geometry; hidden entries keep their place, invisible and `aria-hidden`, after the shown ones, so the legend never reflows. The 2D notebook asks `legendGeometry` in `Plot.tsx`; the 3D notebook lists each study's entries in `web/spatial/legend.ts` and learns what the uploaded scene can draw from `sceneLayers` in `scene.ts`, which the renderer reports through `SpatialPlot`'s `onGeometry`; the 4D notebook matches each descriptor `legendItems` entry's ink family (and roles, where inks are shared) against `drawnInks` in `Drawing.tsx`, which shares the drawing's own layer filter. The parameter probe's notebook-independent parts (`web/probe.ts`: the sample index, plot scale, inks and how a curve probe holds its place while parameters vary; `ProbePlot`) serve the 3D `ProbePanel` and the 2D `PlanarProbePanel`; the 2D diagnostics come from `engine/diagnostics.go`, asked by the worker's `diagnostics` flag, and the plot draws the probe at the sample the live probe or the animation view gives it.

Vite generates a static bundle with relative paths. There is no hosting provider integration; the output can be served by an ordinary static host. Dependencies are recorded in `package-lock.json`.

## Adding a 2D construction

1. Define the mathematical convention and independent analytic expectations.
2. Add pure Go geometry and tests. Preserve null gaps and diagnostics.
3. Extend the request/result schema deliberately on both sides of the bridge.
4. Add controls and a verified preset. Keep rendering separate from computation.
5. Run `make thumbnails` so the example gallery can show the new or changed preset.
6. Run `make check` and `make test-browser`.

## 3D without premature generalization

Keep `Vec` and the current 2D engine honest about their dimension. A future `geometry3` or `engine3` package should define a separate `Vec3`, space curves, parametric surfaces, and meshes. Do not append a dummy z coordinate to the present SVG API.

Reflection/refraction formulas generalize to 3D with a surface normal. Involutes of regular space curves also admit `r−sT`. However, a planar evolute does not transfer as a unique envelope curve of all normals in space, and a two-parameter surface ray family generally forms a caustic surface. Those objects need their own definitions and singularity handling. Projecting rays onto a receiver surface is another operation, with a separate result type.

Reusable boundaries are expression parsing, numerical policies, pure Go geometry, a versioned transport adapter when needed, and worker execution. WebGL coexists with SVG through separate rendering contracts. Piecewise definitions, adaptive sampling, and saved studies remain prospective features.

Source coordinate choice is independent of curve format. Optional source `coordinates`, `radius`, and `theta` preserve existing Cartesian requests; polar requests are converted by Go and return `sourcePosition`, which the worker copies into the resolved frame configuration. Animation target availability follows the source coordinate choice, so switching modes invalidates incompatible tracks.

Framing derives robust bounds independently for base, derived, and each offset stack member (plus circle extents, a roulette's fixed and rolling circles, a Lissajous figure's guides and a Fourier curve's circles, each pursuer's path and each vector-field trajectory, the rolling construction's circles, and the circle enclosing a rolling curve at each placement), then unions the surviving extrema. Outer Tukey fences reject isolated asymptotic tails without using the base curve as a distance cutoff for derived points. Fences and frame are measured in each family's own size, never in fixed world units, so a study at any scale or position is framed alike (see [Scale and translation](mathematics.md#scale-and-translation)). Short prefixes retain both families even with a large involute offset. The policy is explicitly heuristic; manual framing remains the way to examine distant branches. A study that frames its points between samples (`adaptiveFrame`) adds each refined curve's `reach` to its family within the samples' fence; Go computes it from the study's own refinement, never the view's (see [Refinement between samples](mathematics.md#refinement-between-samples)).

Export quality controls intrinsic SVG rasterization size (1000 × 760 or 2000 × 1520) and canvas encoder quality (0.95 or 1.0). The shared viewBox and camera do not change. No promise of lossless encoding is made across browsers. Scrubbing keeps the timeline enabled and its thumb under the pointer, calculates at most one frame at a time, and renders only the latest requested position, so a fast drag cannot build a backlog. Completed animation sessions keep the final frame and scrub support but unlock their settings; editing invalidates that preview before preparing a new session.

Brand assets live in `public/tangent-garden.svg`, shared by the header, favicon, and README. Package, Go module, bridge symbols, titles, and download filenames use the Tangent Garden name. The browser theme preference is stored under `tangent-garden.theme`.

Pedal-family constructions (`pedal`, `contrapedal`, `orthotomic`) use an independent `pole` vector in the request/configuration, not the optical `source`. `engine/pedal.go` projects onto a stable first-derivative tangent, permitting zero curvature and C1 curves. Each is a separate `kind` string end to end, so Go dispatch, export filenames, and metadata stay explicit; `usesPole` in `engine/pedal.go` and `web/types.ts` names the family, and the UI groups it behind one tab with a Projection selector. Representative origin/target samples identify the tangent or normal foot; for orthotomics, the target is the reflected point and the renderer recovers the foot as the midpoint of the pole and target, drawing the reflected half dashed. The renderer adds the pole-to-foot perpendicular and pole marker for the family. Pole tracks (`poleX`, `poleY`) reuse the common animation sampler and export path, and worker validation rejects nonfinite coordinates before JSON could turn them into null.

Offsets (`kind: "offset"`) carry a signed `distance`, deliberately separate from the involute's `offset` string length so neither control or animation track can leak into the other. `engine/offset.go` moves each point along the left unit normal. Like the pedal family it needs only a stable first derivative (`derivativeOrder` in `engine/engine.go`), and it keeps cusps where the offset's own speed vanishes. Representative origin/target samples are the normal segments; the `distance` track reuses the common animation sampler and export path. Framing fits base and offset independently, so a short arc with a large offset stays in view. An offset stack (`stack.enabled`) returns its members in `Result.family`, each a `Path` with its distance and base-indexed points with null gaps, and leaves `derived` empty; `Result.circles` carries generating circles (center, radius, and sample index) when `circles` is requested. Both arrays are always present, empty for other constructions. These are the first multiple-path and circle result types; circles are deliberately not `Ray`s. The renderer draws members in the derived color and circles with the construction lines; reveal slices every member and filters circles by sample index, preserving sample identity. Framing fits each member independently and includes the four extreme points of every circle, whether or not the construction layer is visible, so toggling it never reframes. The `stackFrom`, `stackTo`, and `stackCount` tracks replace `distance` when a stack is enabled; counts round like samples and lines. Animation tracks interpolate as `from·(1−p) + to·p`, which returns each entered endpoint exactly. Roulettes are the first explicit generator: `curve.format: "roulette"` with a `curve.roulette` block (`roll`, `fixedRadius`, `radius`, `arm`, `phase`) replaces the expression parser with `engine/roulette.go`'s closed-form rolling-circle evaluator, so the result is an ordinary base curve and every construction applies unchanged. The expressions and `a` stay in the configuration but are ignored. `Result.roulette` is present only for roulettes (omitted otherwise, like `sourcePosition`): the roll, the fixed radius (0 on a line), closure `turns`/`lobes` computed in Go, and `positions`, one `Rolling` (a `Circle` plus contact and tracing point) per representative sample, recorded even where the construction has a gap. The renderer draws the fixed circle or line and the last position with the construction lines; reveal filters positions by sample index, so the circle rolls along the trace. Framing fits the fixed circle's extremes and the rolling circles' extremes as separate families, so neither is discarded as an outlier of the other; a line is unbounded and is framed only through the rolling circles. The `rollArm`, `rollPhase`, `rollRadius`, and `rollFixed` (not on a line) tracks replace `a`. The rolling construction (`kind: "rolling"`, `engine/rolling.go`) is a construction on any base curve, including a roulette: a `rolling` request block (`side`, `radius`, `arm`, `phase`) and `Result.rolling`, a list of `Rolling` positions at representative samples, always present and empty for other constructions. It shares the involute's Simpson arc length and stop-on-break rule in `Compute`, rolls back out of a cusp instead of stopping (`travel` in `engine/rolling.go` locates each reversal within a sample step by bisection, splits the arc length there, and places the circle with the tangent's reversals undone and a signed arc length), and is first order like the offset. Its rays run from the contact to the tracing point. The renderer draws its last position with the same rolling-circle drawing as a roulette, in a separate group so both can appear together, and reveal and framing treat its positions like a roulette's. The `rollingArm`, `rollingPhase`, and `rollingRadius` tracks join the base curve's own tracks. A rolling curve (`rolling.shape: "curve"`, `engine/rolling_curve.go`) is the same construction with a second curve definition in the `rolling` block (`curve` with `x`, `y`, `min`, `max`, `start`, and a frame `point`); circle fields stay in the configuration but are ignored, and a missing shape means a circle. Go compiles it with the base's parser and `a`, tabulates its Simpson arc length once, and matches each base arc length by interval search and Newton's method. `Result.moving`, present only for a rolling curve, carries the curve's frame path (with gaps), whether it is closed, and a `Placement` (frame origin image, rotation angle, contact, tracing point) per representative sample; `Result.rolling` stays empty. The renderer carries the frame path by the last placement rather than receiving a transformed copy per sample, and framing encloses the path in a circle and frames that circle at every placement. Reveal filters placements by sample. The `rollingPointX`, `rollingPointY`, and `rollingStart` tracks replace the circle's. Line envelopes (`kind: "envelope"`, `engine/envelope.go`) take an `envelope` block (`mode` "angle" or "chord", an `angle` expression, a second endpoint `x`, `y`, and `extend`), compiled with the base's parser, domain, and `a`. They are first order and reuse `Envelope` from the ray construction on the line's unit direction, aligned across the stencil because lines are unoriented. Every defined line is a `Ray` (origin on the base, unit `direction`, `target` or null), even where it touches no finite envelope; a chord's ray adds `end`, and `Result.second`, present only for chords, carries every sample's far endpoint. Unextended chords mark touching points beyond their segments as `virtual`, which the renderer dashes like virtual caustics. The renderer draws chords between their endpoints and unbounded lines clipped to a rectangle well beyond the view, so a wider panel still shows them reaching its edges; the second endpoints are drawn with the base curve. Framing includes the second endpoints but never unbounded lines. Reveal slices `second` like `base`. There are no new numeric fields: the multiplier is `a`, so its existing track animates the multiplication tables. Circle envelopes are the same kind with `envelope.mode: "circle"` and a `radius` expression. They return their two branches in `Result.family`, each `Path` naming its `branch` ("left" or "right", omitted for offset stacks), and leave `derived` empty like a stack. `Result.circles` carries every representative circle with a positive radius, touching its envelope or not, and each touching point adds a `Ray` from the center (origin to target, no direction), drawn as a radius. The renderer labels the branch group separately from an offset stack, and reveal, framing, and collapsed-branch dots reuse the stack's handling. Inversion (`kind: "inversion"`, `engine/inversion.go`) takes an `inversion` request block (`center`, `radius`) and inverts the request's input (below). `inverter` bisects between samples on that input, evaluated at any t. The image is `derived`, as for any construction; each representative sample adds a `Ray` from the input's point to its image. `Result.inversion`, present only for inversions, carries the circle and `breaks`, the samples before which the image is open although both neighbors are finite. Breaks come from bounded bisection between samples, so they follow the mathematical curve rather than the renderer's long-jump heuristic, which remains as a backstop. `pathData` in `web/Plot.tsx` honors them. The renderer draws the dashed circle and segments with the construction lines and a center marker. Framing fits the circle as its own family. The `inversionX`, `inversionY`, and `inversionRadius` tracks lead.

Every construction acts on the request's `input` (`engine/input.go`): `"curve"` (or empty) for the base, or `"evolute"`, `"pedal"`, `"contrapedal"`, `"orthotomic"`, or `"offset"`, reusing those constructions' Go functions with the request's own `pole` and `distance`. It generalizes inversion's former `of` field, which it replaces. `inputCurve` returns a `curveFunc` that evaluates the derived curve at any t from the base evaluator and its stencil derivatives, at a stencil spacing three times the base's (`stencil` in `engine/curve.go` carries a spacing), and `Compute` hands that function to the construction in place of the base: stencils, arc length, directions, chord and circle families, the rolling contact, and inversion's bisection all differentiate or evaluate the input. The base is still sampled for drawing and for generators' own geometry (roulette circles, epicycles, pursuit polygons, trajectories). `derivativeOrder` checks the base at the input's order, `constructionOrder` the input at the construction's, and `validateInput` refuses combinations whose orders sum past three (an evolute feeding the evolute or a caustic); `inputAllowed` in `web/types.ts` mirrors that rule so the interface disables them, and switching to such a tab resets the input to the curve. `Result.input`, present only for a derived input, carries it indexed like `base`; the renderer draws it faintly with the base (`construction-input`), reveal slices it like `base`, framing fits it as its own family, and the pole marker appears for a pedal-family input. Tracks for the input's pole or distance follow the construction's own, unless it has them already. **Construct on**, the last control of the curve section, sets it, showing the input's pole or distance fields when the construction's section does not; a note under the description names the input. Export names include it (`studyName`, for example `tangent-garden-pedal-of-pedal.svg`). Offsets, the involute, and circle envelopes, which are oriented by the tangent, are left open where it reverses within a sample step (`reverses` in `Compute`), with a note; other constructions are unaffected. Composition multiplies evaluations: in WebAssembly at 32,768 samples, a circle rolling on an ellipse's evolute took about 1.6 s here (0.3 s on the ellipse), a catacaustic of its pedal 3.0 s, a vector field's catacaustic of its pedal 6.7 s (1.6 s on the field), and a 16-pursuer chase's catacaustic of its pedal 33 s (5.6 s on the chase), past the client's 30 s calculation limit, which reports a timeout; fewer samples resolve it. Harmonic curves (`engine/harmonic.go`) are two more generators on the roulette pattern: `curve.format: "lissajous"` with a `curve.lissajous` block (`amplitudeX`, `amplitudeY`, `frequencyX`, `frequencyY`, `phase`) and `"fourier"` with `curve.terms`, a list of 1–16 `Term`s (`frequency`, `radius`, `phase`), evaluated in closed form. `Result.harmonic`, present only for these formats, carries the exact `period` computed in Go (0 when the frequencies are not commensurate within bounds), `whole` and `constant` flags, a Lissajous figure's fixed `guides` (as `Circle`s), a Fourier curve's term `radii`, and `positions`, one `Epicycles` (the `joints` where the vectors start or the guide points, and the traced `point`) per representative sample, recorded at construction gaps too. The renderer draws the guides, and the circles, vectors, and projections of the last position, with the construction lines; reveal filters positions like a roulette's. Framing fits the guides and every position's circles as their own families. The UI keys the closure note on the frequencies that move the curve, so it stays while amplitudes and phases recompute. Tracks `lissajousPhase`, `lissajousM`, `lissajousN`, `lissajousA`, `lissajousB`, and, for each Fourier term n, `term<n>Phase`, `term<n>Radius`, `term<n>Frequency` replace `a`; term tracks are named by number, a track for a removed term is dropped, and labels come from `targetLabel`. Adding or removing a term waits for pending field evaluations, since the fields after it are renumbered. Cyclic pursuit (`engine/pursuit.go`) is the first generator integrated rather than evaluated in closed form, and the first with several trajectories: `curve.format: "pursuit"` with `curve.pursuit` (`pursuers`, 2–16 of `x`, `y`, `speed`, and `capture`). Go integrates the chase once per request with adaptive Dormand–Prince steps under a step budget, keeps every accepted state, and evaluates any t by one step from the state before it, so the base curve is the first pursuer's path and constructions differentiate it like any other. `Result.pursuit`, present only for pursuits, carries every pursuer's path indexed like `base` (null outside the chase), `polygons`, one `Polygon` of all positions per representative sample, and why the chase ends: `capture` (time, pursuer, and target, counting from 0) or null, `exhausted`, and `end`, the last time known. These are deliberately separate trajectories, not a `family` of derived paths or `Ray`s. Reveal slices the paths like `base` and filters polygons by sample, so a sample index is a time. The renderer draws every path with the base curve and the polygons and final positions with the construction lines; framing fits each path as its own family. Tracks `pursuer<n>Speed`, `pursuer<n>X`, `pursuer<n>Y`, and `pursuitCapture` replace `a`, and adding or removing a pursuer waits for pending field evaluations like a term.

Vector-field trajectories (`engine/field.go`) are defined by `curve.format: "field"` with `curve.field`:

- `x` and `y`: the expressions for dx/dt and dy/dt;
- `seeds`: 1–16 points, each an `x` and `y`;
- `escape`: the escape radius.

The expression parser (`engine/expr`) has a planar field mode (x, y, t) for them and a spatial one (x, y, z, t, `ParseSpatialField`) for `engine3`. It evaluates without allocating and reports whether an expression reads `t`. Curve expressions keep one variable, `t` (or `x` for a graph), and constant expressions reject `y` and `z` as well.

The pursuit and the trajectories, planar and spatial, share the dimension-free `engine/ode` package, and both pursuits share `engine/cyclic`, which runs a chase of any dimension with its capture policy, step control, and budget. The `engine/ode` package holds:

- the Dormand–Prince step, with stage times;
- a `Solution` of accepted states, evaluated at any t by one step from the state before it, into reused buffers (`Stages`), since a derived input evaluates it hundreds of times per sample.

Step-size control and events stay with each caller, which knows its own error norm and stopping rule.

Go integrates each seed separately, once per request, with its own adaptive steps, step budget, and termination event.

`Result.field` is present only for fields. It carries:

- `paths`: every trajectory, indexed like `base` and null outside it;
- `arrows`: each trajectory's position and velocity at each representative sample;
- `ends`: each trajectory's end time and reason (`end`, `escape`, `singular`, or `exhausted`);
- `timed`: whether the field reads `t`;
- `grid`: a lattice `spacing` and its nonzero finite directions, empty for a timed field.

Reveal slices the paths like `base` and filters arrows by sample. Every trajectory shares the base's sample times, so a revealed prefix is the same span of time on each, whatever steps each took. The renderer draws:

- with the base curve: every trajectory;
- with the construction lines: the chevrons, the seeds, the dashed escape circle, and the grid's arrows, at a fixed fraction of the lattice spacing.

Framing fits each trajectory as its own family and never the escape circle or the grid. Tracks `seed<n>X`, `seed<n>Y`, and `fieldEscape` join `a`, which a field keeps. Adding or removing a seed waits for pending field evaluations.

Implicit curves (`engine/contour.go`) are defined by `curve.format: "implicit"` with `curve.implicit`:

- `f`: the expression F(x, y), parsed in the three-variable mode and rejected if it reads `t`;
- `level`: the level c;
- `family`: `enabled`, `from`, `to`, and `count`, for evenly spaced extra levels;
- `window`: `xMin`, `xMax`, `yMin`, `yMax`;
- `cells`: the grid's cells along the window's longer side;
- `stableNormals` (optional): spaces the normals along each contour from its own origin (an open contour's start, a closed contour's lower centroid-centerline crossing) instead of along all contours in turn from their first grid edges; false or absent retains the original placement.

A level set has no parameter, so `Compute` returns before any construction: `base`, `derived`, and `virtual` are empty, the request's `kind` is ignored, and the domain bounds are not checked. `Result.contours` carries:

- `window`, `columns`, and `rows`: the grid;
- `curve` and `family`: level sets, each a `level` and its `contours`, each a list of `points` and whether it is `closed`;
- `normals`: points on the curve with F's gradient there;
- `discontinuities`: where F changes sign along a grid edge without reaching a level, one per edge;
- `nonfinite`: the number of grid points where F is not finite.

In the UI the construction tabs are disabled and every construction section is hidden while the format is implicit, and the animation targets are the level, window edges, family, grid cells, `a`, and the number of normals; `kind` stays in the configuration for when another format is chosen. The worker checks the implicit fields are finite and the counts whole. Reveal draws each contour along by the same fraction of its points, open until complete, and the normals in order. The renderer draws:

- with the base curve: the curve's contours;
- with the derived curve: the family's contours;
- with the construction lines: the dashed window, the normals as arrows of a fixed fraction of the window, and a cross at each discontinuity.

Framing is the window itself, so the drawing holds still while contours split and join. Export filenames use `implicit` in place of the construction.

Iterated maps (`engine/attractor.go`) are defined by `curve.format: "attractor"` with `curve.attractor`: `map` (`clifford`, `dejong`, or `henon`), coefficients `a`–`d`, `start`, `discard`, `iterates`, `fit`, `window`, and `cells`. Like an implicit curve, `Compute` returns before any construction with empty paths, and `Result.attractor` carries:

- `window`, `columns`, and `rows`: the grid, fitted or given, shaped as for implicit curves;
- `counts`: visits per cell, row-major from the lower-left corner with rows upward, and `max`;
- `accumulated`, `outside`, and `escape`: the iterates counted, those beyond the window, and the number of the iterate that left ±100000, or 0;
- `orbit`: the start and the first `lines` iterates.

A fitted window iterates the accumulated span twice, once to bound it and once to count it, so memory is only the grid (at most 1,024² cells). Budgets are 1,000,000 discarded and 5,000,000 accumulated iterates; the reference study takes about 150 ms in WebAssembly and the largest about 0.7 s.

The browser turns counts into an RGBA image (`web/attractor.ts`: one pixel per cell, top row first, the base color at opacity `log(1 + n)/log(1 + max)`) and a PNG data URL through a canvas, cached per result and color. The SVG draws it as an `<image>` over the window with `image-rendering="pixelated"`, so still and animated exports, which rasterize the same SVG at their target size, show the same cells with square edges, and an SVG export carries the density as an embedded PNG. The Content-Security-Policy already allows `data:` images (`img-src 'self' blob: data:`), so no policy change was needed here or in `iwvelando/cloud-accounts`. Reveal cannot cut back a density, so each revealed frame recomputes the first `round(p·N)` iterates in the finished drawing's window with fitting off; live playback and export sample identically. Tracks are the coefficients, start, both counts, the window edges when not fitted, grid cells, and `lines`; `a` is not offered. Export filenames use `attractor`.

## Spatial curve constructions

`engine3` implements torus-knot generators and bounded parametric space-curve expressions with separate `Vec3`, `Curve`, `Request`, `Result`, `Vertex`, and `Ruling` types. Go computes derivatives, singularity guards, ruling endpoints, normals, and mesh topology. Torus derivatives are analytic; custom curves reuse the bounded Go expression parser with endpoint-safe five-point derivative stencils and half-step stability checks. Nullable paths and explicit interval breaks preserve discontinuities. Surface vertices and rulings carry sample indices for reveal playback. Each curve family is framed independently with robust bounds; no planar vector or SVG contract gains dummy coordinates.

Within one numerical evaluation, the center and both five-point stencils share expression values only at bit-identical parameters, preserving the sign of zero. Eleven stack slots bound this scratch; nothing carries across evaluations. Exactly centered stencils share an immutable coefficient table built by the original Lagrange arithmetic, while even a one-bit departure from the center computes its own coefficients. Only polynomial coefficients through degree two are constructed, since higher terms cannot contribute to the first two derivatives; the retained operations keep their original order. Each sampled evaluator also reuses up to 256 coefficient tables for bit-identical normalized stencil positions. The tables contain no curve values, parameter step or geometric state; a full table cache computes unseen positions normally. Returned tables are value copies, concurrent lookups are synchronized, and discarding the evaluator releases its cache. The steps, weighted sums and stability decisions are unchanged.

The additive `tangentGardenSpatial` WASM entry point is transport only. The worker and `EngineClient.computeSpatial` carry a separate schema mirrored by `web/spatial/types.ts`. The worker rejects nonfinite inputs before serialization, and Go validates geometric/workload bounds. `ScalarInput` retains expressions and applies functional updates. Preset generations invalidate pending evaluations; switching a generated knot to expressions awaits those evaluations. Readiness follows the exact configuration revision. Meshes have at most 28,800 vertices and 240 rulings.

The involute construction (`engine3/involute.go`) reuses the same sampling, derivatives, and interval breaks, then adds a typed `InvoluteResult`: nullable member paths indexed like the base, a collapsed flag, representative strings with sample indices, an unreached count, and, when `involute.restart` asks for it, the anchors arc length restarted from past each break (`restarts`, shared with the involute input by `restart` in `involute.go`). It leaves the developable's boundaries, mesh, and rulings empty rather than overloading them, and does not validate the developable's tangent reach. Arc length is accumulated once per request from the anchor on the final grid; reveal truncates it and parameter playback recomputes it. Families are bounded at 24 members and 48,000 points.

Tangent-foot and orthotomic constructions (`engine3/projection.go`) use the independent request `pole: Vec3` and only the base's first derivative. `ProjectionResult` carries the pole marker, nullable `points` and `feet` paths, `collapsed` and image `invalid` diagnostics, and typed `ProjectionConstruction` records (`contact`, `foot`, `image`, `sampleIndex`). These geometric connectors are distinct from rulings, strings, and optical rays. The developable and involute outputs stay empty. Paths share the base's interval breaks, except across a cusp of the base whose tangent line continues (`engine3/cusp.go`: `units.crossing` finds and checks the simple zero of r′, `units.line` gives the line along r″ where the base stands still): then the projection's own `breaks`, sent only then, replace the base's, and `crossed` counts the cusps joined. Reveal slices both paths, and those breaks, and filters constructions by sample. Bounds fit the base, feet, image and pole independently. `poleX`, `poleY`, and `poleZ` tracks update the independent coordinates; tangent reach is neither used nor validated. The renderer adds derived-path, connector/foot, and pole layers and uses the same batches for live and exported drawings.

Sphere inversion (`engine3/inversion.go`) takes `inversion: {center, radius, input}`, with `input` one of `base`, `tangent-foot`, or `orthotomic`. A derived input composes with the pointwise evaluator `project(kind, pole, r, T)` that the projections also use, rather than differentiating a displayed path; composition is limited to that one level, and involutes are not an input. `InversionResult` echoes the center, radius, input, and (for a derived input) the pole, and carries nullable `source` and `points` paths indexed like the base, its own `breaks`, typed `InversionCorrespondence` records (`sampleIndex`, `source`, `image`), a `collapsed` flag, `invalid` and `crossings` counts, and `crossed` (omitted when zero). Its `breaks` are the base's plus every interval where the source passes through the center, less the base's cusps that a projected source crosses (`crossed` counts them; see `engine3/cusp.go`); the renderer draws the image with these, never the base's alone. Other construction outputs stay empty. Bounds fit the base, source, image, and center independently. Tracks `centerX`, `centerY`, `centerZ`, and `sphere` (the radius) join the pole tracks when the input is derived. The renderer adds image, correspondence, sphere (three great circles and a center cross), and source/pole layers.

A construction built on a curve takes the request's top-level `input` (`engine3/composition.go`): `base` (or empty), `tangent-foot`, or `orthotomic`, from the shared `pole`, or `involute`, described by `unwinding: {anchor, offset}`. `Request.composed` is true only for the developable, involute, framed, ruled and canal constructions; the projections, inversion (with its own `inversion.input`) and `none` ignore it, and Compute returns their results unchanged. A derived input replaces `Compute`'s evaluator with `composedEvaluation`, which evaluates `project` pointwise from the base's evaluator and differentiates it with the expression curve's stencils, so every construction, probe and guard runs unchanged on the derived curve, which fills `Base`. `baseSamples` first samples the base by the sampling loop's own rules, and the loop breaks the derived curve wherever the base breaks, except across the base's cusps that `units.crossings` finds, counted in `CompositionResult.crossed`; the chord (asymptote) guard is not applied to the derived curve itself, which is finite wherever the base is. `Request.analytic` reports that its derivatives are numerical, so the knot's and harmonic curve's closed-form r‴ and r⁗ and their tolerances are not applied to it. `CompositionResult` carries the input and pole, the base's own `curve` and `breaks` (sampled by the same rules), representative `ProjectionConstruction` records from base point to foot to input point, and `cusps`; the base curve and pole join the bounds as their own families. The TypeScript mirror is `SpatialConfig.input` and `SpatialResult.composition` (`takesInput` and `composes` in `web/spatial/types.ts`); the scene draws the base as the `parent` layer in the receding ink, reuses the projections' `connectors` and `pole` layers for its connectors, and the reveal slices the composition with the curve. The link schema carries `config.input`; older links take `base`. Pole tracks follow the construction's own tracks when the input is derived.

The involute input (`engine3/unwinding.go`) replaces the evaluator with `UnwindingRequest.evaluation`, which tabulates arc length outward from the anchor on the sample grid (stopping at base breaks, as the involute construction does), completes it at any t by Gauss–Legendre quadrature, and writes I′ and I″ from the base's own derivatives rather than differencing I. It returns the reached samples, and with `unwinding.restart` the anchors it restarted from, which Compute records as the composition's `restarts`; `composition` counts the rest as `unreached`, leaves them out of the cusp runs, records strings (foot equal to contact) as its constructions, and leaves `pole` zero. `Request.projected` distinguishes the projections, whose pole is validated and framed, from the involute, whose pole is ignored. Compute treats a closed base's involute as open. TypeScript: `SpatialConfig.unwinding`, `CompositionResult.unreached`, `projectsInput`/`unwindsInput`/`curveDomain` (`types.ts`); the scene draws strings contact → image with no feet or pole; tracks `inputOffset` and `inputAnchor`; the link schema carries `config.unwinding`, with the preset default for older links, which only the involute input reads. `InversionInput` excludes the involute.

The coil input (`engine3/coilinput.go`) replaces the evaluator with `CoilRequest.evaluation`, which tabulates the rotation-minimizing frame and arc length on the sample grid as `frames` does (from e_z, restarting after breaks, the holonomy distributed on a closed loop), completes them at any t by one transport step from the sample at or before t, and writes g′ and g″ from the base's derivatives and the transport law. It also reports whether the coil closes (a closed, unbroken base and a whole number of turns), which Compute uses as the input's closure. `composition` records coil arms (foot equal to contact) and leaves `pole` zero; `Request.projected` is true only for the tangent projections. TypeScript: `SpatialConfig.coil`, `coilsInput` (`types.ts`); each input's option, legend name, export title, connector layer and pole use live in one descriptor, `curveInputs` (`web/spatial/inputs.ts`), which the controls, legend, layers, scene and export title read; tracks `inputRadius`, `inputAngle` and `inputTurns`; the link schema carries `config.coil`, with the preset default for older links, which only the coil input reads. `InversionInput` excludes the coil.

Refining between samples (`engine3/refine.go`) is a request flag, `adaptive`, read only by curves given by a formula (`Request.refines`: a torus knot, harmonic or custom curve). `refinePath` takes a drawn path's uniform samples and breaks and a pointwise evaluator, and returns a `RefinedPath`: the samples, unchanged and at whole positions in `at`, with points bisected in between at fractional positions, nulls at every break, and its `tolerance`, `inserted`, `breaks`, `unresolved` and `exhausted` report. A priority queue bisects the worst piece first, so a budget that runs out leaves the error spread evenly, and the order is deterministic. `Compute` refines the base right after its sampling loop's breaks and before the developable's mesh, so breaks it finds join `Result.Breaks` and every surface built on the curve leaves them open. It refines the composition's base curve, the projection and the inversion image after their own results, the image replacing the midpoint passage test. `Request.position` gives each path's evaluator: a custom curve's expressions are evaluated alone, without the derivative stencils, and a projected input from the base's position and tangent. `Result.adaptive` (`AdaptiveResult`) holds the four optional paths. Nothing else in the result changes: framing (unless `adaptiveFrame`, below), construction lines, probe diagnostics and animation tracks stay on the uniform samples, so a study without the flag is byte-identical. TypeScript: `SpatialConfig.adaptive`, `RefinedPath` and `AdaptiveResult` (`types.ts`); the scene draws a refined path, joined except beside a null, in place of the samples of the `base`, `parent`, `projection` and `inverse` batches, so the WebGL drawing, the line drawing and every export share it; `reveal` keeps each refined path's points up to the last revealed sample by `at`, and its reach up to the same sample by `reachAt`. `adaptiveFrame` gives each refined path its `reach` (`refine.Reach`), from the path refined without the view, and `fitReach` takes it into the bounds with the family drawn from that path, within the family's fences; a reveal's `fitFamilies` does the same with what it has reached. The link carries `config.adaptiveFrame` only when set. The link schema carries `config.adaptive`; older links take the first preset's `false`. **Refine between samples** in **Sampling & definition** sets it, for every format but fields, chases, surfaces, mirrors and level sets, and a readout under it totals the report. `adaptiveSurface` (`engine3/surfacerefine.go`) also adds columns to a developable's, ribbon's, ruled surface's or canal's mesh: `surfaceColumns` gathers the fractional positions of the refined paths on that surface, a bisection depth at a time within a vertex budget, `stations` lists each interval's samples and columns, and each surface's mesh loop walks those stations in place of its two samples, placing a column with its own pointwise evaluator. Sample positions keep their vertex keys and creation order, so a mesh without columns is the one built before; `AdaptiveResult` adds `minus` and `plus` (the developable's and ribbon's refined edges), `columns` and `capped`. The link carries `config.adaptiveSurface` only when set. Measured natively, the worst cases found (every refinable path of a 2400-sample curve exhausting its budget, with numerical derivatives under a derived input) take about 0.14 s; the two presets take under 10 ms.

Spatial harmonic curves (`engine3/harmonic.go`) are a third curve definition, `format: "harmonic"` with `harmonic: {center, terms, min, max}` (1–8 `HarmonicTerm`s of `frequency`, `cosine` A, and `sine` B), evaluated with exact derivatives in `compile`. Closure uses `engine/closure`, a small package shared with the planar harmonic curves and roulettes; `compile` reports the curve closed only when the domain spans whole periods, which makes `Compute` share the seam sample. `HarmonicResult`, present for this format under every construction, echoes the center and terms and carries `period`, `whole`, `closed`, and `positions` (`sampleIndex`, `joints`, `point`) at the representative samples. Framing appends each term's joints and ellipse extents as their own families to whatever the construction fits. Tracks `c0x`, `c0y`, `c0z`, and `harmonic<n>Frequency`, `harmonic<n>Ax`…`harmonic<n>Bz` per term (named by number, dropped when the term is removed), plus `min` and `max`, which move the harmonic domain for this format, join the construction's tracks. Adding or removing a term awaits pending field evaluations. The renderer adds vector-sum and ellipse layers for this format; reveal filters positions by sample and frames them as Go does. `web/spatial/harmonic.ts` holds the closure key and note and the next-term rule.

Framed ribbons (`engine3/frame.go`) take `frame: {kind, reference, angle, twist, offset, width, strands, closure}` under `construction: "framed"`. `frames` runs after the shared sampling pass and uses its tangents, speeds and midpoint speeds (Simpson arc length), and, for the Frenet diagnostic, the developable's binormals and normal-validity flags. It fills the result's `mesh`, `minus`, `plus`, and `rulings` with the ribbon, its edges, and cross-lines, so the developable's surface, rulings, and edges layers draw it, and adds a typed `FrameResult`: `frames` (glyphs with `sampleIndex`, `point`, `tangent`, `normal` U, `binormal` V at the representative samples), nullable `strands` indexed like the base, its own `breaks` (the base's plus Frenet flips), `length`, `pieces`, `undefined`, `flips`, `fallbacks`, `closed`, `holonomy`, `correction`, and an optional `seam` (`point`, `start`, `end`, `angle`). The renderer draws the ribbon edges with `frame.breaks`, never the base's alone. Bounds fit the base, ribbon edges, and each strand independently. Tracks `angle`, `twist`, `width`, `distance` (the strand offset), `strands` (rounded), and, for the transported frame, `normalX`, `normalY`, `normalZ` join the curve's tracks; the tangent reach is neither used nor validated. Reveal slices strands and breaks, filters glyphs, and keeps the seam only once the whole loop is shown. `web/spatial/frame.ts` words the note about the frame, the seam and diagnostics.

Ruled surfaces (`engine3/ruled.go`) take `ruled: {partner, thread, rate, shift}` under `construction: "ruled"`, with `partner` either `chord` or `thread`. Before sampling, `RuledRequest.partner` builds the partner evaluator from the curve's own `compile` evaluation (wrapping on a closed curve) or from the parsed thread (through `sampled`, the stencil evaluator it shares with custom curves). `ruledSurface` runs after the shared sampling pass and uses its tangents and speeds for `a′`. It writes the partner's nullable points to the result's `plus` (leaving `minus` empty) and fills `mesh` and `rulings`, so the developable's surface, rulings, and edges layers draw it. Its mesh is four strips per interval, with vertex normals from `S_t × S_u` and face normals where those vanish. It also adds a typed `RuledResult`: `partner`, its own `breaks` (the base's plus the partner's gaps and jumps, shared with the jump rule `jumps` in `Compute`), `closed`, `gap`, and the counts `outside`, `coincident` and `singular`, with `developable` and `deviation`. The renderer draws the partner with `ruled.breaks`, never the base's alone. Bounds fit the base and the partner independently. Tracks `shift` and `rate` join the curve's tracks, and the tangent reach is neither used nor validated. Reveal slices the partner and the breaks, and `web/spatial/ruled.ts` words the note. The mesh has at most 57,600 vertices.

Canal surfaces (`engine3/canal.go`) take `canal: {radius, profile, meridians}` under `construction: "canal"`, with the angle carried by the request's `frame`. `CanalRequest.frame` forces the rotation-minimizing kind and clears the ribbon and strand fields, so they are neither drawn nor validated. `Compute` runs `frames` with that request, which now returns its carried field (U, V, arc length and the offset direction), and then `canalSurface` builds the contact circles from R and R′, evaluated through `sampled` like a custom curve. It fills `mesh` with normals `q/R` and sets the result's `frame` (glyphs, holonomy and seam for the meridians) and a typed `CanalResult`. That result holds representative `circles` (`sampleIndex`, `real`, `sphere`, `center`, `radius`, closed `points`), nullable `meridians`, its own `breaks`, `constant`, `closed`, `gap`, `steepest`, and the counts `undefined`, `imaginary`, `between`, `collapsed` and `folded`. `minus`, `plus`, and `rulings` are empty. Bounds fit the base, each meridian, and the circle points, the same families reveal fits. The renderer adds contact circle (with gray great circles for spheres without one) and meridian layers, and reuses the surface, frame, and seam layers. Tracks `sphereRadius`, `angle`, `twist`, `meridians` (rounded), and `normalX`–`normalZ` join the curve's tracks. Reveal slices meridians and breaks and filters circles, and `web/spatial/canal.ts` words the note. The mesh has at most 69,120 vertices outside dense gaps.

Curve diagnostics (`engine3/diagnostics.go`) run for any curve format and construction when the request sets `diagnostics: true`; surface, ray and implicit studies ignore it. `diagnose` reads the shared sampling pass's velocities, accelerations and binormal guard (the same `valid` flags the developable and the Frenet frame use) before the construction branches, and a thin `Compute` wrapper clips osculating centers against the finished study radius once, whichever branch returned. r‴ is analytic for knots (`knotJerk`) and harmonic sums (`harmonicJerk`), otherwise `jerk` differences the evaluator's own r″ (`jerkStep`) at two steps and discards disagreements. The typed `DiagnosticsResult` holds nullable per-sample `curvature`, `torsion`, `tangent`, `normal`, `binormal` and `center` series indexed like the base, with `flat`, `unknown` and `clipped` counts. The flag is off by default, so a result without it is byte-identical to one made before diagnostics existed.

Vector fields (`engine3/flow.go`) take `format: "field"` with `field: {x, y, z, seeds, escape, min, max, a}`. `Compute` parses and integrates every seed once, before `compile`, which returns the first trajectory as the base evaluator: position from the dense solution, velocity from the field, and acceleration from a central difference of the field along the flow. Every construction then runs on it unchanged. `fieldGeometry` adds a typed `FieldResult`, present under any construction like `harmonic`. It holds nullable `paths` indexed like `base` (the first is the base), `arrows` at the representative samples (`sampleIndex`, `seed`, `point`, `velocity`), `ends` (`time`, `reason`, nullable `point`, `steps`), `resting`, and `timed`. Bounds fit every path as its own family. `construction: "none"` draws the curve alone under any definition: it leaves `minus`, `plus`, `mesh`, and `rulings` empty and fits the base and those families. A first trajectory with no regular sample is refused under a construction, and alone only when no trajectory moves. The renderer adds the other trajectories (the gradient ink, with no breaks before their end), fixed-length field directions, and crosses at the seeds and at early stops. Tracks `a`, every seed's `seed{k}{X,Y,Z}`, `escape`, `min`, and `max` replace the curve's tracks. Reveal slices every path at the same index and filters arrows. `web/spatial/field.ts` words the note and places a new seed.

Spatial pursuits (`engine3/pursuit.go`) take `format: "pursuit"` with `pursuit: {pursuers: [{x, y, z, speed}], capture, min, max}`. `Compute` runs the chase through `engine/cyclic` before `compile`, which, as for a field, receives the prepared first-path evaluator: position from the dense state, velocity and acceleration from the pursuit law. `pursuitGeometry` adds a typed `PursuitResult`, present under any construction: nullable `paths` indexed like `base`, closed `polygons` at the representative samples (`sampleIndex`, `points`), `capture` (`time`, `pursuer`, `target`, from 0) or null, `exhausted`, `end`, and `final` positions. Bounds fit every path as its own family. The renderer reuses the trajectories layer for the other pursuers and the seeds layer for the starts and, after an early stop, the final positions, and adds a polygons layer. Tracks `pursuer{k}{X,Y,Z,Speed}`, `capture`, `min`, and `max` replace the curve's tracks. Reveal slices the paths, filters polygons, and marks the final positions only once it passes the stop. `web/spatial/pursuit.ts` words the note and places a new pursuer.

Surface studies (`engine3/surface.go`) take `format: "surface"` with `surface: {kind, a, b, c, uMin, uMax, vMin, vMax, uSamples, vSamples, curves, reverse, offset, reach, edges?, ridges?}`. `Compute` hands them to `surfaces` before anything else, so the curve's samples, lines, construction and generator fields are neither read nor validated, and every curve field of the result is empty. A surface is a different evaluator, not a curve with dummy coordinates. `SurfaceRequest.patch` returns X and its exact first and second partial derivatives; `point` gives the normal, principal curvatures and directions, and umbilic flag at one parameter point. The result is a typed `SurfaceResult` of grid sheets (`SurfaceSheet`: nullable `points` and `normals` indexed `[i][j]` by u and v sample, the joined edges `alongU` and `alongV`, and `faces`), so parameter identities survive for reveal and drawing. It holds the `surface`, the `offset` (null at d = 0), and two `focal` sheets that add `shape` and `clipped`. It also holds normal `lines` (`i`, `j`, `point`, `end`), the representative `uCurves` (v indices) and `vCurves` (u indices), and the `singular`, `umbilics` and `folded` counts. With `edges` and an offset it holds the offset's cuspidal `edges` (`branch`, `closed`, `points`, and each point's grid place `i`, `j` in sample steps), an empty list when there are none; without them the key is absent, so other results encode as before. With `ridges` it holds the patch's `ridges` in the same form, each point on its focal sheet and with its foot on the patch in `feet`, which an offset's edges never carry. Go decides every edge and face (a focal edge through `continues`); the renderer only splits each face into two triangles, shading a corner without a normal by its triangle's own. Reveal (`web/spatial/animation.ts`) grows every sheet along u, keeping the samples up to the current one with the edges, faces and normal lines among them, and `surfaceBounds` frames them as Go does, so a whole reveal matches the still.

Ray studies (`engine3/rays.go`) take `format: "rays"` with the same `surface` request, read as a mirror (`validatePatch` checks the patch, domain and grid, not the offset or normal reach), and `rays: {light, azimuth, elevation, source, length, stop, edges?}`. With `stop`, each representative line's `end` is its first real caustic point within `length` and its `back` its first virtual one, or `end` as far ahead as `back` when it has no real point, and `back` is `point` when it has no virtual one; the trace, the ride and the framing read those ends as drawn. `Compute` hands them to `rays`, which shares the patch evaluator, the grid helpers (`at`, `positions`, `representatives`, `sheet`, `spans`) and the edge rule `continues` with the surface study. `SurfaceRequest.ray` evaluates one reflection with exact derivatives: the lit flag, R, the reflected wavefront's principal curvatures μ₁ ≥ μ₂ and directions, the stigmatic flag, and the twist for tests. The typed `RaysResult` holds the mirror's `surface` sheet, four `caustics` (`CausticSheet`: a grid sheet with `branch`, `virtual` and `shape`, in the order branch 1 real, branch 1 virtual, branch 2 real, branch 2 virtual), representative `lines` (`i`, `j`, `start`, `point`, `end`, `back`, `virtual`), `uCurves`, `vCurves`, the `source` (null for parallel light), and the counts `singular`, `unlit`, `atSource`, `stigmatic` and `clipped` (per branch). With `edges` it holds the caustics' cuspidal `edges` (`causticEdges`, engine3/causticedge.go), in the surface study's `CuspidalEdge` form with each point's foot on the mirror and `virtual` set on an edge behind it, traced by the same generic `contours` over the mirror's samples; without it the key is absent. Every curve field of the result is empty. The renderer draws the mirror and its parameter curves on the surface layers, each branch's real part on its focal layer, and adds incident rays with the source, reflected rays, and a virtual layer for the extensions of virtual rays and the virtual parts, drawn only as lines. Real caustic edges join the gold `cusps` pass; virtual ones are a pass of their own, drawn only while the virtual layer is on. Reveal splits edges at the revealed row, and the trace keeps the runs of each edge whose points the light has reached, each at its foot's time plus its distance along the ray. Tracks for the shape, `azimuth` and `elevation` or `sourceX`–`sourceZ`, `rayLength`, the domain and the grid replace the curve's. Reveal grows every sheet along u and filters the rays, and `raysBounds` frames them as Go does. `web/spatial/rays.ts` words the note.

Refraction shares that path: `rays.interaction` is `"reflect"` or `"refract"`, and a refracting request adds `n1` and `n2`. `SurfaceRequest.ray` writes both outgoing directions as `D = aI + bn`, so the derivatives and the caustic eigenproblem are unchanged, and it flags samples beyond the critical angle (`Total`), which `traced()` excludes from caustics, edges and receivers. `RaysResult` adds `total` and each `Ray` a `total` flag, its end along the totally reflected ray. The receiver (`engine3/receiver.go`) is its own request, `rays.receiver: {plane, at, c1, c2, size, bins, tilt?, refine?}` with `plane: "none"` for none, and its own result type, `Receiver` (`plane`, `corners`, `size`, `irradiance[a][b]`, `peak`, the fluxes `emitted`, `received`, `outside`, `away`, `total`, `edge`, and `split` and `exhausted` when refined), never merged with the caustic sheets. `receive` weights each cell by its midpoint and spreads the flux over its corners' crossing triangles with `raster`, which accumulates exact edge coverage into per-row differences and a running sum, so its work grows with the bins edges cross rather than those covered. Refined, it splits cells breadth first on the grid 2^refine times finer, tracing new corners and midpoints with `outgoing`, `ray` without the wavefront's shape, and holding each finer column once a point on it is traced; cells never split take the unrefined path, so they are bit for bit as without refinement. The corners fit as their own family, never fenced. The renderer draws the receiver as one quad, its texture coordinates carried as its normal, whose RGBA texture holds each bin's log shade in 16 bits and whether light lands (`receiverSheet` in `scene.ts`, ink 7, unshaded and without hue, sampled without filtering on texture unit 2), so drawing it costs the same whatever its bins, and its window outline, on the **Receiver irradiance** layer; totally reflected rays are gray with the transmitted ones. Reveal withholds the receiver until every column is shown, since it belongs to the whole family. Tracks add `n1`, `n2`, `receiverAt` and `receiverSize`. Conic sections cut from a cone of light, 216 × 60 cells and 200² bins, takes about 70 ms through the WASM bridge; at 960² bins refined twice, splitting 64,800 cells, about 390 ms (`make bench ARGS="--study cone-refined"`).

Each spatial worker owns an `engine3.Engine` for its sequence of requests; the standalone `engine3.Compute` remains stateless. Once a surface/light family is requested again, a receiver study retains its refined corner rays in world coordinates and each level's cell midpoint flux while the surface and light stay fixed. Moving, tilting, resizing or rebinning the window reruns its crossings, splitting decisions, exact rasterizer, accounting and fitted bounds. The private sample grid is retained with the geometry. The coarse landing grid is reused as scratch, bounded by the surface's 14,400-cell limit (under 0.5 MiB); every entry is overwritten before each window or inset pass. Finer landing columns are also reused as scratch and their landing coordinates are cleared before every pass. The exact rasterizer reuses separate private differences and rounding scales for the window and the view inset, clearing them before every pass. Each uses one packed buffer, reshaped within its capacity when the dimensions change, bounded by 960 × 962 values for the window (under 8 MiB) and 1024 × 1026 for the inset (under 8.1 MiB), plus row headers and scales. An absent, disabled or invisible inset releases its scratch immediately. Keeping the two passes separate prevents their different dimensions from displacing each other's storage. Its finished irradiance grid is newly allocated for every result, so a later frame never overwrites an earlier one. Output arrays belong to each result, so lifting them into the typed reply cannot consume the cache. A change to any surface or light field, a disabled receiver, another spatial kind of study or a failed computation releases the cache; changing refinement levels replaces its finer grids. Trace columns are allocated lazily within 16 MiB and finer landing scratch within 8 MiB, plus the surface's bounded sample and coarse landing grids; a full cache evaluates uncached points normally. A family used only once allocates no tracing storage, so continuously changing the surface or light incurs no cache population. Each refinement level also retains its own cell queue within a separate 8 MiB budget. The queues keep their capacities as the window and its inset change; used entries are overwritten before reading. A queue too large for the remaining budget is allocated only for that pass. Changing refinement levels or releasing the ray family drops the retained queues. The fixed surface, caustic sheets, cuspidal edges and representative rays are also retained for that family. Each reply copies their arrays and vertices into independent storage before transport. Pointer grids preserve every gap and row shape, but their packed value buffers reserve space only for present vertices or scalar values; empty caustic and diagnostic grids therefore need no value storage. Repeated source pointers become independent copied values as well. The current mirror or light diagnostics are retained the same way, as one private grid that each reply copies; changing the probe target replaces it, turning diagnostics off releases it, and a free probe between samples is still evaluated at its requested coordinates every frame. `make bench ARGS="--study cone-moving-mirror"` and `--study cone-moving-light` measure the two targets with the moving receiver. The geometry is bounded by the patch limit of 14,400 cells and released with the family. Fitted bounds are recomputed with the current receiver corners. This applies to interactive edits, playback and exports through the same worker path, without changing sampling or exported metadata. `make bench ARGS="--study cone-moving"` follows a receiver through tilts from 20° to 75° and back at 480 bins refined twice, about 210 ms a frame through the WASM bridge, decoding and transfer included; reuse saves roughly an eighth of a frame there and at 960 bins.

Implicit surfaces (`engine3/implicit.go`) take `format: "implicit"` with `implicit: {f, a, level, box: {xMin, xMax, yMin, yMax, zMin, zMax}, cells, refine, sections: {normal, from, to, count}}`, and every other field is ignored. `F` is parsed by the existing `expr.ParseSpatialField` binding (x, y, z, t and `a`), and a request that reads `t` is refused. `field` samples `F − c` on the box's grid, and `march` meshes each cube's six tetrahedra, solving each crossed edge once through a map from edge (or grid point) to vertex, so the result is an indexed mesh: `ImplicitResult` holds flat `positions`, `normals` and `triangles` arrays, the `cut` and `open` boundary edges as vertex-index pairs, `components` with their Euler characteristics, `sections`, `marks` at discontinuities, and the counts `nonfinite`, `discontinuities`, `ambiguous`, `singular`, `sectionDiscontinuities` and `sectionsSkipped`, with `truncated`. It is a new result type; nothing in it is a curve sample or a surface-patch grid, and it never feeds the curvature or ray studies. Sections reuse the planar engine's contour tracer through `engine.TraceLevel`, which traces and refines one level of a field given as a Go function, with a `ContourBudget` carried from plane to plane; the 2D implicit curve and a spatial section therefore share one implementation. Only their refinement tolerance differs: a section refines to a thousandth of a cell, a 2D curve to 1/5000 of its window's longer side and a 3° bend between chords. Bounds fit the mesh's vertices, the section points and the box's corners as separate families, so the box frames the study and a level track keeps the camera still. The renderer draws the mesh by index from the engine's shared vertices (`implicitMesh`; a corner without a normal is a copy of its vertex shaded by the face, and without the `OES_element_index_uint` extension the mesh is drawn corner by corner; the phase is decorative, by height), the sections in the base ink, the plane polygons and box in gray, the cut edges in teal, and the open edges and discontinuity crosses in rust, on the **Level surface**, **Section curves**, **Section planes** and **Box, cuts & open edges** layers. Reveal keeps what lies below a height rising through the box, splitting section paths there, without recomputing. Tracks are `level`, `implicitA`, `sectionFrom`, `sectionTo`, `cells` and `sectionCount`; `refine` is not a track. The worker refuses nonfinite box, level, `a` and, with sections, the normal and offsets, fractional cell or plane counts, and fractional refinement levels.

With `refine` above 0, `engine3/adaptive.go` meshes instead of the uniform loop. It still starts from the grid's samples.

- `refiner` holds binary trees of tetrahedra on an integer lattice. A cube gets trees only when one of its tetrahedra is split, or when a split grid edge borders it. An edge-to-leaves map finds the tetrahedra that share an edge, for the closure.
- `adaptive` keeps `F − c` in three places:
  - the grid's own array;
  - an array for the midpoints of grid edges, which are also face and cube centers;
  - a map for finer points.
- It flags and splits generation by generation, then marches each cube: an unrefined cube as the grid's six tetrahedra, and a refined one leaf by leaf.

Vertices are keyed by lattice edge rather than grid index, and both paths share `marchTet`, the triangle construction. The uniform path is unchanged, and meshes every study without refinement bit for bit as before. `field.vertex` keeps its own copy of the vertex and normal steps, because sharing them changed how the compiler fuses their arithmetic, and with it the last bit of some normals. `ImplicitResult.refinement` reports `{levels, reached, bisected, unresolved, exhausted}` in the JSON.

No spatial mesh goes through JSON. `cmd/wasm/mesh.go` copies every mesh array of a spatial result into one `ArrayBuffer` and returns `{ json, mesh, implicit }`: `mesh` is the curve study's mesh (`Result.Mesh`, an `engine3.CurveMesh`) as `vertices`, seven float64 per vertex (position, normal, phase), `triangles`, three int32 vertex indices per triangle, and `sampleIndex`, one int32 per triangle, and `implicit`, only for an implicit surface, holds `positions` and `normals` (float64) and `triangles`, `cut` and `open` (int32). They are typed views on the buffer, float64 first so every view is aligned, with `null` for each array in the JSON. A refusal is JSON alone. The worker puts the views back into the result and transfers the buffer to the page instead of copying it; `SpatialResult.mesh` is a `CurveMesh` and `ImplicitResult` types its arrays as `Float64Array` and `Int32Array`. The values are the float64 and int32 numbers Go computed, exactly what JSON's round trip gave. The curve mesh is indexed: a tube shares each drawn ring between the strips either side of it, a developable each sheet's points at a sample, and a ruled surface each grid point that has a normal, while a corner shaded by its own triangle's face normal (a framed ribbon's, or a ruled surface's where S_t × S_u vanishes) is its own vertex. A vertex is shared only where every triangle would give it the same seven numbers, so the triangles, corner by corner and in order, are those the unindexed mesh listed. The reveal keeps the triangles whose sample is at most the last revealed, on the same vertices (`revealMesh` in `web/spatial/animation.ts`), and `buildScene` uses the vertices and triangles as an indexed batch. A field added to `ImplicitResult` or `CurveMesh` travels in the JSON unless it is added to the mesh reply on both sides. Transport had been a tenth to a fifth of an implicit frame's time and three quarters or more of a tube's; Go's work is the rest.

The other large numeric arrays of a spatial or 4D result leave the JSON too, without any change to the result the page reads. `cmd/wasm/lift` walks the result by reflection, after the meshes are taken out, and moves every slice, or slice of slices, of `engine3.Vec3`, `*engine3.Vec3`, `[3]float64` or `[4]float64` (the 4D `Vec3` and `Vec4`), `float64` or `*float64` that holds at least 32 floats into one float64 array, setting it to nil. The walk records the slices and their total size first, then packs them into one exactly sized staging array, avoiding repeated allocation and copying as rows accumulate. Slice headers are retained before clearing their result fields; no result storage survives the reply. A missing point or number is three NaN or one NaN, which JSON can never have carried: a NaN or an infinity in a lifted array refuses the result, as `json.Marshal` does. Each array's `Place` (its JSON path, kind, offset, and its length or each row's length, −1 for a null row) goes beside the JSON as `lifted.places`, itself JSON, and the floats as `lifted.floats`, a `Float64Array` on the mesh buffer for a spatial result and on a buffer of its own for a 4D result (`tangentGardenTesseract` returns `{ json, lifted }`). The worker forwards `lifted` with the result, transferring the buffer, and `EngineClient` puts each array back with `restore` (`web/lifted.ts`), so a point comes back as `{x, y, z}` or null, a 4D point as `[x, y, z]`, and a number as the float64 JSON would have parsed, −0 included. A field marked `omitempty` loses its key when lifted, and `restore` adds it back at the end of its object. Boolean slices and grids holding at least 32 flags use the same buffer with kind `flags`: 32 booleans per float64, stored as an exact unsigned 32-bit integer, least-significant bit first. Each row starts a fresh word, unused high bits are zero, and row lengths retain partial words, empty rows and null rows. The page restores ordinary boolean arrays, so topology, breaks and their consumers are unchanged. Integer arrays, fixed-size arrays and short arrays stay in the JSON. This carries the curves (`base`, `minus`, `plus`, `composition`), refined paths, canal circles and meridians, surface, focal, caustic and probe grids, trajectories, pursuits and 4D paths; a surface study's large geometry and topology both travel typed, leaving only its small records in JSON. A new numeric field of these types is lifted with no change on either side. Representative optical rays (`engine3.Ray`) also lift as kind `ray`, packed explicitly as 16 float64 values: the two sample indices, start, contact, outgoing end and virtual end (xyz each), then virtual and total-reflection flags as 0 or 1. At least two rays lift; shorter arrays stay in JSON. Packing fields explicitly avoids native/WASM differences in integer size and struct padding. The page restores the same ray objects, including both flags when false; the numerical engine, scene and exports retain their existing types and values.

Each receiver raster pass prepares the inverse plane rotation once and reuses its sine, cosine and cyclic axes for every crossing. The inverse rotation keeps the original two-coordinate operations and a function boundary that prevents arm64 from fusing them with the caller's arithmetic. Whole turns take the exact identity path, including signed zero. Preparation belongs to the pass, so changing the tilt or plane needs no retained transform or invalidation.

Fresh surface framing samples use one call-owned vertex buffer instead of an allocation per sample. Fresh optical geometry stores its present surface points, normals, caustic points and caustic directions in blocks of 256 vertices, owned by that family. A new block leaves all earlier pointers fixed, gaps consume no vertices, and at most 255 unused vertices (6,120 bytes) remain in the final block. This reduces allocator and garbage-collector object work without changing evaluation order, geometry, or retained-cache limits.

Receiver refinement allocates each level's child cells once, after counting that level's splits, and compacts the cells left whole into the level's own queue. The levels are kept apart in their original order, so the leaves are never copied. The raster finishes its bins into its point-flux grid, so it holds two bin grids. Each fresh point-flux grid packs its columns into one backing buffer, with each column's capacity limited to its own height; this avoids an allocation per column while preserving independent results and safe column appends, for both square windows and rectangular view insets. Stateless requests retain no queues; a worker can reuse them within the bounded cache described above. The box filter, the breadth-first cell budget and the order in which flux accumulates do not depend on this storage.

Spatial curve refinement stores evaluated points in blocks owned by each refinement call; retained paths keep their points alive independently of later calls. A canal shares contact-circle evaluations between its meridians and surface seams, with pointers into private blocks rather than individually allocated map values. Both keep the same evaluation order, subdivision budgets and numerical results. For **A cord twisted round a spring**, batching reduces native allocation count from about 76,000 to 6,600 per frame, with about 15.4 MB allocated in either case. Its WASM bridge time stayed about 83 ms against the deployed engine: fewer allocated objects alone do not establish a playback speedup (what later made it faster is after **Measuring**).

Robust spatial framing sorts each point family's three coordinate lists in one temporary buffer sized to the largest family's nonmissing points. The buffer is reused across families within the fit and released afterward; gaps and empty sheets consume no coordinate slots. Per-family Tukey fences, refined reach, union bounds and the final radius use the same samples and arithmetic.

**Measuring.** `make bench` (`scripts/bench-spatial.mjs`) times the largest implicit studies and the tube, ribbon and developable presets with the largest curve meshes through a WASM engine as the worker calls it: the bridge call, decoding, the copy posting to the page would make, laying a curve mesh out as the scene's batch, and the bytes transferred. `--compare <URL or directory>` times another build's engine, such as the deployed site, beside the local one and prints each study's speedup; it reads either reply shape. `scripts/playback-probe.js`, pasted into the console of any build, times an animation in the page: the interval between drawn frames and the frames drawn per second, each engine's request to reply, the reply to the first draw after it, and how many engines answered. Compare with `make preview`, since the development server's React and worker are slower. Headless Chromium's frame rate varied four- to five-fold between identical runs, so judge smoothness on a device, not by a headless frame rate. `make bench` has no 2D studies; `make preset-hashes ARGS="--compare <URL or directory> --runs 5 --only <name>"` times any preset in all three notebooks the same way, through the page's own worker code, and checks that its results are unchanged. To turn an engine time into a frame rate, recall that playback alternates two engines, so parameter playback runs at about min(30, 2000 ÷ milliseconds per frame) frames per second: a 2D frame of 200 ms plays at about 10. Chromium's CPU throttling (DevTools, or `Emulation.setCPUThrottlingRate`) slows only the page's main thread, not the engine workers, so it measures the cost of drawing alone.

To find where Go's time goes, profile natively. Take real requests by wrapping `Worker.prototype.postMessage` in a Playwright `addInitScript` and saving the payload while a preset plays, or, for a preset at rest, load its `config` through Vite's `ssrLoadModule` as `bench-spatial.mjs` does (`web/presets.ts`, `web/spatial/presets.ts`); the request JSON unmarshals straight into `engine3.Request` (or `engine.Request`, `engine4.Request`). In a scratch `_test.go` in the engine's package, unmarshal it, time `Compute` and `json.Marshal` separately, and run `go test -run <name> -cpuprofile cpu.out`, then `go tool pprof -top -cum cpu.out` for the breakdown. Delete the scratch test and profile afterwards. A native profile shows where the engine spends its time, not what a frame costs in WASM, so confirm a change with `make bench` or `make preset-hashes`.

In WASM, allocation costs more than arithmetic. Go's collector there runs on the one thread the engine has, so a refined study can spend most of its frame allocating and collecting, which a native profile barely shows: WASM ran 4–10 times slower than native for such studies. Profile allocations first (`go test -benchmem`, `-memprofile`), then confirm in WASM itself: `node --cpu-prof` on a script that loads `public/wasm_exec.js` and `public/engine.wasm` and calls the bridge (`tangentGardenCompute`, `tangentGardenSpatial`, `tangentGardenTesseract`) with a captured request writes a profile that Chrome's DevTools opens, and Go's WASM keeps its function names. Removing the allocations from the 2D stencil made refined 2D presets 2.4–2.6 times faster in WASM. For an offset stack, sharing its base curve's evaluations between members and allocating segments in blocks took a frame from about 210 ms to 60 ms. Every preset was unchanged bit for bit both times.

Calls cost more in WASM too. Go compiles the builtin `min` and `max` on floats, and `math.Min` and `math.Max`, to function calls there, where native code uses one instruction. In an inner loop that is a large share of the work: the receiver rasterizer clamps every row and bin, and was about 70% of a refined receiver's frame. It calls `fmin` and `fmax` (`engine3/minmax.go`) instead, which are the builtins bit for bit and inline. **Conic sections cut from a cone of light** at 960 bins refined twice went from about 290 ms a frame in WASM to 170 ms, with every bin unchanged; `engine3/minmax_test.go` checks that the WASM listing of the rasterizer has no such call. A native profile cannot show this, so time the change in WASM, for example with `GOOS=js GOARCH=wasm go test -bench` and Go's `lib/wasm` directory on the path. Replacing `math.Min` and `math.Max` elsewhere in engine3 changed no measured frame, so the helpers stay where a loop runs per bin or per sample: the rasterizer, and the curve evaluator (`sampled`, its stencils and `Vec3.valid`) and chord distance (`segmentDistance`) that refinement calls for every point between samples. The same test covers them.

A refined canal's frame is mostly its meridians' refinement. **A cord twisted round a spring** evaluates 7,440 contact circles, 31 between each pair of its 240 samples: each meridian refines on its own, and the scan probes every interval at 1/32 of a step, at any twist. Every circle is a probe whose distance from its chord decides where refinement goes, so asking for fewer would change the drawing. Only about a tenth of the curve evaluations behind them repeat a parameter exactly (the arc length's midpoints), too few to repay a cache's lookups. Its frame was instead made cheaper at the same circles (2026-10-25). `Vec3.valid` compares each coordinate with its bound instead of calling `math.Max`. The canal's mesh looks up each ring's first vertex once a strip, rather than in a map for each of a triangle's corners. The shared refinement sorts with `slices.SortFunc`, since `sort.Slice` swaps by reflection. Against the deployed engine, the spring went from 77 ms to 57 ms a frame in WASM and **A coiled cord round a trefoil** from 93 ms to 72 ms, with every preset unchanged bit for bit. What remains is mostly evaluating the curve's expressions for its stencils, with about a tenth spent collecting the points, circles and mesh the frame keeps.

Each receiver refinement level costs two to two and a half times the one below it: the cone's moving window at 960 bins took 35, 63, 171 and 428 ms a frame in WASM at 0 to 3 levels (2026-10-25). So frames calculated while parameters play spread a receiver refined twice or more one level coarser (`playbackRefinement`, `web/spatial/receiver-view.tsx`), and each frame's configuration records the level it was spread at. Only the playback loop's lanes ask for it: the opening frame, a pause (which recalculates the frame it stopped on), scrubbing, the end of a single pass, the loop check and export calculate at the study's own levels, and **Play the receiver at full refinement** (`animation.fullRefinement` in a link) turns it off. A GPU rasterizer was considered and declined (see [Declined approaches](#declined-approaches)).

**2D results stay JSON** (`tangentGardenCompute`). Across the 2D presets on 2026-10-09, the largest were Van der Pol (2.9 MB; natively 24 ms to compute and 8 ms to encode, and 15 ms to decode and copy in Node), the pendulum (2.0 MB) and the star's ripples (1.8 MB); about fifty are 0.1–0.4 MB, where JSON costs a millisecond or two. JSON is at most about a third of the largest one's frame, against 75–90% of a tube frame before spatial results left JSON. The heaviest refined flight, **Inside a star's point** refined to a zoomed view, parses a 1.48 MB reply in 2.2 ms once per piece and builds its 14,630 points' path strings in 1.2 ms a frame (2026-10-13), and plays at the 30 fps cap. If a 2D study grows large, add `engine.Vec` (and its pointer, for gaps) as a kind in `cmd/wasm/lift` and `web/lifted.ts`, send the planar result through `liftReply` as the 4D bridge does, and restore it where the worker parses the planar reply.

Moving the meshes and arrays out of JSON took a tube frame in Node from about 800 ms to 50 ms and a surface study's from about 430 ms to 210 ms; Go's own work is most of what remains. A hand-written `MarshalJSON` was tried for the mesh and was no faster: formatting floats to their shortest text dominates, and `json.Marshal` re-scans a `Marshaler`'s output.

### Declined approaches

These were considered and declined. Reopen one only when its stated condition changes.

- **A GPU receiver rasterizer** (2026-10-25). Drawing each cell's triangles with additive blending into a float target would move the receiver's numerics into a shader, give results that differ by device, and need its accounting kept separately, while removing only the rasterizer's half of a WASM frame: about 1.7× at 960 bins refined twice. Playback spreads a coarser level instead (above), about 2.5× faster. Revisit only if finding, landing and emitting cells becomes much cheaper than rasterizing them.
- **2D results off JSON** (2026-10-25): see **2D results stay JSON** above.
- **Worker pools** (2026-10-25). A third playback engine costs about 100 MB.
- **Fewer contact circles on a refined canal** (2026-10-25): it would change the drawing; see the refined canal above.
- **Saved study files** (2026-09-30). Portable links suffice.
- **Out of scope:** lighting and material editors, imported scenes, collisions, path tracing, and a backend.

`NotebookMode` provides a prominent 2D/3D/4D study menu and browser history. Each notebook mounts on its first visit and remains mounted but hidden afterward, preserving edited studies and manual cameras. Changing mode cancels playback/export and quick rotation. Theme preferences synchronize between the notebooks, including when storage is denied. The spatial module loads lazily; the 2D notebook works without WebGL.

`web/spatial/scene.ts` turns a result into everything the drawing shows (`buildScene`): world-space line pairs and triangles, each vertex with a normal and a phase, and an ink. `scenePasses` gives the batches a set of layers shows, in drawing order, and `camera`/`clip`/`page` hold the orthographic camera's arithmetic, the same as the vertex shader's. `web/spatial/palette.ts` holds the drawing's colors; the fragment shader is written from them. `web/spatial/renderer.ts` uploads a scene and performs depth testing and shading only. Each construction has its own layers (surface, rulings, and edges for the developable, the framed ribbon, and the ruled surface, whose edge is its partner thread; strands, frame glyphs, and seam for the framed construction; the canal surface with its contact circles, meridians, frame glyphs, and seam; other trajectories, field directions, and seeds for a vector field under any construction; other pursuers, connecting polygons, and starts with the capture for a pursuit; the surface patch, its parameter curves, normal lines, offset, and each focal sheet for a surface study, the sheets shaded in their own inks; the mirror or interface, its parameter curves, incident and outgoing rays, each caustic's real part, virtual rays and caustics, and the receiver's irradiance for a ray study; filaments and strings for the involute; image, correspondences, sphere, and source for the inversion) and its own line inks; collapsed filaments become a small cross sized to the fitted bounds. Separate sheets meet at the singular spine; invalid normals leave mesh gaps. Orthographic projection preserves equal spatial scale. Manual orbit/pan/zoom is separate from an animation camera override. WebGL absence or context loss is explicit. Buffers, programs and shaders are disposed; offscreen export contexts are released after use.

The parameter probe (`web/spatial/probe.ts`, `ProbePanel.tsx`) asks for diagnostics only while it is on, through `EngineClient.computeSpatial(config, { diagnostics })`; the compute key includes the flag, so turning it on recomputes once, and moving it never does. Its place is a fraction of the base's samples (`probeIndex`), carried in study links as `probe: { enabled, position }`. `probe.ts` holds one table of per-construction highlights and one of per-format highlights (a pursuit's polygon, a harmonic curve's chain, a field's timeline), which components read rather than branching on construction or format names, and builds the probe's few line batches (`probeBatches`) from the diagnostics and the study's own per-sample arrays: nothing is recomputed in TypeScript except the osculating circle's polyline, drawn from Go's center and radius as the scene draws spheres, and a harmonic chain's ellipses, drawn from Go's joints by the scene's own `harmonicEllipses`. A harmonic study's per-sample chains (`harmonic.chains`) are returned only with `diagnostics`. The batches use inks 8–11 (the probe, T, N and B), which the shader and `lineColor` color alike. `scenePasses(scene, layers, probe)` appends them last under the pass layer `probe`, so the renderer (`setProbe`, with its own buffers), still image export and vector linework all draw the same probe. It is not a `Layers` flag. Every animation with the probe on draws it. Those that keep the study fixed (reveal, orbit, camera path, trace, peel) start from the study's own diagnosed frame and set `AnimationView.probe` to the user's step (`probeStep`), except that a reveal sets `probeAway` until `revealedThrough` reaches the sample the step is drawn with (`probeSample`, by the shared `revealedProbe` in `web/probe.ts`); the 2D notebook does the same with its curve samples. The animation mode `probe` instead samples the study's own diagnosed frame at every progress and sets `AnimationView.probe` to `probeIndex(progress, n)`; `SpatialApp` then draws and reads out that sample while leaving the user's `probe.position` alone, and `exportAnimation` calls `setProbe(probeBatches(...))` on each frame, so playback and export share the probe's batches. The mode needs no per-frame engine work. It is offered only while the probe is on, and links refuse it otherwise. Parameter playback with the probe on computes each frame, and both cached endpoints, with `probeOptions(target)`, and `heldProbe` (in `probe.ts`) chooses the frame's step from the session's original diagnostics, the frame's own, and `ProbeMotion` (`stays`, `length` or `along`; `probeMotions` and `probeMotionHelp` name them per target). It returns either a step, set as `AnimationView.probe`, or a sentence, set as `AnimationView.probeAway` and shown in the panel. `length` uses `DiagnosticsResult.length`, the cumulative arc length Go measures in `measure` (`engine3/diagnostics.go`) from the sampling loop's speeds, midpoints and breaks; TypeScript only picks the nearest sample. Links carry the choice as `animation.probeMotion`; older links stay, and a grid's `length` stays as the panel's does. Presets may bring `probe` and `flight.animate.probe`; a preset's probe joins its gallery fingerprint, as its cut does. The surface probe follows the same design. `probe.target` chooses the curve or the surface where a study offers both (a canal, tangent developable, ruled surface, or framed ribbon with a width). A surface study offers only its surface. `surfaceKind` names the study's surface as Go does, `probeSupport` lists the targets, and the descriptor table behind `surfaceTerms` holds each kind's names, parameters, branches, sliders, notes and help; components read these rather than branching on formats or kinds. The request then sets `surfaceDiagnostics` instead of `diagnostics`, and the compute key includes the target. Go returns `engine3.SurfaceDiagnostics`: a grid of points, normals, both principal curvatures, directions and focal points, on the patch's own grid or a canal's regular rows along t × 24 turns, independent of its mesh (`engine3/surfaceprobe.go`), or the same rows × points along the ruling of a developable, framed ribbon or ruled surface (`engine3/ruledprobe.go`). `ruledProbe` serves those three as S = a + u d, each supplying S_t, S_u, S_tt and S_tu from its own derivatives (r‴ from the curve probe's `jerk`, a frame's turning from its transport equations, a partner's b″), and solves them with the patch's `shape`, so all surfaces share one shape operator. Its counts cover singular points, umbilics, unknown curvatures and clipped centers. A canal's and a ruled surface's focal points are clipped in `Compute` against the finished study radius, as the curve probe's centers are. A patch's are clipped against its own reach, as its focal sheets are. `surfaceProbeBatches` draws the point, a canal's contact circle or a ruled surface's ruling, the normal line, and each branch's direction, center and circle from those arrays, in inks 5 and 6 (the focal sheets' rust and slate) and the probe's mark and normal inks. `probeDrawing` and `probeRecord` dispatch on the target for live drawing, still export metadata and animation export. `AnimationView.probeSetup` carries the probe's target and column, so a probe animation moves along a surface's rows at a fixed column. Links carry `probe: { enabled, position, target, across }`. Older links gain the curve target and the middle column, and an older link to a surface study, which had no probe then, opens with it off. A mirror or interface study offers the targets `light` and `mirror` instead. `mirror` sends `surfaceDiagnostics` and gets the patch probe. `light` sends `lightDiagnostics` and gets `SurfaceDiagnostics` of kind `wavefront` from `lightProbe` (`engine3/rays.go`): the outgoing wavefront on the patch's grid, with the ray as its normal, μ as its curvatures and the caustic points as its focal points, clipped as the caustics are, plus a `light` block of incident directions, surface normals, outgoing directions and per-sample states. `probeOptions` maps each target to its request flag, and `probeSteps` requires a wavefront for the light and anything else for a surface or the mirror, so a stale result is never read as the other. `surfaceProbeBatches` adds the incident and outgoing rays to a wavefront's drawing, `lightProbeReadout` computes θ, θ′, the foci's distances and their interval from the returned vectors, and `ProbePanel` shows them instead of K and H. The link records the target the probe describes, not the last one chosen elsewhere. An older link to a mirror or interface study, which had no probe then, names neither `light` nor `mirror` and opens with it off. A surface study with an offset offers the targets `surface` and `offset`. `offset` sends `offsetDiagnostics` and gets `SurfaceDiagnostics` of kind `offset` from `offsetProbe` (`engine3/surfaceprobe.go`), on the patch's grid from the same samples, with the patch's normals and directions, curvatures κᵢ/(1 − dκᵢ) numbered as the patch's, its `distance` d and per-point `folds`. `probeSteps` requires that kind for the offset and refuses it for the surface, and `surfaceProbeBatches` extends an offset's normal line to the patch's point. Every surface study also offers `focal1` and `focal2`, which send `focalDiagnostics: 1` or `2` and get `SurfaceDiagnostics` of kind `focal` from `focalProbe`, with its `sheet` and per-point `feet`, the patch's points whose centers they are; asking for a sheet with the patch's or the offset's diagnostics is refused. `probeSteps` requires that kind and sheet, `surfaceProbeBatches` marks the foot and joins it to the point along the patch's normal, and the descriptor's `singular` words replace the panel's status at a singular point. Like the patch and the offset, a focal sheet clips its own centers, so `Compute` does not clip them again.

The cutaway plane (`web/spatial/cut.ts`, `CutPanel.tsx`) is a drawing setting and never reaches Go: the study, its result, its counts and its probe are the same with or without it. `cut.ts` is its single descriptor: the `Cut` fields, defaults, limits, labels and help, `cutPlane` (validation naming the field, and the unit normal), `cutSpec` (the plane as drawn, or nothing with the reason), `isCut` (which passes each scope cuts), `cutEdges`, `sweepExtent`/`sweepOffset` and the export record `cutRecord`. The renderer (`setCut`) receives a `CutSpec`. Its vertex shader computes the scaled signed distance as a varying, and its fragment shader discards beyond the plane for each pass `isCut` names. The vector line drawing applies the same test on the CPU: in its depth raster, in its visibility test, and by clipping cut lines in world space. Both draw the edge as the pass layer `cut`, between the sheets' lines and the probe, in ink 12. It is not a `Layers` flag. The edge is computed in TypeScript from the scene's own triangles rather than in Go, because it describes the drawn mesh, as `boxEdges` and `receiverSheet` do, not a new mathematical object. It must agree with where the shaded sheet visibly ends, and a peel recomputes it every frame without a round trip to the worker. The renderer caches it by scene, layers and spec. An implicit surface's section curves, by contrast, are Go's. Playback adds the mode `cut`, which keeps the study's own frame and sets `AnimationView.cut` to the spec at that progress, so `SpatialApp`, the plot and `exportAnimation` draw it while the entered `cut` stays untouched. Other modes draw the entered cut, and an export uses the cut captured when it began. Other planes (`others`, at most five, and `beyond`, `every` or `any`) are optional fields of `Cut`, present only while there are other planes, so one-plane cuts, their links, fingerprints and files are unchanged. `cutPlaneInputs`, `withCutPlanes` and `addCutPlane` read and edit the planes in order, the first being the cut's own normal and offset. `CutSpec` carries `others` and `beyond` likewise. The shaders take the planes as `uniform vec4 cut[6]`, interpolate six signed distances as two `vec3` varyings, and combine them with `cutEvery`. The line drawing's raster stores every plane's side at each corner and `hiddenBy` combines them. `cutEdges` clips each plane's own edge to the other planes' half-spaces, and `movedCut` moves every plane with the first for a peel. Links carry `cut: { enabled, normal, offset, cuts, edge, others?, beyond? }`. Older links take `defaultCut`, which is off, and a link refuses a zero normal while the cut is on, or the mode `cut` without the cut. A preset may carry its own `cut`, which choosing it applies (any other preset turns the cut off). Its gallery fingerprint then covers `{ config, cut }`, presets without one keep their old fingerprints, and the stage's `data-cut` lets the thumbnail script wait for it. Still exports add `cut` to their metadata only when there is one, so files without a cut are unchanged.

Seeing through (`web/spatial/sight.ts`, `SightPanel.tsx`) is also a drawing setting that never reaches Go. `sight.ts` is its descriptor: the `Sight` fields, defaults, limits, labels and help, `sightSpec` (the setting as drawn: an invalid opacity leaves the sheets opaque, with the reason), `isPlain`, `arcLengths`, `dashesPerUnit` and the export record `sightRecord`, which is present only when the drawing is not plain, so files of plain drawings are unchanged. The renderer (`setSight`) keeps the plain drawing's pass order and code path when `isPlain` holds. Otherwise it draws the sheets first. For see-through sheets it sums them into a half-float (or float) color target, made when first needed, with additive blending, composites the sum over the background in one full-page pass, and then writes the sheets' depth alone. Hidden lines are drawn next with `GREATER` depth testing, blending and no depth writes, and the visible lines last. `seeThrough()` reports whether the target could be made; without it the sheets stay opaque, the panel says so (through `SpatialPlot`'s `onSeeThrough`), and an export's record states it. Dashes need each line vertex's arc length, which the renderer computes and uploads per line batch the first time it draws dashes. The vector line drawing returns hidden runs in their own `LineGroup`s, marked `hidden`, written first as `hidden-` groups with their opacity. Links carry the setting as `sight`, links made before it open with the default, and a preset may carry its own; its fingerprint then includes it, as it includes a cut. Playback draws the current setting, and an animation export keeps the one it began with.

`SpatialAnimationPanel` mirrors planar session semantics with immutable originals and cached endpoints, one awaited live computation, clamped monotonic progress, bounded scrubbing, and epoch cancellation on stop/pause/edit. Reveal slices the final grid; parameter playback evaluates fresh curves without blending geometry. Orbit changes only the camera, and so does a camera path. `web/spatial/path.ts` is the path's descriptor: the `CameraPath` and `KeyView` types, limits, labels and help, `pathError` (why a path cannot play, naming the field), `keyFromView` (a shown view as a key view about the study's bounds), `pathView` (the camera at a progress, the key view itself at each view's time) and `pathLeg` (the readout). The panel snapshots the path when playback begins, with the study's bounds then (`around`, which its views were taken about), and passes both in each `AnimationView`; `animationCamera` returns `pathView` at the view's own progress for it, ignoring the camera mode and each frame's bounds unless the path fits each frame while parameters vary (`fitsFrames`), when `fitFrame` carries it by the similarity from `around` toward the frame's bounds, weighted min(1, 1/zoom), so playback, scrubbing, the released camera and exports share it, and a late parameter frame is drawn with the camera of its time. The path flies in the path mode (geometry fixed) or as the `"path"` camera mode of every other mode but the orbit (geometry moving); `CameraMode` is the 3D notebook's own, and `spatial/link.ts` carries `"path"` outside the shared camera options, refusing it with the orbit. The drawing's camera stays a manual camera about the study's bounds throughout. **Show** reaches `SpatialPlot` as a restored manual camera on the next reset. Links carry the path inside `animation` as `path`; links made before it fly none. A preset may carry a `flight` (a path and its duration, and optionally `animate`: a mode and tracks to fly it over); choosing a preset sets it, or clears the path and leaves the path mode and camera. The notebook passes the flight only once the frame belongs to the preset, so a trace mode or tracks it brings are judged against the preset's own study. The camera that rides a ray is the `"ride"` camera mode, offered only while light is traced. `web/spatial/ride.ts` is its descriptor: the `Ride` setup (a crossing (i, j), −1 for the middle, and the follow distance and turn window in framing radii), its limits, labels and help, `rideChoices` and `snapRide` (the crossings and the nearest to a choice), `rideError`, `ridePath` (the ray's polyline as optical path from the study's own rays and the trace `Timeline`, which now also says whether the light is refracted), `ridePose` (eye, forward, up and head at τ), `rideView` and `rideReadout`. The panel builds the polyline when playback begins, about the study's bounds, and passes it in each `AnimationView` as `ride`; `animationCamera` returns `rideView` at the view's own progress. A `View` with a `lens` is drawn in perspective: `scene.ts`'s `camera` builds the rotation, focus point and a `lens` triple, `clip` returns homogeneous coordinates with w = 1 for every orthographic view (so no existing drawing changes), the vertex shader takes the same `lens` uniform, and the line drawing (`linework.ts`) clips segments in homogeneous coordinates, clips the hidden-line raster's triangles at the near plane, and interpolates cut sides and dash phase perspective-correctly. The released ride camera keeps the held view's fields beside its lens; `SpatialPlot` drops the lens on the first orbit, pan or zoom. The manual camera's projection is `View.projection` (`scene.ts`'s `Projection` and its `projections` table of labels and fields of view; absent means orthographic). `camera` builds a lens from the turntable for a perspective projection (`turntableLens`: the eye behind the panned target at 1.16 r / (zoom tan(α/2)), near and far from the study's radius) and returns the orthographic camera unchanged otherwise. `SpatialApp` holds the choice, keeps it through Reset view, and passes it to `SpatialPlot`, which stamps it on the manual and released views; an animation's views spread the held view, and `animationCamera` gives a camera path the held view's projection. `keyFromView` keeps a perspective eye in place, `sameCamera` compares projections, `projectionRecord` puts it in export metadata, and links carry it as `projection`. The `"chosen"` projection has no fixed field of view: it draws `View.lensAngle` (whole degrees within `lensAngles`), and `turntableAngle(view)` is the one place that resolves a view's angle, for `camera`, `keyFromView`, `sameCamera` and `projectionRecord` alike; every other projection ignores `lensAngle`. `SpatialApp` holds the angle beside the projection (starting it from a named lens's angle when the chosen angle is picked from one), shows **Lens angle** after the named views in `.camera-controls` only while it is drawn, and passes it to `SpatialPlot`, which stamps it on the shown view only with the chosen projection; `animationCamera` gives a camera path the held view's angle with its projection, and links carry it as `lensAngle`. A preset may carry a `projection` and an opening manual `view`, and with the chosen projection a `lensAngle`; all join its fingerprint, and the stage exposes them as `data-projection`, `data-lens-angle` and `data-opening` for the thumbnail builder. Links carry the ride inside `animation` as `ride`, and `"ride"` outside the shared camera options, refusing it without a trace; a preset's `flight` may carry a `ride` in place of a path. The four framing modes preserve orientation, and Hold current view snapshots effective pan/zoom. Stop restores the manual view. `web/timing.ts` is the notebook-independent timing of a repeat and pace: `progressAt` maps the timeline's time to the motion's progress, and `cycles` says whether playback wraps and an export leaves out its end (`exportTiming(…, cyclic)` then spaces frames over one period). `play` takes `repeat` and wraps its time, ordering replies by the unwrapped time. The 3D session holds `repeat` and `pace`; `sample(s, time)` draws `frameAt(s, progressAt(time))` and records both in the `AnimationView` (`time` for the timeline and `data-time`, `progress` for the drawing), and `complete` only for a single pass at its end. `web/spatial/loop.ts` holds which modes loop, the repeat and pace words, and `loopGap`, which the panel runs on the frames at progress 0 and 1 before a loop plays or exports: it compares their scene passes (the drawn batches, vertex for vertex), the probe's batches and `animationCamera`'s views, and names what differs. A loop's `AnimationView` sets `cyclic`, so `pathView` gives a smooth path periodic slopes at its seam. Links carry `repeat` and `pace` inside `animation`, refusing a loop of a mode that cannot return; older links play once, steadily. A preset's `flight` may bring `repeat`, `pace` and a `camera` in place of flying its path. The repeat and pace choices and their shared help live in `timing.ts`, and `study-link.ts` holds their link schema (`animationTiming`), used by all three notebooks. The 2D and 4D notebooks check a loop with `web/loop-check.ts`: `markupGap` compares the SVG at progress 0 and 1 number for number and otherwise character for character, ignoring title, description and data attributes, and `loopRefusal` falls back to comparing both rasterized at the export size, so the same picture drawn in another order still loops. `planar-loop.tsx` and `tesseract/loop.tsx` draw the two frames with React's static renderer, loaded only when a loop plays. In 2D `loops` (`animation.ts`) allows parameter tracks only, and the 2D session's `sample(s, time)` maps time to progress as in 3D; in 4D each motion choice in the descriptor says whether it `loops`, the app's progress is the timeline's time (`data-time`) and `data-progress` the motion's. Both export with `exportTiming(…, cyclic)`. Presets may bring `repeat` and `pace` (a 2D preset its whole `animation`); others play once, steadily. `FrameRateField.tsx` is the export frame rate shared by every notebook, offering 60 fps for WebP as well as MP4 with a note on its size.

Spatial image and animation export use the same WebGL renderer at the requested intrinsic size, never an enlarged screen capture. PNG is opaque; SVG explicitly embeds that PNG and records inputs, layers, theme and camera in its description. A line drawing (`web/spatial/linework.ts`) needs no WebGL: it projects the same scene's line passes with the same camera and colors, clips them to the clip volume (Liang–Barsky), and joins consecutive pairs that share an end exactly. Sampled hiding rasterizes the shown sheets on the CPU at the page size, keeping the nearest triangle at each pixel center. A line sample is hidden behind a triangle nearest at one of the nine surrounding pixel centers that contains it, when it lies farther than that triangle's depth there by more than the drawing's polygon offset. Interpolating inside the triangle, rather than extending a nearby triangle's plane to the sample, keeps lines on thin, twisted meshes (ruled surfaces) from flickering. Rasterized pixels and line samples share a bounded work count. Animation uses the shared `export-sinks.ts` MP4/WebP encoders, timing, capability detection, quality settings and size limits. Spatial frames are computed and encoded sequentially to bound mesh memory. Cancellation discards output, even when an in-flight operation completes later. Browser tests independently decode downloaded images and animation files.

No new runtime dependency, server, remote resource or CSP resource category is introduced. [Spatial study notes](spatial-study.md) explain examples and limits.

### Where errors are shown

Line weights live in the same descriptor: `Sight.weight`, `lineWeights`, `weightScale`, `strokeUnit`, `inkWeight` (each ink's regular weight; a `Batch` may set its own `weight`), `strokeWidth`, `sheetOffset` and the export record `strokeRecord`, present only for strokes. The renderer draws hairlines with its original program and `gl.LINES`, unchanged. For strokes it links a second program (the same fragment source with `STROKE` defined) that draws each line batch's existing buffer with `ANGLE_instanced_arrays`: six corners per instance at location 0, the segment's ends and phase read from the batch's 7-float vertices at a 56-byte stride, arc lengths from the dash buffer when dashed, and each end's neighbor across its joint from a buffer made by `strokeJoins` when the batch is first stroked (eight attributes, WebGL's minimum). Divisors are reset after each stroke draw, since the other programs share the locations. Strokes two pixels wide or more use alpha to coverage when the canvas is multisampled; thinner and hidden strokes blend with butt ends, their mitred joints neither overlapping nor parting, and thin ones write no depth. With strokes, every sheet is drawn before any line, wide strokes before thin ones. `sheetOffset` sets the sheets' polygon offset from the widest stroke, and `linework` takes `weight` to give each path its `stroke-width` and to sample hiding with the same offset. Without instancing, `strokes()` is false and every weight draws hairlines; the panel says so through `SpatialPlot`'s `onStrokes`, and the canvas's `data-strokes` names the weight only while strokes are drawn. Links made before weights open with `hairline` (`legacyWeight`).

Tapering with depth is the optional `Sight.depth` (`"even"` or `"taper"`, absent in older links), in the same descriptor: `strokeDepths`, `taperRange`, `strokeTaper` (the factor at a clip w), `taperBound` (the most the study's bounds allow, which scales `sheetOffset`), and the line drawing's steps, `taperStep`, `taperStepOf` and `taperBreaks`. `scene.ts`'s `camera` gives every camera a `focus`, the clip w of the plane where tapered strokes keep their width: 1 orthographic, the target's distance over the radius for the turntable's lenses, and 1 for a lens of its own (the ride). The stroke program takes `taper` (on, focus, width) and `split`: each end's width is computed after near-plane clipping, the quad's reach follows it, and the fragment stage interpolates the two ends' widths (`T`) along the segment when `coverTaper` is set; otherwise every value is the uniform one, so even strokes draw exactly as before. A tapered batch is drawn twice, `split` 1 keeping its segments at least two pixels wide on average and 2 the rest. `linework` takes `depth` and splits each run at `taperBreaks` into paths of each step's width. `data-strokes` adds `depth` only while strokes taper.

A validation error about one field is a `FieldError` (`engine`, `engine3` and `engine4` each define one) whose `Field` is the request's JSON path (`curve.roulette.radius`, `unwinding.offset`, `lift.center.1`); validators shared between fields, such as the 2D curve compiler, report a path relative to what they validate and their callers prefix it. `cmd/wasm` adds it to the error reply as `field`, the worker forwards it (and tags its own whole-number checks the same way), and `EngineClient` rejects with an `EngineError` carrying it. Each notebook maps the path to the name of the control that edits it: `web/planar-fields.ts` (a field's help topic where it has one, else its label), `web/spatial/fields.ts` (mostly through the animation tracks' labels) and `web/tesseract/fields.ts` (from the object descriptors, with the labels every 4D object shares). The 2D, 3D and 4D apps provide the target through `FieldErrorContext` (`web/Field.tsx`): a `Field` whose control has the failing scalar input's id, or whose label is the engine error's, shows the message under its control with `role="alert"` and `aria-invalid`, opens any closed section around it, scrolls it into view if needed, and claims it before paint, so the notebook's own alert appears only when no field can show it. That alert (`StudyError`) is compact, stands after the study's controls and is brought into view the same way, since the controls can end below the screen or the sidebar's scroll. The animation panels are outside the provider, so their own fields' errors use that alert. Every notebook keeps its previous valid drawing while the study is invalid, marked **Previous valid study** outside the geometry, and asks for a definition only when there is no drawing yet. An error about the study as a whole (no field) goes under the control last changed. The cut and see-through panels receive the target without its label, so a label they share with a study control (**Offset d**, **Normal x**) only ever shows their own inputs' errors. In a `.pair`, the error has its own subgrid row between control and help, so it never moves the neighboring control.

## Tesseract notebook

`engine4` defines an independent 4-cube request and result, including projected paths, section faces, diagnostics and a rotation-independent framing sphere. `tangentGardenTesseract` in `cmd/wasm` transports JSON, with its large numeric arrays lifted out beside it (see above); the existing worker validates finite inputs and routes the request. `web/tesseract` provides its own SVG drawing, ordinary 3D camera, coalescing numerical queue, playback and export sampler. It never extends a curve type with a dummy coordinate. The shared header lazily mounts the 2D, 3D and 4D notebooks, preserving each study and camera and stopping hidden playback. The tesseract's transparent vector style makes no opaque visibility claim. See [the study documentation](tesseracts.md) for scope and limits.

The 4D request now has `object: tesseract | ball | tube | lift | bypass | weave` independently of its `mode`; an omitted object retains legacy tesseract evaluation. The object descriptors in `web/tesseract/objects.ts` publish supported modes and rotations. `engine4/curved.go` evaluates bounded analytic axis-aligned curved sections. Worker validation carries active radii, curve/sample counts and section inputs through the existing bridge, rejecting nonfinite values before JSON can turn them into null. Smooth section diagnostics carry kind, radius and section dimension rather than polyhedral counts. Curved-object source/section/branch identities and path roles pass unchanged to vector drawing and export metadata. See [curved section contracts](tesseracts.md#exact-curved-sections).

Object descriptors in `web/tesseract/objects.ts` own supported operations, labels, explanations, support, defaults, diagnostics, legends and export descriptions. Controls, the shared renderer and animation help consume those descriptors. Per-object last valid configurations preserve definitions during object switching. Selected curved-section identity is a rendering layer setting shared by live drawing and all exports; geometry remains in Go.

`engine4/lift.go` evaluates six fixed analytic source curves, their compactly supported fourth-coordinate lift, and exact reference-slice intervals. Line/sphere quadratic roots and circle/sphere trigonometric roots partition sources before sampling. Returned paths carry source identity, role, branch, original parameter values and corresponding four-dimensional coordinates; reference coordinates have w = 0. The worker transports the optional lift parameters without classifying geometry. The immutable shared sampler interpolates explicit center or support-radius endpoints. Switching linked views preserves its progress and the manual camera. Descriptors own lift controls, motion choices, guide layers and readouts; the SVG renderer applies the final 3D camera and visibility settings. All annotations stay outside the geometry viewport. See [localized lift contracts](tesseracts.md#localized-thread-lift).

`engine4/bypass.go` classifies complete three-leg routes against canonical embedded and radial shells using analytic sphere/slab events. Both `shadow` and `diagram` return the same physical route, progress, hit intervals and stable point identities; Go owns their projections and framing. Optional bypass parameters and markers extend the existing WASM/worker transport. The descriptor owns the numeric fields, obstacle choices, layers, diagnostics and forward/reverse motion. The diagram applies equal planar scale, pan and zoom while retaining the ordinary camera for the XYZ shadow; it never classifies geometry in TypeScript. The opt-in `paired` mode returns the shadow plus a `companion` diagram in one worker result, evaluated from the same immutable request. Top-level work counts include both representations. React commits that combined frame atomically. `Composition.tsx` arranges already-projected geometry in columns or rows with independent panel cameras and equal axis scale. Live interaction, still images and animation exports reuse this composition; no geometry is classified in the composition layer. Single-view rendering retains its existing path. See [shell bypass contracts](tesseracts.md#shell-bypass).

`engine4/weave.go` evaluates Clifford-torus and Hopf-fiber circles on S³, rotates them in 4D and clips each circle against the stereographic window analytically before sampling. The optional `weave` request and diagnostics extend the existing WASM/worker transport; the worker validates only the active weave fields and ignores spread for a single latitude. Its descriptor supplies the family choice, count fields (`countFields`), latitude key text (`sectionKey`), rotation and latitude motions, readouts and notes. The shared renderer colors paths by latitude through the same section index used by curved sections, without section selection. The tesseract's stereographic clipped-count sentence now comes from its own descriptor, not from a mode check in the component. See [spherical weave contracts](tesseracts.md#spherical-ring-weave).

## Spatial trajectory families

For field and pursuit requests, `allPaths` applies the construction independently to the integrated paths. Request-local evaluators share the original integration while keeping member units, frames, composed inputs and discontinuities separate. The first result retains readouts and probes; `members` carries the other construction results in source order, with an explicit unavailable note for a path without regular samples. Source trajectories and integration diagnostics are returned only once. All member surfaces concatenate into the root indexed `mesh`, with index offsets and the same per-triangle sample grid; child meshes are empty. The existing typed mesh transport carries every triangle, while the generic lifted arrays carry nested member curves. Shadows independently use `shadow.allPaths`, with per-path comparisons in `shadow.family` and a shared plane window. Scene passes, vector linework, still and animation exports read the same member geometry; reveal truncates every member on the shared time grid.
